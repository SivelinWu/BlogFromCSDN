# [测试技术] 数据库主从延迟怎么测？读写分离下的旧数据与状态回退

> 原文: https://blog.csdn.net/weixin_42390585/article/details/164057965

> 原创内容，未获授权禁止转载、转发、抄袭。

页面刚提示“保存成功”，刷新一下，收货地址却又变回了旧值；过几秒再刷，它又自己正常了。这种看起来有点玄学的问题，常常和数据库读写分离有关。系统把写请求交给主库，再把查询分到只读副本，主库事务虽然已经提交，变更却可能还躺在副本的 Relay Log 里，没有真正更新到业务表。更麻烦的是，后台任务若从副本读出旧对象，再整行保存到主库，刚写入的新地址还可能被覆盖回去。
它通常只出现几秒，到了测试环境更是时有时无。一直刷新页面等它露面，效率很低，也很难证明修复是否真的有效。与其碰运气，不如主动暂停 MySQL 副本的 SQL 线程，留出一段稳定的复制延迟，再去观察查询路由、读己之写、乐观锁和恢复过程。文中的命令只适合隔离测试副本，生产副本和多人共用环境不要尝试。
### 先别造故障，确认业务能接受多旧
读写分离之后，并不是每个查询都要强一致。商品浏览量晚几秒问题不大，刚修改的地址、余额和订单状态却经不起随意回退。动手前先把这些接口分清楚，否则好不容易复现了旧值，大家还要现场争论这到底是缺陷还是正常设计。

场景| 建议约定| 测试断言  
---|---|---  
修改资料后立即查询| 同一用户读到自己刚完成的写入| 返回版本不小于写接口返回的版本  
订单、余额等状态查询| 强一致或单调读| 不能从新状态退回旧状态  
报表、推荐等读多场景| 允许最终一致| 在约定时间内追平，超时告警  

最终一致还要约定“从哪一刻开始算、到哪一刻才算追平”。这里从写接口成功响应开始计时，直到所有可能承接该查询的副本都能返回目标版本。只看到一个副本追平就收工，用户下一次随机路由仍可能掉进旧数据里。
后面一直用同一份数据：用户 `U-1001` 的收货地址是“测试路 10 号”，`row_version=7`。更新接口写主库，详情接口默认读副本。写成功后，接口返回新的 `rowVersion`；测试环境的响应 Header 再带上 `X-DB-Node`，这次请求去了哪个节点就一目了然。
`X-DB-Node` 只应在受控测试环境开放。生产环境更适合在服务端日志中记录路由结果、数据库节点标识、业务主键和行版本，避免向外暴露拓扑信息。
### 把副本暂停一下，延迟就不再靠运气
示例使用 MySQL 8.0.22 之后的 `REPLICA` 语法，更早的环境要换成 `SLAVE` 语法。`STOP REPLICA SQL_THREAD` 会暂停副本应用 Relay Log，但接收线程仍然可以继续拉取主库事件。这样就能稳定得到“日志已经到了，业务表还没更新”的状态。下面的脚本按单复制通道编写；若环境里有多个通道，要显式指定 `FOR CHANNEL`，并相应调整状态解析，别停错通道。
暂停复制有一定风险，所以脚本先核对副本身份和运行状态，再准备自动恢复：
    
    set -euo pipefail
    
    REPLICA_LOGIN_PATH='qa-replica'
    EXPECTED_REPLICA_UUID='<qa-replica-server-uuid>'
    
    actual_uuid=$(mysql --login-path="$REPLICA_LOGIN_PATH" \
      --batch --skip-column-names -e 'SELECT @@server_uuid;')
    read_only=$(mysql --login-path="$REPLICA_LOGIN_PATH" \
      --batch --skip-column-names -e 'SELECT @@global.read_only;')
    super_read_only=$(mysql --login-path="$REPLICA_LOGIN_PATH" \
      --batch --skip-column-names -e 'SELECT @@global.super_read_only;')
    status=$(mysql --login-path="$REPLICA_LOGIN_PATH" \
      -e 'SHOW REPLICA STATUS\G')
    io_running=$(printf '%s\n' "$status" \
      | awk '/Replica_IO_Running:/ {print $2; exit}')
    sql_running=$(printf '%s\n' "$status" \
      | awk '/Replica_SQL_Running:/ {print $2; exit}')
    
    [ "$actual_uuid" = "$EXPECTED_REPLICA_UUID" ]
    [ "$read_only" = '1' ]
    [ "$super_read_only" = '1' ]
    [ "$io_running" = 'Yes' ]
    [ "$sql_running" = 'Yes' ]
    
    resume_replica() {
      if ! mysql --login-path="$REPLICA_LOGIN_PATH" \
        -e 'START REPLICA SQL_THREAD' >/dev/null; then
        printf '警告：SQL 线程自动恢复失败，请立即人工检查。\n' >&2
      fi
    }
    trap resume_replica EXIT
    
    mysql --login-path="$REPLICA_LOGIN_PATH" \
      -e 'STOP REPLICA SQL_THREAD;'
    paused_status=$(mysql --login-path="$REPLICA_LOGIN_PATH" \
      -e 'SHOW REPLICA STATUS\G')
    printf '%s\n' "$paused_status" \
      | sed -n '/Replica_IO_Running:/p;/Replica_SQL_Running:/p;/Last_SQL_Error:/p'
    paused_io=$(printf '%s\n' "$paused_status" \
      | awk '/Replica_IO_Running:/ {print $2; exit}')
    paused_sql=$(printf '%s\n' "$paused_status" \
      | awk '/Replica_SQL_Running:/ {print $2; exit}')
    [ "$paused_io" = 'Yes' ]
    [ "$paused_sql" = 'No' ]
    
    printf '副本已暂停，请在另一个终端执行测试；按回车恢复，300 秒后也会自动恢复。\n'
    read -r -t 300 _ || true
    
先把 `EXPECTED_REPLICA_UUID` 换成测试副本的真实 UUID。脚本确认副本原本正常后才会暂停，并留在当前终端等待；此时打开另一个终端执行后面的业务请求，跑完再回来按回车。暂停后应该看到 `Replica_IO_Running: Yes`、`Replica_SQL_Running: No`，且没有新增 SQL 错误。要是 IO 线程也停了，这次实验就已经变味，不再是单纯的复制延迟。
脚本最多暂停 300 秒，退出时会尝试恢复 SQL 线程。别忘了，暂停期间接收线程仍在积累 Relay Log，磁盘空间和待回放量也要看着，尤其不要在高写入环境长时间停留。跑完再确认一次 SQL 线程是否恢复；如果托管数据库不允许控制复制线程，可以申请专用延迟副本，或者在数据库代理层做受控路由。给业务客户端加个 `sleep`，模拟不了这里真正要测的链路。
### 复现现场：写成功了，查询还停在旧版本
副本停稳后，从正常业务入口修改地址。下面的域名和 Token 都是占位内容：
    
    set -euo pipefail
    
    API_BASE='https://profile.example.test'
    TOKEN='<test-token>'
    HEADERS=$(mktemp)
    trap 'rm -f "$HEADERS"' EXIT
    
    curl -fsS -X PUT "$API_BASE/api/users/U-1001/address" \
      -H "Authorization: Bearer $TOKEN" \
      -H 'Content-Type: application/json' \
      -d '{"address":"测试路 20 号"}' | jq .
    
    curl -fsS -D "$HEADERS" \
      "$API_BASE/api/users/U-1001" \
      -H "Authorization: Bearer $TOKEN" | jq .
    
    awk 'tolower($0) ~ /^x-db-node:/' "$HEADERS"
    
    mysql --login-path=qa-source-read --table \
      -e "SELECT address, row_version FROM app.user_profile WHERE user_id='U-1001';"
    mysql --login-path=qa-replica --table \
      -e "SELECT address, row_version FROM app.user_profile WHERE user_id='U-1001';"
    
写接口返回“测试路 20 号”和 `rowVersion=8`。马上查询详情，如果请求命中副本，拿到的可能还是“测试路 10 号”和 `rowVersion=7`。一张页面截图解释不了这件事，把接口和数据库证据摆在一起会清楚很多：
    
    写接口响应：address=测试路 20 号，rowVersion=8
    详情接口响应：address=测试路 10 号，rowVersion=7，X-DB-Node=replica-1
    主库记录：    address=测试路 20 号，row_version=8
    副本记录：    address=测试路 10 号，row_version=7
    
如果详情接口承诺“读己之写”，这个结果可以直接判为缺陷；如果它只承诺最终一致，那就继续看副本多久能追平。测试时最好使用独立用户，或者临时关闭这个对象的缓存，同时通过路由日志确认查询真的到了副本。否则折腾半天，抓到的可能只是缓存旧值。
### 行版本可以帮服务做一次选择
一种比较顺手的做法，是让写接口返回 `rowVersion`，客户端后续查询时带上自己能接受的最低版本：
    
    GET /api/users/U-1001 HTTP/1.1
    X-Min-Row-Version: 8
    
服务先去副本找数据。如果记录还不存在，或者副本中的 `row_version < 8`，再转去主库。这里的版本只在 `U-1001` 这条记录内比较，不能拿用户 A 的版本约束用户 B。测试时分别发送不带 Header、携带 8、携带非法值和携带超大版本的请求，观察下面几种结果：
  * 携带 8 时返回版本必须大于等于 8，并能从日志确认发生了主库回退；
  * 副本追平后，同样的请求应恢复走副本；
  * 非法或伪造的超大版本应快速返回约定错误，不能造成无限等待、主库持续高压或缓存污染；
  * 最低版本只能用于一致性路由，不能代替用户鉴权和数据权限校验。


还有一种更直接的做法：写入后的一小段时间内，同一用户的查询都走主库。它实现起来简单，但窗口太长会增加主库压力，太短又可能盖不住复制延迟。系统有多个副本时，还要连续切换节点验证单调读；客户端可以携带上一次看到的版本，避免这次读到 version=8、下次又落到 version=7。不管用版本令牌还是主库粘滞，都要同时看结果是否正确、多少请求回退了主库。接口最后返回新值，只能说明功能兜住了，不能说明这个方案扛得住流量。
### 真正棘手的是，旧对象又被写回主库
单看查询结果，读到旧数据只是暂时显示不对，但用户可能因此重复提交或做出错误操作；如果旧数据又被写回主库，问题就真的落库了。例如备注服务从副本读到 version=7 的用户对象，只改了 `remark`，ORM 却把地址、备注和版本一起保存，主库里的新地址就可能被覆盖回去。
这个场景可以顺着三步跑下来：
  1. 调用地址接口，把地址更新为“测试路 20 号”，得到 version=8。
  2. 调用备注接口，把备注改为“工作日送达”；该接口故意命中仍为 version=7 的副本。
  3. 查询主库，地址必须保持“测试路 20 号”，备注更新结果符合接口契约，版本只能向前增加。


写入侧可以用字段级更新和乐观锁把这个口子堵住：
    
    UPDATE user_profile
    SET remark = :remark,
        row_version = row_version + 1
    WHERE user_id = :userId
      AND row_version = :expectedVersion;
    
当 `expectedVersion=7`、主库已经是 8 时，这条 SQL 的受影响行数应该为 0。服务可以重新读取主库后再按规则重试，也可以返回冲突交给调用方处理，但不能绕过版本条件，更不能拿副本里的整行旧对象硬覆盖主库。并发执行地址和备注更新时，除了最终字段和版本，还要看看审计日志、通知消息有没有重复。
### 恢复复制时，别用 `sleep 5` 碰运气
测试结束时启动 SQL 线程：
    
    START REPLICA SQL_THREAD;
    SHOW REPLICA STATUS\G
    
固定等 5 秒很省事，但数据量、事务大小和机器负载随便变一个，结果就不稳定了。更稳妥的方式是轮询目标业务行，直到副本版本达到主库版本，或者超过测试超时时间：
    
    set -eu
    
    is_uint() {
      case "$1" in
        ''|*[!0-9]*) return 1 ;;
        *) return 0 ;;
      esac
    }
    
    target_version=$(mysql --login-path=qa-source-read --batch --skip-column-names \
      -e "SELECT row_version FROM app.user_profile WHERE user_id='U-1001';")
    is_uint "$target_version"
    
    deadline=$((SECONDS + 60))
    version=''
    
    while [ "$SECONDS" -lt "$deadline" ]; do
      version=$(mysql --login-path=qa-replica --batch --skip-column-names \
        -e "SELECT row_version FROM app.user_profile WHERE user_id='U-1001';" \
        2>/dev/null || true)
      if is_uint "$version" && [ "$version" -ge "$target_version" ]; then
        break
      fi
      sleep 1
    done
    
    is_uint "$version" && [ "$version" -ge "$target_version" ]
    
`Seconds_Behind_Source` 可以拿来辅助观察，但别只靠它判断业务已经追平。线程停止、没有活跃事务或出现部分异常时，这个值可能为空，也不能直接证明目标记录已经可见。自动化回归可以同时检查复制线程、业务行版本和自建心跳表。实验结束后，再确认 `Replica_SQL_Running: Yes`、没有复制错误，待执行日志也已经收敛。
确认所有测试副本追平后，再通过测试数据工厂清理 `U-1001`，或者把它重置为下一轮需要的状态。不要直接改副本，也不要为了恢复版本号去手工回写旧值；测试数据本身也应该沿正常写链路复制过去。
### 最后留下哪些回归用例

场景| 关键断言  
---|---  
写后立即读| 承诺读己之写的接口，返回版本不小于写接口版本  
新增后立即查询| 副本尚无记录时按契约回退主库，不能误报 404  
删除后立即查询| 已删除数据不能因副本延迟再次出现在可操作页面  
最终一致查询| 副本在约定时间内追平，超时可观测、可告警  
连续多次读取| 同一业务状态不能从新版本退回旧版本  
最低版本路由| 副本版本不足时回退主库，追平后恢复读副本  
非法最低版本| 不无限等待，不持续压垮主库，不绕过权限校验  
旧对象更新| 备注更新不能覆盖主库中的新地址  
并发字段更新| 乐观锁冲突可识别，最终字段和副作用正确  
SQL 线程恢复| 用业务版本确认追平，复制线程和错误状态正常  

性能测试还要单独看看主库回退比例、连接池占用和 P95/P99 响应时间。大量请求同时发现副本太旧，可能会一起涌向主库。功能上虽然返回了正确数据，主库却被回退流量打满，这个方案同样不能算通过。
### 总结
主从延迟平时很难抓，主动暂停副本 SQL 线程后，它就不再神出鬼没。写接口返回的行版本、查询命中的节点、主副本记录以及后续写入产生的副作用，都可以一项项对上。
说到底，承诺读己之写或单调读的接口要守住两条线：用户刚完成的写入，后面不能越读越旧；从副本拿到的旧对象，也不能覆盖主库里的新数据。把一致性约定、行版本和路由证据放进自动化回归，下次再遇到“刷新一下又好了”，就不用守在页面前碰运气了。
