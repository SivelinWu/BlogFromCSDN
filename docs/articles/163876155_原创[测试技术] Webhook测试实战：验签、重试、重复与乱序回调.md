# 原创[测试技术] Webhook测试实战：验签、重试、重复与乱序回调

> 原文: https://blog.csdn.net/weixin_42390585/article/details/163876155

> 原创内容，未获授权禁止转载、转发、抄袭。

支付完成后，支付平台把结果 `POST` 到商户系统；物流状态变化后，物流平台再推一次；商户接口一时超时，平台稍后把同一事件重发。页面上看起来只是几次 HTTP 回调，真正出问题时却常常落在状态同步：签名校验拿错了报文，重试把退款处理两次，旧事件晚到把“已退款”改回“支付成功”，接收端已经返回成功响应，后台任务却在随后失败，发送方也不再补发。
本文用“支付状态通知”做一个完整案例。示例平台通过 Webhook 告知商户 `payment.succeeded` 和 `payment.refunded` 事件，商户服务验签后先把事件写入 Inbox，再异步更新订单。这里讨论的是怎样构造请求、制造失败、保留证据和判断副作用，不绑定某个具体支付平台。域名、事件、订单和密钥均为测试数据，命令只应在授权的测试环境使用。
### 先把回调契约写清楚
Webhook 没有统一的重试、验签和幂等协议。不同平台的 Header、签名串和重试条件不同，测试前必须拿到被测平台的正式说明。下面是一份演示契约，后面的用例都以它为准：
    
    POST /callbacks/payments HTTP/1.1
    Content-Type: application/json
    X-Webhook-Event-Id: evt-pay-10001
    X-Webhook-Delivery-Id: dlv-pay-00001
    X-Webhook-Timestamp: <unix-seconds>
    X-Webhook-Signature: v1=<hmac-sha256>
    
    {"eventId":"evt-pay-10001","type":"payment.succeeded","version":2,"occurredAt":"2026-10-19T08:00:00Z","data":{"paymentId":"pay-10001","orderId":"order-10001","amount":10000,"currency":"CNY","status":"SUCCEEDED"}}
    
字段| 契约  
---|---  
`eventId`| 一次业务事件的稳定标识；重试和人工回放都不变。Header 与 Body 中的值必须一致  
`deliveryId`| 一次投递尝试的标识；同一事件重试时变化。它只用于审计，不能作为鉴权或幂等依据  
`version`| 同一 `paymentId` 的单调递增状态序列，不是报文 Schema 版本  
签名串| `timestamp + "." + 原始 HTTP Body 字节` 的 HMAC-SHA256。Header 中的 `eventId` 必须与已签名 Body 一致；若 `deliveryId` 也需要防篡改，必须纳入平台定义的签名串  
时间窗口| 接收时间与 `X-Webhook-Timestamp` 相差超过 300 秒则拒绝；每次重试重新签发 Timestamp 和签名  
成功响应| 接收端已持久化 Inbox 后返回 `204`；不等后台业务处理完成  
失败响应| 本示例中，签名或时间戳不合法返回 `401`；签名通过但报文不符合契约返回 `400`  
重试策略| 示例平台对网络错误和 5xx 重试；4xx 是否重试以平台约定为准  

这里的 `300` 秒、`204` 和 HMAC 拼接方式只是示例。Stripe、GitHub 等平台都有自己的签名格式和重试规则，不能把这套 Header 直接复制到生产接口。测试报告里应附上真实的契约版本、回调地址、事件类型、签名算法、密钥轮换策略和重试策略。
### 先准备能串起来的证据
排查 Webhook 时，只有一条“收到回调”的应用日志远远不够。发送端和接收端至少要能按下面字段关联：

字段| 用途  
---|---  
`eventId`、`deliveryId`、`version`| 区分业务事件、投递尝试和业务先后  
`payloadSha256`| 不记录原文也能比对重试和篡改  
`signatureValid`、`timestampValid`| 判断请求为什么被拒绝  
HTTP 状态、耗时、尝试次数| 判断发送端是否重试、何时停止  
`inboxStatus`、任务 ID、`traceId`| 串起接收、异步处理和业务落库  

接收端建议有一个可查询的 Inbox。最小结构不复杂，但唯一键要建立在事件身份上，而不是投递身份上：
    
    CREATE TABLE webhook_inbox (
        provider           VARCHAR(32) NOT NULL,
        event_id           VARCHAR(64) NOT NULL,
        payload_sha256     CHAR(64)    NOT NULL,
        first_delivery_id  VARCHAR(64) NOT NULL,
        status             VARCHAR(32) NOT NULL,
        received_at        TIMESTAMP   NOT NULL,
        PRIMARY KEY (provider, event_id)
    );
    
    CREATE TABLE webhook_delivery (
        provider        VARCHAR(32) NOT NULL,
        delivery_id     VARCHAR(64) NOT NULL,
        event_id        VARCHAR(64) NOT NULL,
        payload_sha256  CHAR(64)    NOT NULL,
        received_at     TIMESTAMP   NOT NULL,
        result          VARCHAR(32) NOT NULL,
        PRIMARY KEY (provider, delivery_id)
    );
    
`webhook_inbox` 保存业务事件，`webhook_delivery` 保存每次到达的投递。重复请求仍会留下投递痕迹，但不会再次扣款或改订单。若同一个 `eventId` 的摘要不同，属于契约冲突或安全事件，应保留原事件、记录冲突并告警。`deliveryId` 不能替代业务幂等键。
### 用原始报文构造一条有效回调
验签用的是原始 Body，不是 JSON 解析后重新序列化的结果。下面的签名脚本保存为测试工具目录中的 `sign_webhook.py`，只负责构造演示契约的 HMAC：
    
    import hashlib
    import hmac
    import os
    import sys
    
    timestamp = os.environ["WEBHOOK_TIMESTAMP"].encode("ascii")
    secret = os.environ["WEBHOOK_SECRET"].encode("utf-8")
    raw_body = sys.stdin.buffer.read()
    
    signature = hmac.new(
        secret,
        timestamp + b"." + raw_body,
        hashlib.sha256,
    ).hexdigest()
    print(f"v1={signature}")
    
在测试终端中创建一份固定事件。密钥从标准输入读取，不打印到终端或报告；使用的必须是测试端点专用密钥：
    
    set -eu
    
    WORK_DIR="$(mktemp -d)"
    trap 'rm -rf "$WORK_DIR"' EXIT
    
    WEBHOOK_URL='https://merchant.example.test/callbacks/payments'
    EVENT_ID='evt-pay-10001'
    DELIVERY_ID='dlv-pay-00001'
    WEBHOOK_TIMESTAMP="$(date +%s)"
    
    jq -cn \
      --arg eventId "$EVENT_ID" \
      '{eventId: $eventId, type: "payment.succeeded", version: 2,
        occurredAt: "2026-10-19T08:00:00Z",
        data: {paymentId: "pay-10001", orderId: "order-10001",
               amount: 10000, currency: "CNY", status: "SUCCEEDED"}}' \
"$WORK_DIR/event.json"
    
    read -r -s -p '测试 Webhook 密钥: ' WEBHOOK_SECRET
    printf '\n'
    export WEBHOOK_SECRET WEBHOOK_TIMESTAMP
    SIGNATURE=$(python3 /path/to/tools/sign_webhook.py < "$WORK_DIR/event.json")
    unset WEBHOOK_SECRET
    
    HTTP_CODE=$(curl -sS \
      -D "$WORK_DIR/response.headers" \
      -o "$WORK_DIR/response.body" \
      -w '%{http_code}' \
      "$WEBHOOK_URL" \
      -H 'Content-Type: application/json' \
      -H "X-Webhook-Event-Id: $EVENT_ID" \
      -H "X-Webhook-Delivery-Id: $DELIVERY_ID" \
      -H "X-Webhook-Timestamp: $WEBHOOK_TIMESTAMP" \
      -H "X-Webhook-Signature: $SIGNATURE" \
      --data-binary "@$WORK_DIR/event.json")
    
    test "$HTTP_CODE" = '204'
    
这条请求只证明接收端接受了事件。接着查询 Inbox：`eventId`、摘要、首个 `deliveryId` 和状态应已写入；再查询订单和后台任务，确认支付状态最后只推进一次。若接收端在业务处理完成前就返回 `204`，后台任务必须有自己的重试和死信记录，不能把 204 当成“订单一定已更新”。
### 验签测试不要改 JSON 对象，要改字节
最常见的验签问题是框架先把 Body 解析为对象，再 `JSON.stringify` 后计算摘要。字段顺序、空格和换行变化后，JSON 语义没变，字节却不同。下面四条请求放在一起跑，结果更容易比对：

场景| 构造方式| 预期  
---|---|---  
正常签名| 原始文件和对应签名| `204`，写入一条 Inbox  
Body 被改| 保留签名，只改 `amount` 的一个字节| `401`，无 Inbox、无任务  
重新格式化| 保留签名，将 JSON 格式化后发送| `401`，无 Inbox、无任务  
过期回放| 使用正确签名但 Timestamp 超过窗口| `401`，无 Inbox、无任务  
标识不一致| 签名有效，但 Header 与 Body 的 `eventId` 不同| `400`，无 Inbox、无任务  

例如，将原文件格式化后仍带着原签名发送：
    
    jq . "$WORK_DIR/event.json" > "$WORK_DIR/event-pretty.json"
    
    HTTP_CODE=$(curl -sS -o "$WORK_DIR/pretty-response.json" -w '%{http_code}' \
      "$WEBHOOK_URL" \
      -H 'Content-Type: application/json' \
      -H "X-Webhook-Event-Id: $EVENT_ID" \
      -H "X-Webhook-Delivery-Id: dlv-pay-00002" \
      -H "X-Webhook-Timestamp: $WEBHOOK_TIMESTAMP" \
      -H "X-Webhook-Signature: $SIGNATURE" \
      --data-binary "@$WORK_DIR/event-pretty.json")
    
    test "$HTTP_CODE" = '401'
    
签名比较是否使用常量时间函数，需要在代码评审或安全测试中确认，单靠接口返回值无法证明。功能测试还要覆盖签名 Header 缺失、格式错误、重复安全 Header 和未来时间戳，并检查拒绝日志只记录摘要和事件标识。接收端应在读完整 Body 前设置请求体上限，测试 `Content-Length` 临界值和分块传输的超限行为；不要为了验签先把任意大小的内容读进内存。契约要求 JSON 时，错误的 `Content-Type` 或未定义的 `Content-Encoding` 也应拒绝，不能交给框架做猜测性解析。源 IP 白名单可以作为额外防线，但不能替代签名或 mTLS；代理、NAT 和平台 IP 变更都会让仅依赖 IP 的校验变得脆弱。
密钥轮换也要纳入回归。准备当前密钥和上一把密钥，在宽限期内分别签名同一类测试事件，两个请求都应通过；宽限期结束后，旧密钥签名必须拒绝。轮换期间如果 Header 支持多个签名版本，还要验证接收端按声明的版本选择正确密钥，不能因“有任意一个字符串像签名”就放行。
签名通过后才进入 JSON 解析和业务校验。Header 与 Body 的 `eventId` 不一致、必填业务字段为空或 `version` 非法时，本示例返回 `400`，不写 Inbox、不创建任务。支付回调还要校验 `paymentId`、`orderId`、金额和币种是否与本地待处理记录一致：构造一条签名有效但订单归属或金额不匹配的报文，订单状态不得改变，并应进入告警或对账流程。未知事件类型则落一条 `IGNORED_UNSUPPORTED` 的 Inbox 和投递审计，返回 `204` 并告警，避免提供方对一个接收端暂不支持的事件无休止重试。真实平台若另有约定，以它的重试行为为准，但“不改业务状态、不创建业务任务”必须是测试断言。
### 重复投递：事件去重和投递审计要分开
先让同一个 `eventId` 再发送一次，Body 保持不变、签名用新的 Timestamp 重新计算、`deliveryId` 改为 `dlv-pay-00003`。本文契约下，接收端应记录一次新的投递审计，但订单状态、库存、积分和其他业务副作用都不能重复执行。
顺序重发能验证分支逻辑，还要做并发重发：用 20 个不同的 `deliveryId` 同时投递同一份签名有效的事件。断言应是 1 条 Inbox、20 条投递审计、至多 1 个业务任务和 1 次业务副作用。这里最容易暴露“先查再插”的竞态，应该依赖数据库唯一键或等价的原子幂等操作，而不是依赖应用内存锁。
还要测一条不应被静默吞掉的异常：用同一个 `eventId` 发一份内容不同但签名有效的 Body。例如把 `amount` 改为 `20000` 并重新签名。接收端不能因为唯一键冲突直接返回 204；它应保留原事件，记录摘要冲突并告警。这样能区分正常重试、供应方数据异常和潜在伪造。
如果应用使用“收到事件后异步处理”的模型，重点测试四个断点：
  1. Inbox 写入前数据库失败：接口返回 5xx，发送方按策略重试，不能产生业务副作用。
  2. Inbox 已提交、任务还未投递时进程退出：服务重启后，`PENDING` 事件能被扫描并且只投递一次。
  3. 消费者领取任务并标记 `PROCESSING` 后崩溃：租约超时后事件能重新领取，不能永久卡在处理中。
  4. Inbox 写入成功、后台处理失败：接口已经返回 204，接收端内部任务重试直到成功或进入死信，业务最终只处理一次。


第 2、3 条经常被忽略。只有事件能被可靠地再次发现，才可以在业务处理前返回 `204`：要么 Inbox 和任务投递记录在同一事务中落库，要么有扫描器补捞 `PENDING` 事件；`PROCESSING` 状态则需要租约或等价的超时回收。再故意在“订单已更新、Inbox 尚未标记完成”之间终止任务，确认订单更新和完成标记处于同一事务，或业务表本身以 `eventId` 做幂等保护。把所有异常都交给发送方重试，容易在长链路里产生重复；过早返回成功响应又会丢掉没有持久化或不可恢复的事件。
### 发送端重试要用可控接收器验证
测试发送端时，准备一个受控接收器。它至少记录请求摘要、必要 Header 和接收时间；定位验签问题需要原始 Body 或完整 Headers 时，应写入有访问控制的测试存储，设置短期保留和访问审计，不写到普通日志。再按事件标识返回 204、400、500，或者延迟到发送端超时后才返回。不要拿真实商户地址制造 500 或超时。
下面这个标准库脚本足够做本地验证。将远端平台的测试回调地址指向经授权的 HTTPS 测试域名，再反向代理到该接收器；本地脚本不应直接暴露到公网。
    
    # webhook_receiver.py，仅用于测试
    from collections import defaultdict
    from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
    import hashlib
    import json
    import threading
    import time
    
    PLANS = {
        "evt-500-then-204": [(500, 0), (204, 0)],
        "evt-timeout-then-204": [(204, 20), (204, 0)],
        "evt-always-400": [(400, 0)],
    }
    MAX_BODY_BYTES = 1_048_576
    attempts = defaultdict(int)
    lock = threading.Lock()
    
    class Receiver(BaseHTTPRequestHandler):
        def do_POST(self):
            try:
                content_length = int(self.headers["Content-Length"])
            except (KeyError, TypeError, ValueError):
                self.send_response(400)
                self.end_headers()
                return
            if content_length &lt; 0 or content_length &gt; MAX_BODY_BYTES:
                self.send_response(413)
                self.end_headers()
                return
            body = self.rfile.read(content_length)
            event_id = self.headers.get("X-Webhook-Event-Id", "missing-event-id")
            with lock:
                index = attempts[event_id]
                attempts[event_id] += 1
            plan = PLANS.get(event_id, [(204, 0)])
            status, delay = plan[min(index, len(plan) - 1)]
            print(json.dumps({
                "eventId": event_id,
                "deliveryId": self.headers.get("X-Webhook-Delivery-Id"),
                "attempt": index + 1,
                "payloadSha256": hashlib.sha256(body).hexdigest(),
                "reply": status,
            }), flush=True)
            time.sleep(delay)
            self.send_response(status)
            self.send_header("Content-Length", "0")
            self.end_headers()
    
        def log_message(self, _format, *_args):
            pass
    
    ThreadingHTTPServer(("127.0.0.1", 8080), Receiver).serve_forever()
    
启动 `python3 webhook_receiver.py` 后，分别发送 `evt-500-then-204`、`evt-timeout-then-204` 和 `evt-always-400`。第二个计划中的 `20` 秒必须大于被测发送端的超时阈值；若前面还有反向代理，它的超时必须更长，否则测到的是代理返回的 `504`。脚本只接收带 `Content-Length` 的测试请求；生产接收端应由框架或网关对分块传输同样实施大小限制。脚本有意只输出脱敏审计，投递次数、事件标识和摘要就是发送端重试测试的证据。
用同一事件依次配置下面三组响应：

接收器行为| 发送端应观察到的结果  
---|---  
第一次 500，第二次 204| 两次投递，`eventId` 不变、`deliveryId` 和签名时间戳更新；达到 204 后停止重试  
第一次超时，第二次 204| 可能出现接收端已收到但发送端未知的重复请求；接收端仍只处理一次  
一直返回 400| 是否重试由平台契约决定；无论是否重试，发送端要留下终态和失败原因  

每次投递应保存请求摘要、`deliveryId`、尝试次数、开始时间、响应码和错误分类。DNS、TLS、连接超时、5xx 与 4xx 的可重试性不能只按一个“失败”字段混在一起。需要人工回放时，使用原 `eventId`、新的 `deliveryId`、新的 Timestamp 和新签名，记录 `replayBy`；不能重新生成一个业务事件来掩盖第一次投递失败。
`Retry-After`、最大尝试次数和退避间隔都属于平台行为。测试不要假定所有提供方都是指数退避或只重试 5xx，而是用受控接收器测出当前契约的真实表现，并在回归中固定下来。
### 乱序事件靠版本号判断，不靠到达时间
支付事件可能按下面的业务顺序产生：
    
    payment.created    version=1
    payment.succeeded  version=2
    payment.refunded   version=3
    
网络重试后，`payment.refunded` 可能先到，`payment.succeeded` 后到。接收端不能用 HTTP 到达时间判断谁更新谁，应以供应方定义的 `version` 或等价序列为准。测试前先准备 `payment_state` 的 version=1 基线，再投递 version=3，随后投递 version=2；预期订单最终仍为 `REFUNDED`，第二条记录标记为 `IGNORED_STALE` 或项目定义的等价状态。
这个案例把每条事件当成当前支付状态的完整快照，所以 version=3 可以直接落为 `REFUNDED`。若平台发送的是增量事件，不能简单跳过 version=2：要么缓冲缺失序列，要么查询供应方的权威状态后再收敛，测试也要覆盖这条补偿路径。
条件更新是一个简单的实现边界：
    
    UPDATE payment_state
    SET status = :status,
        last_event_version = :version
    WHERE payment_id = :paymentId
      AND last_event_version < :version;
    
受影响行数为 0 时，不能一律当成功：可能是同版本重复、旧版本乱序，也可能是该支付记录不存在。测试报告要同时保留 `eventId`、版本、处理结果和订单最终状态，才能判断旧事件是否真的没有覆盖新状态。
版本号只解决到达顺序，不能代替状态机。再补一条 version=4 但把 `REFUNDED` 改回 `SUCCEEDED` 的事件：除非供应方契约明确允许更正，接收端应拒绝或告警，而不是因为版本更大就直接更新。
如果平台没有事件版本或可比较的状态序列，接收端无法可靠推断全局先后。此时要在需求层确定状态机和冲突策略，不能拿 `occurredAt` 或本地接收时间硬凑顺序。
### 回调地址配置也要做安全测试
这一部分测试的是发送端。创建 Webhook 订阅时，回调地址若可被任意配置，系统可能被用来访问内部服务或把事件发送到错误主机。测试环境使用受控域名，至少覆盖：
  * 非 HTTPS 地址、URL 中携带用户名密码、非法端口和过长 URL；
  * 指向回环、私有网段或测试保留地址的主机；
  * 首次校验合法、重定向后指向受限地址的 URL；
  * DNS 解析结果变化后的再次投递；
  * IPv6、IPv4-mapped 地址以及同一域名返回多个 A/AAAA 记录；
  * 回调地址被禁用或删除后，待重试任务是否还能继续投递。


创建订阅时的地址校验不够，实际投递前仍要重新解析并校验目标；否则 DNS 变化后，最初合法的域名仍可能指向受限地址。校验完成后还要确保 HTTP 客户端连接的是已校验的地址，不能校验一次 DNS、再让客户端按主机名重新解析。项目可以选择不跟随重定向；若允许跳转，每一跳都要重新执行目标地址校验并限制跳转次数。还要检查回调地址、请求 Header 和响应体是否被完整写入普通日志，尤其不要泄露签名、授权头或带签名的下载 URL。
### 回归时保留这些用例

场景| 关键断言  
---|---  
合法回调| 原始报文签名通过，Inbox、任务和订单状态可关联  
签名篡改| 签名、时间窗口或 Body 不匹配时无 Inbox、无副作用  
输入边界| 重复安全 Header、超大或分块超限 Body 被拒绝，不耗尽接收端资源  
业务一致性| 签名有效但订单归属、金额或币种不匹配时不改变订单，进入对账或告警  
正常重试| 相同 `eventId` 多次到达，业务副作用只有一次  
摘要冲突| 相同 `eventId` 不同 Body 被告警且不覆盖原事件  
发送端 500 重试| 事件身份稳定，成功后停止投递  
发送端超时| 接收端已处理但发送端重发时仍幂等  
并发重复投递| 多个投递并发到达，Inbox、任务和副作用仍各只有一次  
Inbox 后投递中断| 外部已确认后，`PENDING` 事件仍能被补捞并只处理一次  
任务领取后崩溃| `PROCESSING` 租约到期后可恢复，不遗留永久处理中事件  
Inbox 后处理失败| 外部已确认，内部重试和死信可追踪  
乱序事件| 旧版本不能覆盖新版本状态  
增量事件缺序| 缺失序列时缓冲或查询权威状态，不把局部事件当完整快照  
回放| 使用原事件、新投递身份，不生成第二个业务事件  
回调地址配置| 协议、目标地址、重定向和禁用订阅均受控  

这组用例覆盖的是 Webhook 最容易失控的部分。新增事件类型时，优先补状态机、版本规则和副作用断言，而不是只增加一条“收到回调返回 200”。
### 总结
Webhook 测试最终要回答四个问题：这是谁发来的，它对应哪个业务事件，重复或乱序时业务状态会不会倒退，发送失败后能不能查清和恢复。把原始报文摘要、`eventId`、`deliveryId`、事件版本、Inbox 状态和业务结果串在一起，回调问题才有可追溯的证据。
先用受控接收器把 500、超时和重复投递跑透，再扩展到真实平台的签名和重试策略。这样写出来的回归用例能覆盖链路风险，也不会被某个供应商的临时行为绑死。
