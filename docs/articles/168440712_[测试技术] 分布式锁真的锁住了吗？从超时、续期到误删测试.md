# [测试技术] 分布式锁真的锁住了吗？从超时、续期到误删测试

> 原文: https://blog.csdn.net/weixin_42390585/article/details/168440712

> 原创内容，未获授权禁止转载、转发、抄袭。

准备两个相同的定时任务，给锁设置 5 秒过期时间。任务 A 拿到锁后执行了 8 秒，任务 B 在第 6 秒开始，发现 Redis 中已经没有这个 Key，于是也拿到了锁。两次任务的日志看起来都很正常，但它们实际上同时进入了临界区。
这是一个可以在测试环境稳定复现的简化场景。它说明，看到 Redis 里存在一个锁 Key，只能证明某个时刻有人写入过锁，不能证明业务执行期间始终只有一个持有者。分布式锁的测试，要把加锁、持有、续期、释放和业务副作用放在同一条证据链上观察。
### 先把锁的契约写清楚
我会先确认这把锁保护的资源是什么，以及业务真正需要的约束是什么。以“同一订单只能有一个任务处理”为例，至少要明确下面几件事：

约束| 测试时要看到的结果  
---|---  
同一个订单不能并行处理| 同一时间最多一个有效持有者进入临界区  
锁不能永久占用| 持有进程异常退出后，锁能在约定时间内失效  
旧持有者不能释放新锁| 锁过期并被别人重新获取后，旧请求的清理动作不能删除新锁  
获取失败不能继续执行业务| `tryLock` 返回失败后，不写库、不发消息、不调用下游  
长任务不能悄悄超过租约| 要么续期成功，要么在租约到期前停止或转为失败  

如果这些约束没有写进接口或技术方案，测试很容易退化成“执行两次加锁命令，再看第二次是不是失败”。这种验证只能覆盖最短的一段时间，覆盖不了锁失效后的行为。
### 最小加锁实现要满足什么
Redis 中常见的加锁命令是把“只在 Key 不存在时写入”和“设置过期时间”放在一次操作里：
    
    SET lock:order:1001 8f8b3d5d-<request-id> NX PX 5000
    
`NX` 保证 Key 已存在时不会覆盖，`PX 5000` 为锁设置租约，随机值则用来识别本次请求是不是锁的持有者。`SETNX` 和 `EXPIRE` 分成两条命令会留下一个窗口：第一条成功后进程崩溃，第二条没有执行，锁就可能永久存在。
释放锁也不能直接执行 `DEL lock:order:1001`。正确做法是先比较 Value，确认还是当前请求的令牌，再删除，而且比较和删除必须是一个原子操作：
    
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    end
    return 0
    
这里的 `KEYS[1]` 是锁 Key，`ARGV[1]` 是当前请求生成的令牌。测试时要检查删除结果，不要只看接口是否返回成功：持有者释放应返回 `1`，令牌不匹配或锁已经不存在时应返回 `0`。
### 场景一：业务执行时间超过锁的 TTL
这是最值得先测的一组用例，因为它不依赖网络抖动，也不需要复杂的故障注入。准备两个 Worker，锁的 TTL 设置为 3 秒，让 Worker A 拿锁后暂停 5 秒，再启动 Worker B。
可以按下面的顺序执行：
  1. Worker A 获取 `lock:order:1001`，记录 `critical_start=A`。
  2. 确认 A 仍在业务处理中，但 Redis 的 `PTTL` 已经变成负数，说明锁已过期。
  3. Worker B 获取同一个 Key，记录 `critical_start=B`。
  4. 等 A、B 都结束，检查两段临界区的开始和结束时间是否重叠。


日志至少保留这些字段：
    
    requestId=REQ-A lockResult=acquired pttl=3000 criticalStart=10:00:00.120
    requestId=REQ-B lockResult=acquired pttl=3000 criticalStart=10:00:03.180
    requestId=REQ-A criticalEnd=10:00:05.130
    requestId=REQ-B criticalEnd=10:00:04.200
    
如果业务要求同一订单不能并行处理，这组结果就是缺陷：A 还没有结束，B 已经进入了临界区。Redis 的互斥只在租约有效期内成立，不能替业务自动延长执行时间。
修复方向要根据业务选择：
  * 业务本来就应该在 3 秒内完成，就把超时当作失败处理，不允许继续写入结果；
  * 任务可能运行很久，就使用可靠的续期机制，并测试续期失败后的行为；
  * 任务可以拆分，就缩短锁保护的范围，把耗时操作移出临界区；
  * 不能接受重复执行时，再增加业务幂等键或状态条件更新，不能只依赖锁兜底。


这里有一个容易被忽略的断言：即使第二个 Worker 最终返回“未获取锁”，也要检查它有没有发消息、写数据库或修改任务状态。返回码正确、业务副作用错误，仍然是失败。
### 场景二：续期成功，不等于续期可靠
对于超过固定租约的任务，客户端通常会在持有锁期间定期刷新过期时间。测试时不能只让任务正常跑完，还要观察续期是否真的发生，以及续期线程失效后系统会怎样。
正常续期可以这样验证：任务执行时间设置为租约的 2 到 3 倍，每隔一小段时间记录一次 `PTTL`。只要持有者仍然存活，TTL 就不应持续降到 0；任务结束后，锁必须被释放，而不是靠很久以后自然过期。
    
    time=10:00:00.000 owner=REQ-A pttl=30000 renew=ok
    time=10:00:10.000 owner=REQ-A pttl=29980 renew=ok
    time=10:00:20.000 owner=REQ-A pttl=29970 renew=ok
    time=10:00:26.400 owner=REQ-A action=business_done release=1
    
随后再做两次异常测试：
  * 让续期线程停止，但业务线程继续运行，确认锁会在租约到期后消失，且系统有明确日志或指标；
  * 临时阻断持有者到 Redis 的连接，确认续期失败后不会无限假设自己仍拥有锁。


续期机制只能延长锁的有效时间，不能消除进程暂停、网络隔离和 Redis 故障带来的不确定性。对于使用 Redisson 的服务，还要区分两种调用方式：不显式指定租约时间时，客户端可以使用 Watchdog 续期；显式传入 `leaseTime` 时，通常按固定租约处理，不能再假定会自动续期，具体行为应以当前客户端配置和文档为准。
测试续期时建议把业务状态和锁状态分开记录：

观察项| 通过条件  
---|---  
续期次数| 任务运行期间持续增加，失败时有明确记录  
`PTTL`| 持有者存活时不会无故归零  
任务状态| 续期失败后进入可重试或失败状态，不继续伪装成功  
竞争请求| 锁仍有效时不能进入临界区  
进程退出| 不再续期，锁最终能够释放  

不要把“Redis Key 一直存在”直接当成续期成功。旧线程可能只是在刷新一个已经不再属于自己的 Key，必须同时校验令牌或客户端提供的持有者信息。
如果旧请求在失去锁后仍可能继续运行，单靠 TTL 还不够。可以在每次成功获取锁时分配一个递增的 fencing token，并让数据库更新、消息消费者或下游服务拒绝旧 token：
    
    A 获取锁，token=41，然后发生长时间暂停
    A 的锁过期，B 获取锁，token=42，并完成状态更新
    A 恢复后带 token=41 写入，数据库按条件拒绝这次旧写入
    
这组用例的关键不是检查 A 最后有没有收到异常，而是检查 A 的旧数据有没有覆盖 B 已经写入的新状态。测试时可以让 A 在拿到 token 后暂停，等待 B 完成更新，再恢复 A 执行写操作，最终数据必须保留 B 的结果。fencing token 需要在获取锁和分配序号之间保持正确的原子关系，不能简单地在客户端本地生成一个时间戳代替。
### 场景三：旧请求误删了新请求的锁
这个问题通常要等到锁超时后才会出现，手动点几次接口很难遇到。用两个不同的令牌可以把过程固定下来：
    
    1. A 使用 token-A 获取锁，租约为 3 秒。
    2. 等待锁自然过期。
    3. B 使用 token-B 获取同一个锁，租约为 10 秒。
    4. A 的 finally 逻辑执行释放锁。
    5. 检查 token-B 对应的锁是否仍然存在。
    
如果释放逻辑是无条件 `DEL`，A 会把 B 的锁删掉。此时第三个请求 C 可以拿到锁，B 和 C 就会同时执行。这个缺陷的危险之处在于，A 的释放动作看起来是正常清理，日志甚至可能打印“unlock success”，但它清理的是别人的资源。
正确的结果应该是 A 的释放脚本返回 `0`，B 的令牌仍保留在 Key 中，C 在 B 的租约有效期内获取失败。测试可以直接断言：
    
    release(owner=token-A) result=0
    lock value after release=token-B
    acquire(owner=token-C) result=false
    
这组测试要覆盖正常返回、业务异常和进程恢复三条释放路径。尤其是 `finally` 中的清理代码，不能为了“确保解锁”而无条件删除 Key。使用带令牌校验的脚本后，也要检查脚本执行失败是否被记录，否则真正的锁残留会变成下一次任务的无声超时。
### 还有几个容易漏掉的锁测试
加锁和解锁之外，我通常会补下面几组，避免只验证理想路径：
  * 两个请求使用不同订单 Key 时可以并行，不能把锁粒度写成全局 Key，导致无关业务互相阻塞；
  * `tryLock` 超时返回失败后，业务方法不能继续执行；
  * 持有者在临界区抛异常时，锁按约定释放或等待租约过期，不能出现永久占用；
  * 非持有者执行释放操作时，Key 和 TTL 都不能被改变；
  * 如果客户端支持可重入锁，同一线程获取两次后，第一次释放不能让其他线程立即进入，第二次释放才结束持有状态；
  * 租户、业务类型和资源 ID 组成的锁 Key 必须隔离，不能因为两个模块都使用 `lock:1001` 互相影响。


每条用例都要检查业务结果。例如锁获取失败时，不仅检查接口返回“处理中”，还要检查订单状态、库存流水、发送消息和下游调用记录是否没有新增。锁是并发控制手段，最终要保护的是这些业务副作用。
### 用一条证据链判断是否真的有效
分布式锁问题很容易被“偶尔成功”掩盖。测试日志至少应能关联请求、锁和业务动作：
    
    traceId=TRACE-001 requestId=REQ-A resource=order:1001
    lockKey=lock:order:1001 ownerHash=7c1... acquire=success pttl=5000
    criticalStart=10:00:00.120 criticalEnd=10:00:04.880
    renewCount=3 release=success businessWrite=1
    
生产环境不建议记录完整令牌，可以记录不可逆的摘要。测试环境还可以增加一个“当前临界区持有者”指标，在同一资源出现两个活跃持有者时立即告警。Redis 的 `GET`、`PTTL` 只能说明 Key 的状态，必须和任务日志、数据库记录、消息发送记录一起看，才能判断锁是否真的阻止了重复业务。
### 最小回归集

场景| 核心断言  
---|---  
同一资源并发获取| 只有一个请求进入临界区  
不同资源并发获取| 互不阻塞，分别拿到各自的锁  
固定租约内完成| 任务完成并正确释放，Key 不残留  
业务超过 TTL| 按契约失败、续期或阻止并行，不能无声重叠  
续期正常| 任务运行期间锁不会提前过期  
续期失败| 锁最终失效，任务和告警状态清楚  
旧持有者晚释放| 不能删除新持有者的锁  
非持有者释放| Key、令牌和 TTL 保持不变  
获取锁超时| 不执行写库、发消息等业务动作  
临界区抛异常| 按约定释放或过期，后续请求可以恢复  

### 总结
分布式锁的测试要围绕生命周期展开：谁拿到锁、锁能撑多久、业务跑慢时会不会失效、续期失败后怎么收场，以及旧请求释放时会不会误伤新请求。
一套可靠的验证至少要同时检查 `SET NX PX` 的原子加锁、令牌匹配释放、TTL 变化、续期结果和业务副作用。只断言“Redis 里有 Key”或“第二次请求返回失败”，都无法证明同一资源在整个业务过程中真的只有一个有效执行者。
