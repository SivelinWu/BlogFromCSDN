# [测试技术] App升级测试：旧数据迁移与登录态保留

> 原文: https://blog.csdn.net/weixin_42390585/article/details/165715471

> 原创内容，未获授权禁止转载、转发、抄袭。

用户更新App时，通常希望打开新版就能接着用：没写完的草稿还在，个人设置不用重做，仍然有效的登录也能继续使用。App升级测试要验证的，就是这次版本切换有没有打断原有的使用过程。
新版本可能调整数据库字段、附件保存位置，或更换登录凭据的存储方式。安装包覆盖成功以后，旧草稿仍可能打不开，金额可能被错误转换，原本保存的凭据也可能读不出来。这些问题需要带着旧版留下的数据进入新版，才有机会发现。直接安装一个全新的App，再跑通登录和提交，很容易漏掉这部分风险。
下面用一个支持离线草稿的报销App举例：在旧版保存一张尚未同步的草稿，升级后继续编辑和提交，沿着这个过程检查旧数据是否迁移正确、账号是否还能正常使用。Android部分给出操作命令，iOS部分补充安装和凭据访问的差异。
### 给旧版留下一点真实使用痕迹
先安装需要支持升级的旧版，在旧版里登录测试账号A，准备好已同步记录，再断网创建下面的本地草稿。确认服务端尚无这些草稿，避免新版从服务器重新拉回数据，掩盖本地迁移失败。不要直接在新版数据库里插记录来代替，它们没有经过旧版的写入逻辑。

旧版中准备的状态| 升级后检查什么  
---|---  
草稿D-001：128.30元、一张附件、未同步| 金额、附件、草稿ID和账号归属保持正确，能继续编辑  
草稿D-002：金额未填、备注为空| 空值仍表示未填写，不被迁移成已填写的0元  
一条已同步的报销单| 本地记录与服务端对应，不因重试多出一份  
已修改的语言和通知偏好| App内设置按约定保留；系统通知授权另行核对  

把草稿ID、关键字段和附件内容记下来，保留几张升级前截图。有测试诊断页或数据库检查工具时，也记录本地记录数和数据库结构版本。附件至少核对能否打开、内容是否相同，有条件再比较文件哈希。
在旧版确认保存完成后，结束进程再启动，检查草稿是否落盘。否则，升级后找不到数据，可能是旧版根本没保存成功。再补一份接近真实用户数据量的旧库，记录从启动到草稿可编辑的耗时，与同设备后续冷启动及项目耗时要求对照，留意卡死和无响应。
### 覆盖安装，别顺手把旧数据清了
常规升级要保留旧版的应用数据。卸载重装、清除应用数据后再安装，都走了不同的路径，不能拿来代替覆盖升级。
Android测试前，核对新旧包的包名一致、签名满足系统更新要求；常规升版使用更高的`versionCode`。尤其要分清商店分发签名和本地调试签名；安装报签名冲突时，应先解决包的来源问题，不要卸载旧版来绕过。
下面是单APK覆盖安装的命令示例，设备序列号、包名和路径需要替换。命令未连接具体测试App执行：
    
    adb -s DEVICE_SERIAL install -r ./app-new.apk
    adb -s DEVICE_SERIAL shell dumpsys package com.example.expenses
    
`-r`表示重新安装并保留数据。安装成功后，在包信息中核对`versionCode`和`versionName`。Android离线迁移这轮可用预先下载的测试包，让设备保持断网；如果产品通过应用市场或拆分APK分发，再用对应测试渠道单独走一次升级，并记录期间是否发生数据同步。
iOS也要通过被测产品支持的分发渠道，用同一App的后续构建覆盖旧版。安装前后核对Bundle ID和构建号；删除App后重新安装不属于这一组升级用例。
### 数据还在，也可能已经变了意思
假设新版将金额从“元字符串”改为“分整数”，并给历史人民币草稿补上币种。下面这些预期要先和开发确认，不能只看迁移后还有几条记录：

旧值| 本例迁移后的预期  
---|---  
`"128.30"`| 金额为`12830`分，币种为`CNY`  
`"0.01"`| 金额为`1`分，不能截断成0  
未填写| 仍为未填写，编辑页继续执行必填校验  

这里的币种默认值有前提：旧数据确实只包含人民币。如果历史上存在多币种记录，就要按原币种迁移，不能统一补成`CNY`。
升级后的第一次启动，可以先断网打开D-001，确认本地金额和附件能读到；本例要求旧新版都支持离线草稿。保持断网，把金额改为138.30元并保存，结束进程再启动，确认修改仍在。随后恢复网络、提交一次，核对服务端只生成一条对应的报销单，金额为138.30元，附件和账号也都正确。
如果附件记录还在，文件却打不开，就继续核对本地路径、文件是否存在，以及访问授权是否仍有效。列表里显示一张缩略图，不能证明原始附件可以读取或上传。
如果项目使用Room，`MigrationTestHelper`可以帮助验证迁移后的数据库结构，金额、空值和业务字段是否正确仍需要额外断言。让开发把这几组旧数据加入迁移测试，比单纯验证表能创建更有用。
还要留意“迁移失败后删库重建”的处理。Room的`fallbackToDestructiveMigration`在缺少迁移路径时可能删除原有数据。对于尚未上传、无法从服务端恢复的草稿，清空后正常进入首页应判为数据丢失，不能当成升级成功。
### 头像还在，登录态未必有效
登录态通常同时涉及本地凭据和服务端会话。升级后显示账号A的头像，只能说明页面还认得A；真正的验证是调用需要登录的接口，确认服务端识别的仍是A，并能完成一次受保护操作。
本例约定常规升级不主动注销有效会话。每种状态都从独立的旧版数据开始准备，并在升级后的首次请求时重新核对有效性：安装过程不会暂停Token的过期计时。

登录状态| 升级后的预期  
---|---  
访问凭据及服务端授权仍有效| 首次联网可以继续使用，服务端账号与旧版一致  
Access Token过期，Refresh Token有效| 按既有机制刷新后继续操作，无需重新输入密码  
Access Token已失效，Refresh Token过期或已撤销| 刷新被拒绝后引导重新认证，不能靠旧缓存继续通过服务端鉴权  
旧版已经退出登录| 保持退出，不从历史存储中恢复成已登录  

再让刷新请求超时一次：网络失败不等于凭据失效，不应仅因超时就清空凭据或未提交草稿。恢复网络后，按实际会话状态重试或引导重新认证。
Token过期最好通过测试环境的短有效期或服务端会话控制来准备。修改手机时间会同时影响证书、缓存和业务时间判断，容易把几类问题混在一起。如果产品有升级后强制重新认证的安全策略，就按该策略验收，不把登录页本身判成缺陷。
重新认证还要顺手检查账号隔离：A的会话失效后改用B登录，B不应看见或提交A的本地草稿。A的草稿是保留待本人恢复，还是按退出策略清理，需要事先约定；不应直接改挂到当前登录账号下。
遇到升级后全部掉登录，可以让开发对照凭据读取位置、加密方式和密钥访问结果。iOS的Keychain访问受`keychain-access-groups`等签名权限约束；访问组变化、所用保护等级要求设备解锁，都可能导致暂时或持续读不到旧项。应结合错误信息，在设备解锁后复查，不能直接判定凭据被删除。Android若更换凭据存储位置或加密方案，也要验证旧数据的读取与迁移。排查只记录错误类型和脱敏账号，不导出完整Token。
### 中断要发生在迁移过程中
先确认迁移何时触发。有些在首次启动时执行，有些要进入草稿页、打开本地数据库时才开始。在测试构建中记录迁移开始和结束，并设置暂停点：旧数据读完后、数据库事务提交前，以及数据库迁移完成但其他存储尚未更新时，分别中断应用。
Android可在目标阶段执行下面的命令，然后手动重新启动App：
    
    adb -s DEVICE_SERIAL shell am force-stop com.example.expenses
    
需要通过日志或测试钩子确认命中了哪个阶段。`force-stop`可用于验证应用被强制停止后的恢复，不能代表安装过程断电、磁盘写入故障等所有中断情形。
重启后核对草稿没有丢失或重复、金额没有再次乘100，迁移标记与实际数据一致。如果数据库已经升级，而偏好设置、附件文件还没迁完，应能继续恢复；数据库事务不会自动覆盖这些改动。恢复成功后再做一次冷启动，确认不会重新转换金额或再次搬运附件。
剩余空间不足要分两处看：安装被拒绝时，核对实际版本及旧数据是否保留；新包已装好但迁移失败时，核对错误提示和原数据是否可恢复。保留现场后腾出空间重试，确认迁移能完成且不重复转换，不用清除应用数据来恢复。
### 跨版本路径，要从各自的旧数据出发
用简化版本号举例：当前版本是3.0，仍需支持2.6和2.8升级，至少分别验证`2.8 → 3.0`、`2.6 → 3.0`，以及有历史使用痕迹的`2.6 → 2.8 → 3.0`。App版本号和数据库结构版本不是一回事，应记录两者的对应关系。
直接跨版本升级不要求用户手动安装中间版本，新包必须包含所需的迁移路径。每条路径都要重新准备旧版数据，或恢复对应的测试机快照；拿已经被3.0迁移过的库，只改版本标记再测，不能代表真实升级。恢复快照也不会回退服务端会话，测试前应重新核对凭据是否已过期、轮换或撤销。
新安装的3.0可以用来对照最终数据库结构和新建数据的默认值；升级用户已保存的语言、通知偏好等仍按保留策略验收，不应被强行重置成新安装状态。回退安装则需要单独的兼容方案，旧程序未必认识新库结构，不能把“覆盖装回旧包”当成默认恢复办法。
还要把备份恢复单独记一条路径。Android在满足备份恢复条件时，重新安装可能自动带回旧数据，所以卸载后再装也未必是干净环境。记录是否发生了恢复，才能区分升级迁移问题与备份恢复问题。
### 总结
一条有价值的升级用例，应从旧版真实写入的数据开始，到新版继续使用这些数据结束。草稿能读取、修改、提交，登录凭据能按服务端策略继续使用或重新认证，中断后还能恢复，这些结果比“安装成功、能进首页”更能说明问题。
提交测试结果时，把旧新包版本、系统版本、迁移路径、升级前后的数据对照和登录验证结果放在一起。发现问题后保留那份旧数据，它往往就是复现缺陷最有用的材料。
