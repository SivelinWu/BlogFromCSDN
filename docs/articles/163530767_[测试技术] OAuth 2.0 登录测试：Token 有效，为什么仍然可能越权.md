# [测试技术] OAuth 2.0 登录测试：Token 有效，为什么仍然可能越权

> 原文: https://blog.csdn.net/weixin_42390585/article/details/163530767

> 原创内容，未获授权禁止转载、转发、抄袭。

很多系统把第三方登录统称为“OAuth 登录”，严格来说并不准确。OAuth 2.0 解决的是授权：客户端拿到 Access Token 后，可以在限定范围内访问资源。登录还需要确认用户身份，实际项目通常在 OAuth 2.0 之上使用 OpenID Connect（OIDC），由 ID Token 告诉客户端“当前用户是谁”。
一次网页登录会跨过浏览器、业务系统、身份提供方和资源 API。页面最终跳回首页，只能说明这条跳转链路走完了；授权码有没有被替换、回调是否属于当前浏览器会话、Token 是否发给正确客户端和 API、退出后凭证还能用多久，都藏在重定向和后端换票过程中。本文使用授权码模式加 PKCE，围绕一个订单后台拆解这条链路。示例参数均为脱敏测试数据，只用于说明测试方法。
### 先把四个参与方分开
订单后台采用下面的结构：
    
    浏览器 -> 订单后台（OIDC Client） -> 身份提供方（Authorization Server / OP）
                                  -> 订单 API（Resource Server）
    
开始抓包前，先从身份提供方的 Discovery 文档确认 `issuer、authorization_endpoint、token_endpoint、jwks_uri、revocation_endpoint、end_session_endpoint`，并检查 `code_challenge_methods_supported` 是否包含 `S256`。测试环境迁移后常见的配置问题，是页面跳到了新身份提供方，后台却仍使用旧的 Token Endpoint 或 JWKS；这时登录失败看似随机，实际是 Issuer 和端点没有成组切换。
    
    curl -sS 'https://idp.example.test/.well-known/openid-configuration' |
      jq '{issuer, authorization_endpoint, token_endpoint, jwks_uri,
           revocation_endpoint, end_session_endpoint,
           code_challenge_methods_supported}'
    
用户点击登录后，订单后台生成一次性的 `state`、`nonce` 和 `code_verifier`，保存到当前登录事务，再将浏览器跳转到授权端点。下面为了阅读进行了换行，实际 URL 应连续编码：
    
    GET /authorize?
      response_type=code&
      client_id=order-console&
      redirect_uri=https%3A%2F%2Forders.example.test%2Fcallback&
      scope=openid%20profile%20order.read&
      state=STATE-7f3a&
      nonce=NONCE-b921&
      code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&
      code_challenge_method=S256
    
回调只带授权码和原来的 `state`：
    
    GET /callback?code=CODE-a83d&state=STATE-7f3a
    
订单后台随后从服务端调用 Token Endpoint，并提交对应的 `code_verifier`：
    
    POST /token HTTP/1.1
    Content-Type: application/x-www-form-urlencoded
    
    grant_type=authorization_code&code=CODE-a83d&redirect_uri=https%3A%2F%2Forders.example.test%2Fcallback&client_id=order-console&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
    
机密客户端还要按注册方式完成客户端认证，凭证只能留在服务端，不能出现在浏览器脚本、URL 或日志中。换票成功后通常会得到 ID Token、Access Token，以及按服务端策略签发的 Refresh Token。ID Token 用来建立登录会话，Access Token 用来访问订单 API，两者用途不同，不能互换。
上面的 verifier 和 challenge 取自 RFC 7636 附录 B，二者是可校验的一组值；项目测试时应为每次登录重新生成，verifier 长度必须在 43 到 128 个字符之间。怀疑客户端计算错误时，可以在本地复算，输出应与授权请求中的 challenge 完全一致：
    
    printf %s 'dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk' |
      openssl dgst -sha256 -binary | openssl base64 -A |
      tr '+/' '-_' | tr -d '='
    # E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    
#### 动手前准备一组可串用的数据
不要只准备一个账号和一个客户端，否则很多越权场景只能靠修改 JWT Payload 模拟，签名随即失效，测到的只是“签名错误”。我通常在测试身份提供方或独立测试租户中准备下面这组数据：

对象| 测试数据| 用途  
---|---|---  
OIDC Client A| `order-console`| 被测订单后台  
OIDC Client B| `report-console`| 生成合法但 Audience 不同的 ID Token  
Resource A| `order-api`| 订单查询、取消接口  
Resource B| `profile-api`| 生成合法但 Audience 不同的 Access Token  
普通用户| 只有 `order.read`| 验证 Scope 与接口权限  
管理用户| 拥有 `order.read order.write`| 跑通取消订单基线  

抓包时保留浏览器重定向、客户端换票请求和 API 响应，服务端日志至少能按 `loginTransactionId` 串起 `client_id、redirect_uri、state、nonce、code` 的处理结果。Token 使用带服务端密钥的指纹或 SHA-256 摘要前 16 个十六进制字符关联日志，不记录原文；测试报告则保留操作、HTTP 状态、OAuth 错误码、业务数据变化和审计事件。
### 回调地址先做“差一个字符”的测试
`redirect_uri` 是最值得先测的参数。攻击者一旦能把授权码引到自己的地址，后面的 Token 校验做得再完整也可能来不及。注册地址假设为：
    
    https://orders.example.test/callback
    
我会依次尝试：
    
    https://orders.example.test/callback/
    https://orders.example.test/callback?next=https://evil.example
    https://orders.example.test.evil.example/callback
    https://orders.example.test/%2e%2e/callback
    http://orders.example.test/callback
    
这些地址都不该因为前缀匹配、通配符或二次跳转被接受。OAuth 2.0 安全最佳实践要求对预注册回调地址进行精确字符串匹配，原生应用的 Loopback Redirect URI 端口是明确例外。业务回调页本身也不能成为 Open Redirector，例如直接执行未经校验的 `next` 参数。
还要把错误链路走完：用户拒绝授权时，身份提供方可能带着 `error=access_denied` 返回已注册回调地址；未注册或非法的回调地址则不能被用于错误重定向，否则错误信息也可能被送到攻击者控制的页面。
如果同一个客户端接入多个身份提供方，还要交换两条登录事务的授权响应：从 IdP A 发起登录，却把 IdP B 返回的 `code` 送入 A 对应的回调事务。授权服务器支持授权响应 `iss` 参数时，客户端应将它与发起登录时保存的 Issuer 比较，并只向该 Issuer 的 Token Endpoint 换票；不支持时，可以为不同 Issuer 使用不同回调地址。只在 ID Token 落地后才检查 `iss`，可能已经把授权码发错端点。
### 在回调处交换三样东西
正常请求中的 `state`、`nonce` 和 PKCE 经常被写成“都有随机数”，测试时却承担不同任务。
`state` 绑定浏览器发起的登录事务与回调。把 A 浏览器生成的授权码和 B 浏览器保存的 `state` 拼在一起，订单后台应拒绝回调，且不能创建本地会话。`state` 使用后应立即失效，刷新回调页或再次提交同一组参数也不能重复登录。返回地址等业务数据适合保存在服务端登录事务中，`state` 只放不可预测的关联值，不携带手机号、用户标识或内部页面参数。
`nonce` 进入 OIDC 请求，并应出现在 ID Token 中。客户端需要将它与本次登录事务保存的值比较，用来发现 ID Token 重放或串用。缺失、错误以及来自另一条登录事务的 `nonce` 都应失败。
PKCE 保护授权码交换。客户端为每次登录生成独立的 `code_verifier`，授权请求只发送其 `S256` 派生值，Token Endpoint 再校验原始 verifier。先通过浏览器拿到一枚未兑换的授权码，再复制换票请求，依次替换为正确 verifier、错误 verifier、删除 verifier、另一条登录事务的 verifier。每次都要重新获取授权码，避免“授权码已使用”掩盖 PKCE 结果。只有正确 verifier 可以成功，客户端也不能在 `S256` 失败后自动降级为 `plain`。
授权码本身必须短时有效且只能使用一次。我会先在抓包工具中暂停换票请求，将同一份请求复制到两个终端，再用并发命令同时发送；只有一个请求可以成功。随后把 `client_id` 或 `redirect_uri` 替换成另一客户端的数据，服务端也应拒绝。RFC 6749 要求拒绝重复兑换，并建议在可行时撤销基于该授权码签发的 Token，因此还要从审计日志和后续调用中检查第一次拿到的 Token 是否继续有效。
    
    umask 077
    TOKEN_URL='https://idp.example.test/token'
    FORM='grant_type=authorization_code&code=CODE-a83d&redirect_uri=https%3A%2F%2Forders.example.test%2Fcallback&client_id=order-console&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk'
    OUT_DIR="$(mktemp -d)"
    
    for name in a b; do
      curl -sS "$TOKEN_URL" \
        -H 'Content-Type: application/x-www-form-urlencoded' \
        --data "$FORM" -o "$OUT_DIR/token-$name.json" -w "$name: %{http_code}\n" &
    done
    wait
    echo "响应暂存于：$OUT_DIR"
    
如果被测对象是机密客户端，还要按其注册方式补充客户端认证。报告中不要只写“一个成功、一个失败”，还要记录失败请求的 OAuth 错误码、两条请求的到达时间，以及首枚 Access Token 后续调用 API 的结果。临时目录含有 Token，分析结束后执行 `rm -rf "$OUT_DIR"`，不能提交到代码仓库。
### Token 签名正确，还可能发错对象
JWT 解码网站能展示 Payload，却不能代替验证。订单后台接收 ID Token 时，应校验签名算法和签名结果、`iss`、`aud`、`exp`，以及前面保存的 `nonce`；若系统设置了 ID Token 最大可接受年龄，再按该策略检查 `iat`，并单独考虑允许的时钟偏差。若 `aud` 包含多个接收方，还要检查 `azp`。
同一个身份提供方可能服务多个客户端，可以从测试身份提供方给 `report-console` 正常签发一枚 ID Token，再送到订单后台的 Token 校验边界；即使签名正确，只要它不是签给 `order-console`，就不能建立会话。正常授权码流程中，ID Token 由客户端后端从 Token Endpoint 获取，浏览器无法直接替换，因此该场景应放在组件测试、可控的测试 IdP 或专用校验接口中完成，不能伪装成一次普通页面回调。跨客户端、跨 API 的 Token 应优先通过测试租户合法签发，只有测试 `alg`、未知 `kid` 和错误签名时才使用专用测试密钥构造异常 Token，不能修改 JWT Payload 后沿用旧签名。
访问订单 API 时，Access Token 也要校验接收方和权限。Access Token 不一定是 JWT；采用 Audience 或 Resource 绑定的自包含 Token 可以在资源服务本地验证，不透明 Token 通常通过 Introspection Endpoint 查询 `active、aud、scope` 等状态。具体字段取决于项目使用的 Token Profile 和授权服务器，不能把所有 Access Token 都按 JWT 的 Claim 集合断言。下面两个串用场景很容易暴露问题：
  * 把用户信息 API 的 Access Token 交给订单 API，检查错误的 `aud` 是否被拒绝；
  * 使用只有 `order.read` 的 Token 调用取消订单接口，检查 Scope 或权限映射是否真正生效。


授权服务器实际签发的 Scope 可能少于客户端申请值，客户端应以返回结果为准。身份提供方支持细粒度授权时，可以让用户拒绝部分授权；不支持时，则通过测试策略、测试账号或授权服务器配置签发缩减后的 Scope。拿到只有 `order.read` 的 Token 后，页面不应展示取消入口，直接调用写接口也应失败。
    
    POST /orders/O900001/cancel HTTP/1.1
    Host: api.example.test
    Authorization: Bearer <order.read access token>
    Content-Type: application/json
    
    {"reason":"duplicate_order"}
    
预期是 HTTP 403，并在 `WWW-Authenticate` 中返回 `insufficient_scope` 或项目约定的等价错误；过期、撤销或签名错误的 Token 通常返回 401 和 `invalid_token`，两类失败不应混为一个业务错误码。订单仍为原状态，没有产生取消流水，库存没有回补，消息队列中也没有取消事件，审计日志则要区分“Token 无效”和“Token 有效但权限不足”。另一个值得保留的反例是 ID Token 与 Access Token 互换：API 不应因为它们都是 JWT 就接受错误类型的 Token。
签名验证还需要固定允许的算法，不能完全相信 Token Header 中的 `alg`。使用 `none`、非预期算法、未知 `kid` 和错误签名生成 Token，应全部被拒绝。密钥轮换则按真实顺序测试：先用旧 Key 让客户端建立 JWKS 缓存，再发布新旧两把公钥并用新 Key 签发 Token，确认客户端遇到新 `kid` 后能够刷新 JWKS；最后按约定移除旧 Key，验证旧 Token 在设计的过渡期内如何处理。没有明确过渡策略时，不能把旧 Key Token 一律判为无效。
本地账号映射也要看键值。OIDC 中稳定的身份是 `iss + sub`，邮箱可能修改，也可能在两个身份提供方中重复。准备两枚邮箱相同但 `iss` 或 `sub` 不同的合法 ID Token，订单后台不应把它们静默合并为同一个账号；账号绑定必须经过明确流程。
### 换票成功后检查本地 Session
多数 Web 系统不会把 ID Token 直接当页面会话，而是验证完成后创建自己的 Session Cookie。测试时先在浏览器开发者工具中记录登录前 Cookie，再完成回调，对比响应中的 `Set-Cookie`，确认系统重新生成会话标识。随后用登录前保存的 Cookie 单独请求受保护页面，它不能获得登录后的身份；只看新页面是否正常，发现不了 Session Fixation。
新 Cookie 至少要符合项目约定的 `Secure、HttpOnly、SameSite` 和有效期策略。`SameSite` 不是越严格越好：普通顶层 GET 回调与 `response_mode=form_post` 的跨站行为不同，配置错误会让回调找不到登录事务。应在真实浏览器中按项目使用的响应模式验证，不能只检查响应头字符串。
采用 BFF 模式时，Access Token 与 Refresh Token 留在服务端，浏览器只持有 Session Cookie；如果产品选择把 Token 交给前端，则需要单独评估存储位置和脚本读取风险，不能沿用服务端会话的断言。
### 并发刷新可能把正常用户踢下线
Access Token 过期后，客户端可以使用 Refresh Token 换取新凭证。安全最佳实践要求公共客户端的 Refresh Token 使用发送方约束或轮换机制。采用轮换时，每次刷新都会得到新的 Refresh Token，旧值随即退出使用。
确认单次刷新正常后，我会让两个请求同时拿同一个 Refresh Token 换票：
    
    refresh_token=RT-01
            |-- 请求 A -> AT-02 + RT-02
            |-- 请求 B -> 应失败，并触发约定的重放处置
    
执行时可以复用前面的并发脚本，将 `FORM` 改为 `grant_type=refresh_token&refresh_token=RT-01&client_id=order-console`。先用单次刷新确认轮换已开启，再重新登录获取一枚新的 Refresh Token 做并发，避免旧测试数据影响判断。
测试需要确认客户端最终保存哪一个新 Token，旧 `RT-01` 是否失效，新 Access Token 的 Scope 和 Resource 是否超出原授权。Refresh Token 必须绑定用户已经同意的权限与资源，刷新请求不能借机增加 `order.write`。轮换机制发现旧 Refresh Token 被再次使用后，授权服务器无法判断攻击者和合法客户端，应撤销当前仍有效的 Refresh Token，迫使客户端重新授权。前端如果把两次刷新结果按返回顺序直接覆盖，很可能先保存 `RT-02`，随后又被失败响应清空，表现成用户偶发退出。
Token Endpoint 超时也要单独测。服务端可能已经完成轮换，只是响应没有到达客户端；客户端再拿旧 Refresh Token 重试时，会被当成重放。这个场景没有统一的客户端补救答案，系统需要明确是重新登录、查询会话状态，还是使用带幂等能力的内部机制，测试只按约定验证，不能靠无限重试兜底。
### 退出登录后，旧 Access Token 还能用吗
退出通常同时涉及订单后台本地会话、身份提供方会话和 Token，三者不是一个开关。只清理浏览器 Cookie，已有 Access Token 可能仍可调用 API；只退出身份提供方，本地会话也可能继续存在。
我会分别执行“仅退出当前应用”“退出身份提供方”“撤销 Refresh Token”“管理员禁用账号”，记录以下结果：当前页面何时失效，旧 Access Token 是否立即失效，Refresh Token 能否继续换票，其他设备是否受影响。RFC 7009 要求支持撤销 Refresh Token，但关联 Access Token 是否同步失效取决于授权服务器策略和 Token 形态；自包含 JWT 常见做法是等待短有效期结束，或额外查询状态。需求没有写清楚时，不能擅自把“退出后立刻 401”当成唯一正确结果。
撤销接口的 HTTP 200 也不能作为唯一证据。RFC 7009 允许对无效 Token 返回成功，避免泄露其是否存在；调用完成后，还要再次使用原 Refresh Token 换票，并按系统策略请求受保护 API，才能确认撤销范围。机密客户端应按注册方式完成认证，`token_type_hint` 只是提示，不代替服务端识别 Token：
    
    POST /revoke HTTP/1.1
    Host: idp.example.test
    Authorization: Basic <client credentials>
    Content-Type: application/x-www-form-urlencoded
    
    token=<refresh token>&token_type_hint=refresh_token
    
OIDC 的 RP-Initiated Logout 请求应发送到 Discovery 返回的 `end_session_endpoint`，而不是在客户端写死 `/logout`。其中 `post_logout_redirect_uri` 必须与预注册地址精确匹配，非法地址不能在退出后获得跳转机会。浏览器返回登录页时，也要观察身份提供方会话是否仍在：如果再次点击登录无需输入账号，这是 SSO 会话仍有效，不一定是退出失败，但产品文案必须与真实行为一致。
    
    GET /logout?id_token_hint=&lt;当前会话的ID Token&gt;&post_logout_redirect_uri=https%3A%2F%2Forders.example.test%2Fsigned-out&state=LOGOUT-3d71 HTTP/1.1
    Host: idp.example.test
    
回跳后除检查地址，还要比对本次退出事务生成的 `state`，防止退出响应与其他浏览器事务串用。`id_token_hint` 通常用于让身份提供方识别当前 RP 会话；缺少它时，使用 `post_logout_redirect_uri` 的请求通常还需要 `client_id`，身份提供方也必须要求用户确认是否退出。规范允许 GET 和 POST，若 GET 查询串会进入代理或访问日志，项目应在身份提供方支持的前提下优先使用 POST 并做好日志脱敏。具体交互仍应以项目使用的身份提供方策略为准。
### 我会保留的回归路径
日常版本回归不需要把所有 Token 组合重新跑一遍。我会保留下面五条路径，它们分别卡住登录事务、资源边界和会话生命周期：

路径| 操作| 至少保留的证据  
---|---|---  
正常登录| 授权码加 PKCE 完成登录| Issuer、Session ID 变化、API 调用成功  
回调串用| A 浏览器的 `code` 搭配 B 浏览器的 `state`| 回调失败、本地 Session 未创建  
Token 跨 API| `profile-api` Token 调用订单 API| 401、`invalid_token` 或项目等价错误、订单数据不变  
并发刷新| 两个请求同时使用同一 Refresh Token| 一次成功、重放处置、新 Token 最终状态  
退出后调用| 保存旧 Token，退出后再次换票和请求 API| Session、Refresh Token、Access Token 各自失效时间  

身份系统升级、客户端接入方式变化或新增身份提供方时，再扩展 Redirect URI 绕过、算法与密钥轮换、授权码并发兑换、用户拒绝授权、时钟偏差和多设备退出。测试日志通过 `loginTransactionId` 关联浏览器、客户端、身份提供方和 API，但只记录 Token 指纹，避免为了排查登录问题制造新的凭证泄露。
### 总结
这条登录链路有四段绑定关系：回调属于哪次浏览器会话，授权码属于哪个客户端，Token 发给哪个接收方，刷新和退出后哪些凭证仍然有效。把 `state、nonce、code、aud、scope` 与业务副作用串起来，页面跳回成功才有完整含义。
