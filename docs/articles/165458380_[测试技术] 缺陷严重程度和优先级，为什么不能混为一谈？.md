# [测试技术] 缺陷严重程度和优先级，为什么不能混为一谈？

> 原文: https://blog.csdn.net/weixin_42390585/article/details/165458380

> 原创内容，未获授权禁止转载、转发、抄袭。

缺陷评审时，经常会同时讨论两个问题：这个问题影响大不大？现在要不要马上修？
前一个问题对应严重程度（Severity），后一个问题对应优先级（Priority）。两个字段经常一起出现在缺陷单里，但判断依据并不相同。把“严重程度高”直接当成“优先级高”，看似简单，实际会让缺陷排序失去依据。
### 先把两个概念分开
ISTQB对这两个概念的解释，可以压缩成两句话：
  * **严重程度** ：缺陷对系统或组件造成的影响有多大。
  * **优先级** ：这个缺陷应该按照什么顺序被处理。


换成更容易记的说法：
严重程度看“出了问题会有多大影响”，优先级看“现在是不是要先处理”。
严重程度更接近缺陷本身的属性。优先级则会受到发布时间、用户范围、业务活动、合规要求和临时规避方案影响。同一个缺陷，在日常版本中可能排在后面，到了大促或正式发布前，优先级可能马上上调。
团队可以把严重程度和优先级分成高、中、低，也可以使用 Blocker、Critical、Major 等名称。等级名称不是行业统一标准，真正需要统一的是每个等级的判断条件，以及谁有权调整它。
### 四种组合

组合| 典型场景| 通常的处理方式  
---|---|---  
高严重、高优先| 支付重复扣款、用户数据丢失| 立即排查，必要时止损或暂停发布  
高严重、低优先| 低频管理配置错误，触发后会导致系统无法启动| 记录高风险，根据触发条件和发布计划安排  
低严重、高优先| 大型活动首页的主要文案错误| 技术影响小，但曝光范围大，尽快修正  
低严重、低优先| 低频后台页面的对齐问题| 排入后续改进，不影响当前发布  

“高严重、低优先”最容易被误解。问题本身依然重要，只是当前触发条件很窄，或者现阶段几乎没有使用场景。将它排在后面时，应留下风险说明和复查条件；一旦用户范围、业务阶段或发布计划发生变化，优先级就应该重新评估。
### 严重程度怎么判断
严重程度不应只看页面有没有报错，要看业务结果发生了什么变化。评审时可以关注：
  * 是否造成金额、库存、订单或权限数据错误；
  * 是否导致业务中断、数据丢失或功能完全不可用；
  * 是否涉及个人信息、账号权限或合规要求；
  * 是否只影响一个页面，还是会沿着公共逻辑扩散到多个业务。


例如，导出按钮的文字写错，通常属于较低严重程度。但如果用户因此选择了错误的导出范围，接口实际返回了不该看到的数据，问题就应按数据安全风险重新判断。
严重程度还要看影响是否可恢复。页面颜色不一致，通常刷新即可恢复；订单状态写错，可能会引发库存、支付、退款等后续数据问题。后者即使偶尔发生，也不能只按发生频率来降低严重程度。
### 优先级怎么判断
优先级关心的是处理顺序，可以从下面几个问题入手：
  * 是否阻塞当前发布、验收或上线活动；
  * 是否影响大量用户、高频功能或关键客户；
  * 是否存在合同、法规、客户承诺或明确的时间节点；
  * 是否有临时规避办法，以及规避方案会带来什么成本；
  * 修复需要多长时间，是否会引入新的发布风险。


一个大促页面的标题写错，系统功能可能完全正常，但它会直接影响活动转化和品牌展示，优先级可以高于某个后台管理页面的功能缺陷。相反，一个严重程度很高的配置问题，如果只有极少数管理员能触发，且当前版本没有启用相关能力，优先级可以暂时靠后，但必须保留风险记录。
优先级也不应该只由测试人员单独决定。测试人员负责提供影响范围、复现条件和证据；产品、开发、运营或项目负责人结合当前目标确定处理顺序。优先级本来就包含业务安排，需要由了解当前目标的人共同确认。
### 评审缺陷时，可以先问四个问题
  1. 这个问题实际改变了什么？是页面展示、业务结果，还是数据安全？
  2. 受影响的用户和业务范围有多大？是否可以稳定复现？
  3. 什么时间点必须解决？不修会阻塞什么工作？
  4. 有没有临时规避办法？规避方案会带来什么成本？


前两个问题更接近严重程度，后两个问题更接近优先级。它们不是严格的打分公式，却能把“感觉很严重”变成可以讨论的事实。严重程度和优先级也不能简单相乘，得出一个统一分数；四种组合本身就可能对应不同的处理策略。
缺陷描述也应把两类信息分开。比如：
严重程度：高。支付请求超时重试时，可能创建两条扣款记录。
优先级：高。本版本即将开放支付功能，当前没有可靠的人工对账方案。
如果后来增加了幂等保护，问题仍然可能是高严重程度，但优先级可以根据剩余风险重新调整。严重程度描述问题本身，优先级描述当前怎么安排。
### 几个常见误区
**把严重程度当成优先级。** 高风险问题不一定马上处理，低风险问题也可能因为发布节点临近而需要先改。
**用发布时间反推严重程度。** “马上要上线”只能说明优先级升高，不会改变问题对数据、资金或权限的实际影响。
**只看界面，不看业务结果。** “按钮无法点击”可能只是低频页面交互问题，也可能意味着用户无法完成关键操作。判断严重程度要追到接口和业务结果。
**所有缺陷都使用同一套固定规则。** 统一定义有助于协作，但产品类型、用户范围和业务风险不同，不能脱离上下文机械打分。即使都标为 High，也要看团队对这个等级的具体约定。
**忽略字段的变化。** 缺陷复现范围扩大、临时方案失效、发布计划调整后，优先级应该重新评估。严重程度和优先级都不是提交缺陷时一次填写、之后永远不变的标签。
### 总结
严重程度描述缺陷已经造成或可能造成的影响，优先级描述当前处理它的先后顺序。前者帮助团队理解风险，后者帮助团队安排工作。
评审时先说清实际影响，再结合用户范围、发布时间、临时方案和修复成本决定优先级。两个字段分开填写，缺陷排序才有依据，测试人员提供的风险信息也更容易转化成团队可以执行的处理计划。
