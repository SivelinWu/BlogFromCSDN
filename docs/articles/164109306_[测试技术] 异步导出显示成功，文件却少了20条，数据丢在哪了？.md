# [测试技术] 异步导出显示成功，文件却少了20条，数据丢在哪了？

> 原文: https://blog.csdn.net/weixin_42390585/article/details/164109306

> 原创内容，未获授权禁止转载、转发、抄袭。

后台导出看起来是个很普通的功能：选好条件，点一下导出，等任务跑完再下载文件。真正测起来，它比页面查询麻烦不少。一次导出要经过创建任务、分页查库、写临时文件、合并分片、上传对象存储等步骤，页面上的“成功”只是最后展示出来的一个状态，并不能天然证明文件是完整的。
我遇到这类问题时，通常先把场景压缩到足够简单：列表里有 5000 条已支付订单，导出任务显示成功，CSV 也能正常打开，但文件里只有 4980 条。重新导一次，数据又可能正常。下面用一组可复现的测试数据还原这个现场，看看 20 条数据是怎样被分页跳过去的。示例中的订单号和表结构都是简化数据，不对应真实业务。
### 先把任务卡在第三页
测试库准备 5000 条 `PAID` 订单，ID 连续为 1～5000。导出程序每页读取 1000 条，使用的是很常见的 Offset 分页：
    
    SELECT id, order_no, amount, status
    FROM orders
    WHERE status = 'PAID'
    ORDER BY id
    LIMIT 1000 OFFSET :offset;
    
为了稳定复现，我会让开发加一个只在测试环境生效的暂停点：第三页写完后挂起任务，手动恢复后再查第四页。如果暂时不方便加测试开关，也可以在本地调试时打断点。靠“导出过程中赶紧改几条数据”碰时机，偶尔能撞上，但不适合后面做回归。
操作顺序如下：
  1. 创建导出任务，确认任务快照或预期主键清单里有 5000 条数据。
  2. 等前三页写入完成，此时文件中已有 ID 1～3000。
  3. 保持任务暂停，把前面读过的 20 条订单改成取消状态。
  4. 恢复 Worker，让它继续读取第四、第五页并生成文件。


第三步执行的 SQL 很简单：
    
    UPDATE orders
    SET status = 'CANCELED'
    WHERE id BETWEEN 101 AND 120;
    
这 20 条记录退出筛选范围后，`PAID` 结果集从 5000 条缩成了 4980 条。第四页仍然执行 `OFFSET 3000`，等于跳过当前结果集的前 3000 条。因为后面的记录已经整体向前补了 20 个位置，这一页会从 ID 3021 开始，ID 3001～3020 就这样被跨了过去。
最后写进文件的数据是：
    
    第 1～3 页：ID 1～3000，共 3000 条
    第 4～5 页：ID 3021～5000，共 1980 条
    最终文件：4980 条
    缺失数据：ID 3001～3020
    
任务没有报错，SQL 每次也都正常返回，所以代码很可能顺顺当当地把状态改成 `SUCCESS`。这正是问题难找的地方：流程确实结束了，数据却没有走完整。
### 一个很巧的误判：数量居然对得上
导出结束后再查数据库，当前 `PAID` 订单也是 4980 条；下载文件同样有 4980 条。只比数量的话，这次测试会通过。
但两边并不是同一批数据。文件保留了已经写入的 ID 101～120，而当前数据库里没有这 20 条；文件又缺少仍然处于 `PAID` 状态的 ID 3001～3020。一进一出，刚好把数量抹平了。
所以我在测导出时，会先留下一份“任务创建时应该导出哪些业务主键”的清单。任务结束后比较主键集合，再检查关键字段。当前数据库的 `COUNT(*)` 只能当辅助信息，因为导出期间数据可能已经变了。
Offset 还有另一种表现：如果新记录能插入已经读取过的排序区间，后面的分页可能重复读取旧数据。排序字段不唯一时更麻烦，相同排序值的记录顺序本来就不稳定，数据不变也可能在两页之间来回晃。
### 把 Offset 换掉后，还要确认导出的是哪个时刻
开发看到上面的现象，通常会先把分页改成按主键向后读：
    
    SELECT id, order_no, amount, status
    FROM orders
    WHERE status = 'PAID'
      AND id > :last_id
    ORDER BY id
    LIMIT 1000;
    
每页成功写入后保存最大的 `id`，下一页从这个位置继续。这样不会因为前面的数据减少而跳行，任务重试时也更容易找到续跑位置。
不过这里还差一个产品约定：用户下载的文件，代表点击导出那一刻的数据，还是任务执行期间陆续读到的最新数据？游标分页稳定了读取顺序，却没有固定数据版本。任务跑了十分钟，期间新订单、状态变化和金额修改仍然可能混进不同分页。
实际项目里常见三种处理方式：

做法| 适合的场景| 要接受的代价  
---|---|---  
同一事务内读取一致性快照| 数据量可控，希望拿到同一时刻的数据| 长事务会保留旧版本并占用资源，失败后通常要重新开始  
截止时间加游标| 只需要排除任务创建后的新增数据| `created_at <= cutoff` 留不住后续更新、删除前的字段值  
创建任务快照表| 大任务需要分片、续跑和对账| 要增加快照生成、存储和清理逻辑  

MySQL 的 `REPEATABLE READ` 可以让同一事务里的普通一致性查询读取同一个快照。这里有个实现细节要问清楚：分页是否真的使用同一数据库连接和同一事务？如果每查一页就提交，然后重新开启事务，后面的页面还是会看到新数据。
快照表也要看保存了什么。只保存订单 ID，可以固定导出范围，但查询详情时仍可能拿到修改后的金额和状态；若需求写的是“导出点击时的数据”，快照中需要保存实际导出字段，或者从审计、历史版本等数据源读取。这个问题最好在需求评审时说清楚，否则测试和开发各自理解一个“正确结果”。
### 页面显示成功之前，再做一次对账
我会建议任务记录至少留下这些信息：
    
    task_id
    snapshot_id / cutoff_time
    expected_count
    exported_count
    completed_parts / expected_parts
    file_checksum
    object_key
    status
    
分片明细再记录 `part_no`、`row_count`、`min_id`、`max_id`、`checksum` 和状态。所有预期分片完成、数量与快照相符、文件流关闭、对象上传完成后，任务才能进入 `SUCCESS`。如果一条订单会导出多行商品明细，对账对象就换成明细主键或约定的业务唯一键，不能拿订单数直接套。
对象存储也可能留下“接口调用过了，但文件没真正组装完成”的空档。以 Amazon S3 的分段上传为例，完成接口会根据提交的 Part 列表组装对象；直接调用 API 时，初始响应已经是 `200 OK`，响应体里仍可能带有处理错误。业务代码最好使用官方 SDK，并在确认完成操作成功后再发布下载地址。
### 修完后，我会专门断几次任务
正常导出 100 条数据只能证明主流程能跑，分页和异步任务的问题往往藏在中断位置。回归时我会补下面几次故障注入：
  * 第 7 页固定抛出查询超时，任务应失败，页面不能下载已经写了一半的文件；
  * 分片写完、进度落库之前终止 Worker，重启后不能把这一片再写一遍；
  * 合并时故意漏掉最后一个分片，数量或校验不一致时不能标记成功；
  * 文件还没关闭就触发上传，系统应阻止上传未写完的临时文件；
  * 上传完成、任务状态更新之前终止 Worker，重试时应识别已有对象，不能生成两份互相打架的文件。


这些故障点不一定都要长期保留成产品配置，可以做成测试环境的 Hook，或者在集成测试里替换相应组件。每次注入后除了看任务状态，还要检查临时文件、对象存储、分片记录和重试次数，避免表面失败了，后台却留下重复文件或无法清理的分片。
### 下载以后，按订单号把文件对一遍
下面的脚本适用于“一条订单对应一行”的 CSV。`expected_ids.txt` 来自任务快照或预置测试数据，每行一个订单号，不能在导出结束后重新查询当前数据库充当预期。
    
    import csv
    import sys
    from collections import Counter
    
    
    if len(sys.argv) != 3:
        raise SystemExit("用法：python3 verify_export.py expected_ids.txt orders.csv")
    
    
    def read_expected(path):
        with open(path, encoding="utf-8") as file:
            return {line.strip() for line in file if line.strip()}
    
    
    def read_actual(path):
        with open(path, newline="", encoding="utf-8-sig") as file:
            reader = csv.DictReader(file)
            if "订单号" not in (reader.fieldnames or []):
                raise ValueError("CSV 中缺少订单号列")
            return [row["订单号"].strip() for row in reader]
    
    
    expected = read_expected(sys.argv[1])
    actual_list = read_actual(sys.argv[2])
    actual = set(actual_list)
    duplicates = sorted(
        order_no for order_no, count in Counter(actual_list).items() if count > 1
    )
    missing = sorted(expected - actual)
    unexpected = sorted(actual - expected)
    
    print(f"expected={len(expected)}, actual_rows={len(actual_list)}")
    print(f"missing={len(missing)}, unexpected={len(unexpected)}, duplicates={len(duplicates)}")
    print("missing_sample=", missing[:10])
    print("unexpected_sample=", unexpected[:10])
    print("duplicate_sample=", duplicates[:10])
    
    if missing or unexpected or duplicates:
        raise SystemExit(1)
    
运行方式：
    
    python3 verify_export.py expected_ids.txt orders.csv
    
主键集合对上只是第一道门。金额、状态、时间等关键字段还要和任务快照逐项比较，或者对排除导出时间等动态列后的规范化内容计算校验值。
CSV 里还有一个很日常的坑：备注字段可以带换行，地址可以带逗号，内容里也可能出现双引号。RFC 4180 描述了这类字段的引号和转义方式，所以别再用 `wc -l` 当 CSV 记录数，直接交给 CSV 解析器。测试数据里放一条带换行备注的订单，很多粗糙的导出或校验脚本当场就能露出问题。
如果导出 Excel，还要记得单个工作表最多 1048576 行。第一行放表头后，业务数据最多是 1048575 行。超过上限时，系统要明确拆工作表、拆文件还是直接失败，写满后悄悄截断肯定不行。
### 最后收进回归的场景
这次问题修完，我会留下这些用例：
  * 分别导出 999、1000、1001 条，专门踩一次分页边界；
  * 导出暂停后新增、更新、删除数据，结果符合约定的快照语义；
  * 准备相同排序值的数据，确认使用唯一且稳定的次级排序；
  * Worker 在不同分片位置重启，文件没有缺失和重复；
  * 单个分片、合并、上传失败时，任务状态和残留文件都符合约定；
  * CSV 特殊字符能被标准解析器读回，字段值不变；
  * Excel 数据量跨过单表上限时，拆分数量与总记录数能对上；
  * 数据不变时连续导出两次，主键集合一致，去掉动态列后的内容校验值一致。


自动化报告里最好带上任务 ID、快照标识、预计数量、实际数量、已完成分片数和文件校验值。下次再少数据，可以先判断是查询漏了、分片丢了，还是文件上传不完整，不用从下载按钮一路猜到数据库。
### 总结
这次复现里，20 条数据丢在了两次分页之间。Offset 遇到结果集变化后发生位移，任务状态又没有和快照、分片、文件做最终对账，于是残缺文件也顺利走到了“成功”。
以后再测异步导出，我会先固定任务开始时的预期数据，再在分页中途主动改数据或杀 Worker，下载后按业务主键和关键字段对一遍。页面数量、数据库数量和文件行数即使都一样，里面仍然可能少一批、又多一批。把这层巧合拆开，问题就好查多了。
