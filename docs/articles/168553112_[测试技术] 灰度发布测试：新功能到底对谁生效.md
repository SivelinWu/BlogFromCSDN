# [测试技术] 灰度发布测试：新功能到底对谁生效

> 原文: https://blog.csdn.net/weixin_42390585/article/details/168553112

> 原创内容，未获授权禁止转载、转发、抄袭。

同一个活动页面，有人看到新版，有人仍看到旧版，灰度期间这很正常。但如果同一个账号刷新几次，页面就在新旧版本之间切换，就得往下查了：是用户分流不稳定，还是请求随机落到了不同版本的服务？
灰度发布会先让部分用户或流量使用新版本，观察效果后再逐步扩大范围。实际项目里，网关可以把一部分请求转给新服务，功能开关也可以按账号决定是否展示新入口。这两种方式可以同时使用，但测试预期得分开写。把流量权重设成 10%，并不自动等于固定的 10% 用户能看到新功能。
下面以“新版优惠券领取页”为例，把账号、配置和领取记录串起来检查。规则和数据均为测试设计示例。
### 先问清楚，这个 10% 按什么分
假设新版页面只对部分登录用户开放，产品约定如下：

条件| 示例规则  
---|---  
总开关| 关闭时所有用户走旧版，白名单也不例外  
基础门槛| 已登录，且客户端具备新版所需能力  
排除名单| 满足门槛后仍优先排除  
白名单| 满足门槛且未被排除时，固定走新版  
普通用户| 按服务端账号 ID 稳定分桶，命中前 10% 的桶  
未登录用户| 走旧版，登录后重新判断  

这张表比“灰度比例 10%”多写了几个条件，却省掉不少争论。比如白名单账号使用不兼容的旧客户端，到底应不应该开放？总开关关闭以后，测试账号还能不能看到新版？这些都需要明确优先级，不能靠测试人员猜。
按这套约定，白名单与排除名单同时命中时走旧版；白名单账号使用不兼容客户端时也走旧版。测试要实际构造这两种冲突，再关闭总开关检查原先已命中的账号，单独验证每条规则无法证明优先级正确。
本例要求在配置修订和账号属性不变时，同一账号在兼容客户端上得到一致结果。如果项目按设备、租户或地域分流，就要换成相应的判断单位。企业产品按租户灰度时，还得验证同一租户的多个成员是否一起生效。
这里采用账号级功能开关；服务可以同时支持新旧页面。若部署中还用了网关流量灰度，需要另查命中用户的请求能否到达兼容服务。功能开关开启，不代表请求一定去了新版本；新服务接到请求，也不代表必须向该用户展示新功能。
### 用固定账号验证命中，别靠反复刷新碰运气
准备一个白名单账号、一个排除账号，以及分别落在灰度范围内外的普通账号。普通账号应由配置平台或后端提供已知分桶结果，不能挑一个偶然看到新版的账号，就把它当作稳定的测试数据。
例如系统约定 10,000 个桶，编号为 `0～9999`，10% 对应 `bucket < 1000`。可以专门准备落在 `999` 和 `1000` 的两个普通账号，预期分别为命中、不命中；两者都满足基础门槛且不在任何名单中。这是本文自定义的示例分桶规则，不是所有灰度平台的统一算法。
预期桶值应根据已确认的算法、种子和账号 ID 编码生成，并固定为测试数据。运行时再与判定日志核对，避免直接把被测接口返回的桶值当作正确答案。若平台不暴露分桶算法，就依据其公开契约验证稳定命中和比例，不强行套用 `999/1000` 这组边界。
对每个账号，连续请求、重新登录，再换一个兼容客户端访问。检查页面表现的同时，让后端提供能关联请求的判定日志。下面只是建议字段，不是实测输出：
    
    traceId=qa-001 subjectHash=7ab... flag=coupon_page_v2
    configRevision=rev-17 reason=percentage bucket=999 enabled=true
    serviceVersion=coupon-service-v2
    
`reason` 能解释为什么命中，`configRevision` 能区分请求是否使用了同一份配置，`serviceVersion` 则帮助判断有没有实际路由到新服务。用户标识使用摘要，内部版本和分桶信息留在服务端诊断日志中即可。
这样，刷新后版本变了，就能沿日志查到是分桶、配置修订还是服务路由发生了变化，不必只凭页面截图猜原因。
#### 比例是另一条用例
命中规则正确，不代表总体分布一定合理。比例用例只统计满足基础门槛、且不在白名单或排除名单中的普通账号，保持配置修订一致，按唯一账号计数。一个活跃用户请求一百次，也只能算一个用户。
10% 通常是分桶目标，并不保证任意十个账号恰好命中一个。比例用例应根据样本规模预先确定允许偏差，并使用独立于命中结果选取的账号样本，不能拿专门挑选的边界账号做分布统计。同一批账号重复请求不会增加统计样本量；边界用例要求明确的命中结果，比例用例关注整体分布，两者不要混成一条断言。
### 页面稳定了，还要看看账号切换和缓存
先用命中新版的账号 A 登录，再退出，换成未命中的账号 B。页面不应因为复用了 A 的本地配置继续显示新版，提交请求也不应沿用 A 的功能判定结果。
还可以延迟 A 的配置响应，等 B 登录后再让这条旧响应返回。客户端应该丢弃与当前会话不匹配的结果，不能让迟到的 A 配置覆盖 B 的状态。否则即使退出时清理了缓存，仍可能发生串用。
这个场景可以沿着实际访问链路检查：浏览器本地存储是否按账号隔离，服务端缓存是否包含必要的用户或租户维度，CDN 是否把带个性化内容的页面当成公共页面缓存。并非所有缓存都需要加用户 ID，但个性化判定不能被无差别复用。
再试一次从未登录状态进入页面，然后直接登录。按照示例规则，登录前走旧版，登录后需要重新判定。若系统只在应用启动时拉取配置，登录后可能一直用旧值，直到用户彻底重启应用才变化。
隐藏入口也没有提供访问权限控制。若灰度限制的是领取行为，未命中账号直接调用接口或伪造灰度标记时，服务端仍应执行自己的判定；若只灰度页面样式，共用领取接口正常成功并不算绕过。两种情况下，登录校验、资源归属和领取资格都必须生效，客户端自带的标记不能成为授权依据。
### 扩量时，原来的用户别被重新洗牌
把比例从 10% 调到 30%，本例希望原先命中的普通账号继续命中，再新增一批用户。固定分桶算法和种子，只扩大阈值，通常可以满足这个目标；如果发布时顺手更换了分桶字段或种子，用户集合就可能整体变化。
测试可以保存扩量前后的账号集合：
    
    S10：10% 配置下命中的普通账号
    S30：30% 配置下命中的普通账号
    
    预期：S10 是 S30 的子集
    前提：同一批账号，账号属性、名单、分桶算法、种子和开关标识均未改变
    
配置下发也需要时间。例如测试环境约定发布成功后 30 秒内生效，就以发布确认时刻为起点，记录各判定节点使用的修订，检查它们是否在期限内切到目标修订；30 秒只是示例，应替换成项目约定。配置到达节点还不够，必须再发请求确认实际判定已经使用它。服务端 SDK、浏览器或 App 若各自缓存配置，都要纳入检查。
传播窗口内能否暂时出现新旧结果，需要提前约定；超过期限仍未收敛才可按该时限判失败。不能只反复请求负载均衡入口来推断所有节点都已更新，应结合实例日志或受控的节点定向验证。
可以在测试环境让其中一个实例暂时无法获取配置，观察它采用缓存值、默认关闭还是其他回退策略。预期要以系统约定为准，同时检查恢复后能否追上当前配置。需要紧急关闭的功能，还应确认旧缓存最多能让功能继续开放多久。
### 回滚测试，要带着新版产生的数据一起退
关闭开关后，旧页面恢复显示，只完成了一半验证。新版如果已经生成了旧代码不认识的字段、状态或消息，用户下一次查询、取消或退款时，问题才会出现。
仍以领取优惠券为例，可以先让灰度账号完成一次新版领取，再关闭开关，继续查看领取记录并尝试使用这张券。检查旧页面能否展示、新旧接口能否读取同一条记录，以及后续核销流程是否正常。若新版增加了业务状态，旧版的处理方式必须有明确约定，不能默认“遇到未知状态就跳过”。
回滚时还要保留一个已经打开新版页面、但尚未提交的会话。关闭开关后再点击领取，服务端应重新判定或按明确的兼容策略处理，不能出现页面提示成功却没有领取记录，也不能因为客户端重试而多领一张。
再补一个真正的在途请求：服务端已经受理领取，但响应尚未返回时关闭开关。应提前约定这类请求继续完成还是中止，不能默认关开关会撤销已受理的操作。若响应丢失，再用同一业务幂等标识重试，核对领取记录、库存流水和通知是否符合一次有效领取的约束；中止的请求则检查有无遗留扣减和补偿。
功能开关回退与服务版本回退也要分别验证。关掉入口不会撤销已发生的数据库变更、消息投递或外部调用；已经成功的领取记录应保留，异常数据按补偿规则处理。若旧代码无法读取新数据，直接回退服务版本可能比暂时保留新版更危险。
### 决定继续放量时，看哪些结果
灰度期间，整体成功率可能掩盖小范围故障。新版本只承接少量用户时，即使这些用户频繁领取失败，总体曲线也可能变化不大。应分别观察新旧组的接口错误率、延迟和业务成功率，再结合样本量判断。
对这个领取场景，可按业务幂等标识去重，统计受理的领取操作中最终成功的比例，既有记录的幂等返回也按成功处理；尚未完成的单独列出，并约定观察期限。接口错误率仍按请求统计，两套口径不要混用，否则重试次数变多就会扭曲业务成功率。重复领取、库存扣减和下游通知还要单独对账。
新旧组应采用相同时间窗口和统计口径，并记录实际执行的变体及配置修订，不能用用户当前分组回填历史请求。两组用户构成可能不同，指标差异可以触发排查，但不能直接当作新版本导致变化的证据。
白名单用户通常有专门准备的数据，不能代表全部用户。正式放量前，至少补上新老账号、无可领优惠券、重复领取和不兼容客户端这些有差异的条件。告警阈值、观察窗口与暂停放量的条件也应提前约定，不能等出问题后再挑一个看起来正常的指标。
### 总结
时间有限时，可以先固定一批账号，走完命中、切账号、扩量和回滚。每一步保留配置修订、实际判定和业务记录，出问题时才知道该查哪一层。尤其别跳过回滚后的领取记录和在途请求：页面恢复旧版后，新版产生的数据仍然存在，旧流程能否继续处理它们，需要实际验证。
