# [测试技术] 一次订单ID替换，暴露了接口的水平越权

> 原文: https://blog.csdn.net/weixin_42390585/article/details/164288962

> 原创内容，未获授权禁止转载、转发、抄袭。

订单详情页回归时，我准备了两个普通测试账号，账号A和账号B各自创建一张订单。在抓包工具里重放详情请求时，我保留账号A的Token，只把路径中的订单ID换成账号B的。接口没有拒绝，而是返回了账号B的收货人、金额和订单状态。
两个账号角色相同，也都已经正常登录，区别只在于订单归属。这个问题后来被归为水平越权：用户有权调用订单详情接口，却没有权访问这张具体订单。下面按这次回归过程做一份脱敏记录，账号、订单号、接口和响应内容均已简化，只用于说明测试方法。
### 问题是怎么暴露的
当时准备的数据很少，反而方便对照：

测试账号| 角色| 自有订单  
---|---|---  
`U-A`| 普通用户| `ORD-A-1042`  
`U-B`| 普通用户| `ORD-B-2077`  

先用账号A的Token查询自己的订单，接口正常返回200：
    
    GET /api/orders/ORD-A-1042 HTTP/1.1
    Authorization: Bearer &lt;token-a&gt;
    
接着保持Token不变，只替换路径中的订单ID：
    
    GET /api/orders/ORD-B-2077 HTTP/1.1
    Authorization: Bearer &lt;token-a&gt;
    
问题版本的响应可以简化成下面这样：
    
    HTTP/1.1 200 OK
    Content-Type: application/json
    
    {
      "orderId": "ORD-B-2077",
      "buyerId": "U-B",
      "status": "PENDING_PAYMENT",
      "amount": "199.00",
      "receiver": "测试用户B"
    }
    
这里用的是已知测试订单，不需要枚举订单号，更不需要扫描接口。OWASP的测试指南也建议准备至少两个用户和各自拥有的对象，这比猜测别人的资源ID更快，结果也更容易复核。所有操作都应限制在授权的测试环境和自建测试数据中。
### 先把证据对齐
发现接口返回200后，我没有马上下结论，先核对Token、订单归属和服务端日志。这个过程留下四份证据：
  * 请求中的Token确实属于账号A，重新登录获取新Token后结果不变；
  * 请求路径使用的是账号B的订单ID；
  * 数据库中该订单的买家是 `U-B`，没有共享、代下单等特殊关系；
  * 服务日志记录的当前用户是 `U-A`，查询结果却来自 `ORD-B-2077`。


如果项目有租户概念，还要把当前租户和订单租户一起记下来。缓存命中也值得看一眼：若数据库查询已经带了用户条件，接口仍返回他人订单，问题可能藏在只使用订单ID的缓存Key里，而不一定在SQL。
这份证据链可以区分三种常见情况：登录态拿错、测试数据准备错，以及服务端确实缺少对象级授权。前两种是测试环境或数据问题，第三种才是这里讨论的水平越权。
### 登录校验通过，不等于有权看这张订单
排查代码后，问题落在一条只按订单ID查询的语句上。下面是简化后的问题写法：
    
    SELECT order_id, buyer_id, status, amount, receiver
    FROM orders
    WHERE order_id = :order_id;
    
接口入口已经校验Token，因此未登录用户进不来；但普通用户只要拿到任意有效订单ID，查询就会返回记录。参数化SQL可以防止SQL注入，却不会自动解决资源归属问题。
普通用户查询自己的订单时，查询条件需要带上当前登录用户。多租户系统还要同时限定租户，简化示例如下：
    
    SELECT order_id, buyer_id, status, amount, receiver
    FROM orders
    WHERE order_id = :order_id
      AND buyer_id = :current_user_id
      AND tenant_id = :current_tenant_id
      AND deleted = 0;
    
`:current_user_id` 和 `:current_tenant_id` 必须来自服务端验证后的身份上下文，不能直接相信客户端传来的 `userId`、`buyerId` 或租户Header。单租户项目可以去掉租户条件，但资源所有者校验不能省。查询不到数据时，项目可以按契约返回403或404；这次回归统一使用404，使“订单不存在”和“订单不属于当前用户”的外部表现保持一致。
真实系统通常不止买家一种访问者。商家、客服和管理员可能按店铺、工单分配或数据范围访问订单，这时简单比较 `buyer_id` 也不够，需要根据“当前主体、目标订单、操作类型和业务关系”执行统一授权策略。OWASP将这类问题称为对象级授权失效，要求每个接收对象ID并对对象执行操作的接口都做检查。
### 详情接口修了，我继续沿着订单ID往下测
只修详情查询，很容易在旁边的接口再漏一次。我按不同状态分别准备了几张可丢弃测试订单：待支付订单用于取消和修改收货信息，已支付或已完成订单用于物流、售后、发票和附件。然后沿着同一个订单ID检查这些操作：
  * 查询订单详情、物流轨迹和操作记录；
  * 修改收货信息、取消订单和申请售后；
  * 下载发票、合同和订单附件；
  * 查询导出任务并下载导出文件；
  * 批量取消或批量下载时混入一张他人订单。


订单ID不一定都在URL路径里。我也检查了Query参数、JSON Body和批量ID列表，防止同一个业务在不同入参位置上使用了不同的授权逻辑。
读取接口被拒绝时，响应体不能顺手带出收货人、手机号、金额等字段；把敏感字段打码后返回200，也不等于授权正确。修改类接口还要检查数据库、缓存、消息和审计日志，确认没有发生部分副作用。例如取消接口虽然返回404，订单状态却已经变成已取消，权限判断放得仍然太晚。
附件和物流信息常通过自己的 `fileId`、`logisticsId` 查询，不能因为它们不是 `orderId` 就跳过归属校验。服务需要沿着子资源找到父订单，再判断当前用户是否有权执行这次操作。异步导出也一样：创建任务、查询进度、下载文件和取消任务都要校验任务归属。
批量接口要先约定失败策略。无论选择整体拒绝还是逐条返回结果，他人订单都不能被读取或修改；如果整体拒绝，前面已经校验通过的自有订单也不应提前产生副作用。我会专门组一次“一张自己的订单 + 一张别人的订单”，检查服务是否在执行前完成全量授权。
### 几种看起来修了、其实还留着口子的做法
把数字订单号换成UUID，只是降低了被猜中的概率。OWASP也建议使用难以预测的ID，但同时明确要求每个使用对象ID的接口执行授权检查。订单ID一旦出现在日志、分享链接、消息通知或浏览器历史里，单靠“别人猜不到”就站不住了。
前端隐藏取消按钮也没有用，接口仍然可以被直接调用。网关只校验“是否登录”或“是否拥有普通用户角色”同样不够，因为账号A和账号B都能通过这两层检查，真正缺失的是账号A与订单B之间的关系判断。
还有一种修法是在详情接口补上归属条件，却漏掉缓存、附件、导出和批量操作。授权逻辑散落在每个Controller里时尤其容易发生，新增接口也可能忘记复制。更稳妥的做法是把资源授权放到统一的服务或策略层，并为每个资源操作留下自动化回归。
### 这组用例后来留进了回归
回归没有按接口数量机械复制，而是围绕“谁、操作什么资源、执行什么动作”组合。订单场景中，至少保留下面这些：

场景| 关键断言  
---|---  
账号A查询自己的订单| 返回200，字段完整且正确  
账号A查询账号B的订单| 返回404，不泄露订单字段  
分别通过Path、Query、Body传入账号B的订单ID| 均返回404，不读取或修改他人订单  
账号A访问其他租户订单| 被拒绝，不能通过修改租户Header绕过  
查询不存在或已删除订单| 错误响应符合契约，不泄露对象是否曾存在  
账号A取消、修改或售后账号B订单| 请求失败，订单、库存、退款和消息均无变化  
账号A下载账号B的发票或附件| 请求失败，预签名地址或文件内容不返回  
批量请求混入他人订单| 按约定整体或逐条失败，不处理越权对象  
客服访问已分配订单| 按业务规则允许，并记录审计日志  
客服访问未分配订单| 被拒绝，不因客服角色直接放开全部订单  
权限或订单关系变化后再次访问| 缓存及时失效，旧权限不能继续使用  

自动化中不必随机生成陌生ID。固定准备账号A、账号B和各自的资源，先验证所有者访问成功，再让账号A对账号B的资源执行同一组操作，失败时同时检查响应和副作用。这样每增加一个订单子资源或新动作，都能很快判断对象级授权有没有跟上。
### 总结
这次问题没有复杂的攻击过程，只是登录账号A后替换了一个订单ID。接口做了身份认证，也校验了普通用户角色，却没有确认当前用户是否拥有目标订单，最终让同级用户之间的数据边界失效。
水平权限回归要盯住对象关系：当前用户是谁、目标资源属于谁、这次动作是否被允许。详情接口返回约定的错误响应只是第一步，修改、附件、批量任务、缓存和异步导出都要沿着同一条关系继续验证，并确认被拒绝的请求没有留下业务副作用。
