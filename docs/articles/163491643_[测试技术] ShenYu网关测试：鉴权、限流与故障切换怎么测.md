# [测试技术] ShenYu网关测试：鉴权、限流与故障切换怎么测

> 原文: https://blog.csdn.net/weixin_42390585/article/details/163491643

> 原创内容，未获授权禁止转载、转发、抄袭。

Apache ShenYu（神禹）是一款 Java 原生 API 网关，通常部署在客户端与业务服务之间，统一承接服务代理、协议转换和 API 治理。业务不再直接暴露每个服务地址，而是由网关根据请求路径、方法、Header 等信息选择上游。鉴权、限流、熔断、日志等能力也可以通过插件接入这条请求链路。
一条请求进入 ShenYu 后，先由选择器筛出适用流量，再由规则决定具体处理方式，随后按插件顺序执行并转发到上游。路由和插件配置由 ShenYu Admin 管理，再同步到各个网关节点。这个过程涉及规则匹配、配置同步、实例状态和插件顺序，任何一处出现偏差，都可能让相同请求在不同节点得到不同结果。
因此，订单接口经过 ShenYu 返回 200，只能说明这一次请求完成了转发。实例下线后流量有没有及时切走，规则变更是否到达所有节点，网关超时时订单是否已经落库，鉴权或限流拒绝的请求有没有继续进入业务服务，都需要单独验证。为了把这些问题讲清楚，文中固定使用一组订单接口、两台网关和两个上游实例，示例用于说明测试方法，不包含虚构的运行结果。
### 先让每次转发都可追踪
测试环境部署两个订单服务实例 `order-a`、`order-b`，通过网关访问：
    
    POST /api/orders
    GET  /api/orders/{orderId}
    
上游响应增加仅在测试环境开放的诊断字段：
    
    {
      "orderId": "T20260804001",
      "instanceId": "order-a",
      "requestId": "REQ-001"
    }
    
同时记录网关节点、选择器、规则、插件链和最终上游。一次请求至少要能串起下面这些证据：
    
    requestId -> gatewayNode -> selectorId -> ruleId
              -> rewrittenPath -> pluginResult -> upstreamInstance
              -> upstreamCallCount -> orderId
    
ShenYu 默认日志不一定提供全部字段，缺少的部分需要通过测试探针或日志扩展补齐。探针只在测试环境开放，`instanceId` 使用测试标识，不返回生产主机名和 IP。网关和上游还要沿用同一个 `requestId`，否则无法准确统计一次外部请求触发了几次内部调用。
### 把路由边界测出来
ShenYu 的选择器先筛选流量，规则再决定如何处理。两者都支持 URI、Header、Query、IP、Host 和请求方法等条件，多个条件可以使用 `and` 或 `or`；当多条配置可能命中时，`Order` 数值越小，优先级越高。
假设订单服务配置如下：

层级| 条件| 用途  
---|---|---  
选择器| `uri startsWith /api/orders`| 选中订单服务  
查询规则| `req_method = GET`| 查询订单  
创建规则| `req_method = POST`| 创建订单  

我会优先检查下面这些容易改变匹配结果的输入：
  * `/api/orders/1001`、`/api/orders/` 和 `/api/orders-extra` 的边界匹配；
  * GET、POST、OPTIONS 以及不支持的方法；
  * Header、Query 缺失、重复、大小写变化和 URL 编码；
  * 两条选择器或规则同时命中时，是否按预期优先级执行；
  * 无规则命中时，是否返回明确的网关错误，而不是落到默认上游；
  * 路径重写后，Path、Query 和 Body 是否保持业务语义；
  * `%2F`、`..`、重复斜杠等输入是否绕过鉴权或匹配范围。


每次请求同时核对 `ruleId`、重写后的路径以及上游实际收到的方法和参数。没有命中规则的请求，上游调用次数应为 0。选择器或规则的匹配日志只在测试环境短时开启，并检查其中是否意外记录了 Token、签名或敏感请求体。
### 验证规则是否到达每个网关
ShenYu Admin 可以通过 WebSocket、HTTP Long Polling、ZooKeeper、Nacos、Etcd 或 Consul 等方式同步插件、选择器、规则、元数据和签名数据。Admin 页面保存成功，只说明变更已经进入管理侧，不能证明每个网关节点的内存配置都已更新。
以两台网关 `gateway-a`、`gateway-b` 为例，把创建订单规则由 `/api/orders` 临时改为 `/api/v2/orders`：
  1. 记录配置变更时间、规则 ID 和新旧内容。
  2. 绕过负载均衡，分别请求两台网关的新旧路径。
  3. 隔离 `gateway-a` 与当前使用的数据同步通道，再发布一次规则。
  4. 验证 `gateway-a` 保持旧规则、`gateway-b` 使用新规则，且监控能发现版本不一致。
  5. 恢复链路，确认 `gateway-a` 无需重启即可追平。


这里要区分两类链路：数据同步负责把 Admin 中的网关规则同步到网关，服务注册与发现负责维护上游实例。阻断其中一条，不应笼统描述为“配置中心故障”。如果环境没有可查询的配置版本，可以使用一组互斥探测请求推断规则状态，但必须分别命中每个网关节点。
### 观察实例摘除和恢复
`divide` 支持 `roundRobin`、`random` 和 `hash` 负载策略，也支持服务预热、请求超时与重试。正常流量下，先确认两个实例都能接到请求；随机或加权策略只检查实例可达、长期分布与权重方向，不要用少量请求断言精确的 50:50。
故障切换可以按以下顺序执行：
  1. 持续发送带唯一 `requestId` 的查询请求，记录 A、B 的上游计数。
  2. 停止 `order-a`，观察失败窗口、摘除时间和请求去向。
  3. 确认稳定后流量收敛到 `order-b`，且没有继续请求已摘除实例。
  4. 恢复 `order-a`，按当前注册与发现方式确认它重新成为可用实例后再接流量，而不是进程启动即接流量。
  5. 在 `order-a` 故障期间修改 Admin 路由，检查配置更新没有把该实例错误恢复为健康。


故障期间修改路由这一项我会保留在升级回归中。ShenYu 2.7.1 的发布说明包含 Admin 配置更新后保持各网关独立上游健康状态等修复，单独测试“实例下线”或“规则更新”都覆盖不到两者叠加后的状态。Divide 文档中的 Admin 上游有效性检测仅适用于 HTTP 类型注册中心；使用 ZooKeeper、Nacos 等方式时，要从实际服务注册与发现链路确认实例状态。实验记录保留首次失败、实例摘除和恢复三个时间点，基本就能判断延迟出在哪一段。
### 超时后检查订单是否已经创建
把 `order-a` 的处理延迟设置为大于 Divide 规则的 `timeout`。请求返回后同时检查网关耗时、响应状态、上游日志和订单库，不能因为网关超时就认定上游没有执行。
对 GET 查询，若业务允许，可分别验证 `retryStrategy=current` 和 `retryStrategy=failover`：前者继续请求原实例，后者通过负载均衡选择其他实例。断言重试次数时应查看上游调用计数，不能只数网关日志，因为一次外部请求可能产生多次内部调用。
创建订单的 POST 不应直接沿用查询接口的重试策略。下面这个故障序列必须验证：
    
    网关发送 POST -> 上游写入订单 -> 上游响应延迟
                  -> 网关超时 -> 客户端重试
    
同一个幂等键只能生成一笔订单，库存扣减和支付记录也只能发生一次。接口没有幂等键时，自动重试本身就是风险，增加重试次数只会让问题更难排查。
### 鉴权、限流和熔断怎么对账
这三类插件的配置差异很大，但测试时可以共用一条证据：请求被网关拒绝后，`requestId` 不应该出现在上游。先画清楚插件执行顺序，否则同一个 401 或 429 很难判断由谁返回。
#### Sign 和 JWT 分开测
Sign 1.0.0 使用 `appKey`、`timestamp`、`sign`、`version` 等请求头。默认签名材料包含 `path`、`timestamp`、`version`，开启 `signRequestBody` 后才加入 Body 字段。我会在合法请求的基础上逐项删除或篡改这些字段，再检查过期时间戳、重复签名和 PathAuth 越权；开启请求体签名时，还要核对 JSON 字段顺序、空白与字符编码的处理是否一致。
普通业务 Header 和 Query 未必受 Sign 1.0.0 保护。Sign 2.0.0 的签名材料包含相对 URL，Query 应按 2.0.0 规则另测。官方文档提到 1.0.0 默认过滤 5 分钟前的请求，这只能限制时间窗口，不能直接视为防重放。JWT 使用另一套规则，测试项跟随实际 Header 配置，覆盖签名错误、过期、Bearer 格式和密钥轮换即可。
#### 限流要把多台网关放在一起
RateLimiter 支持令牌桶、漏桶和滑动窗口等算法，内置 Key 可以按整个规则或来源 IP 解析。压测流量要经过所有网关节点，再分别统计接收、放行、拒绝和上游收到的 `requestId`。业务 Key 只有在项目实现了自定义解析器后才有测试意义。
配额边界、突发容量和窗口恢复是我会保留的三个场景。多节点使用相同规则和 Key 时，还要确认它们共享预期的 Redis 状态。专项测试隔离其他插件且上游稳定时，上游收到数可以与限流放行数相等；跑完整插件链时，后续鉴权、熔断或路由仍可能拦截请求，此时只需保证被限流拒绝的 `requestId` 没有穿透。Redis 故障时放行还是拒绝，则按项目事先约定的容错策略判断。
#### 熔断期间盯住上游计数
使用 Resilience4j 时，先记下最小调用数、滑动窗口、失败率阈值、Open 等待时间、Half-Open 探测数和 `fallbackUri`，然后用连续超时或错误推动状态变化：
    
    Closed -> Open -> Half-Open -> Closed（恢复）
                             -> Open（仍失败）
    
Open 期间的新请求应被短路，上游计数不再增加；Half-Open 只放行配置数量的探测请求。Fallback 也需要独立的降级标识。如果它与真实下单使用相同的 HTTP 200 和业务码，调用方很容易把降级结果当成订单创建成功。
### 回归时间有限时怎么取舍
我会先跑四组：重叠路由加边界路径、单个网关同步断链、实例故障期间更新规则、订单落库后的网关超时。这四组覆盖了 ShenYu 最容易出现状态分叉的地方。鉴权、限流和熔断则各保留一条拒绝链路，用 `requestId` 确认请求没有到达上游。
Header/Body 上限、管理权限和日志脱敏适合放在版本升级或安全回归中，不必每次业务发布都完整重跑。这样的取舍比维护一张面面俱到、却长期跑不完的清单更实际。
### 总结
这套测试最后落在两份数据上：网关做了什么决策，上游产生了什么结果。规则命中、配置同步和插件状态解释前者，调用次数、订单记录和业务副作用解释后者；两边能用同一个 `requestId` 对上，网关返回的状态码才有意义。
