# [测试技术] 库存并发怎么测？从两笔成功订单查出超卖

> 原文: https://blog.csdn.net/weixin_42390585/article/details/164259218

> 原创内容，未获授权禁止转载、转发、抄袭。

测试环境里把一个 SKU 的库存调成1，然后同时提交两笔订单。两个接口都返回成功，库存表最后是0，没有出现负数。第一眼看上去，扣减逻辑似乎没问题；再查订单表，却已经有两张待支付订单。库存没有扣成 `-1`，商品还是卖出了两件。
下面用一个简化的订单场景记录这类问题怎么复现、怎么找证据，以及修复后还要继续测什么。这里约定下单时先冻结库存，支付后转为已售，取消或超时关闭后释放。表名、字段和接口均为演示数据，不对应真实系统。
### 先把账算清楚
测试 SKU 使用 `SKU-CONCURRENT-01`，初始库存如下：
    
    available_stock = 1
    frozen_stock   = 0
    sold_stock     = 0
    
下单成功后，预期变成 `available=0、frozen=1、sold=0`。如果订单支付成功，冻结库存转为已售；如果订单取消，则冻结库存退回可用库存。不管状态怎么走，当前场景都应满足：
    
    available_stock + frozen_stock + sold_stock = 1
    
这个等式只是当前简化场景的对账口径。真实系统若还有采购入库、退货、盘点和报损，需要把对应的增加量、减少量一起带入，不能永远和初始库存比较。
数量守恒还不够，冻结库存要能对应到有效的待支付订单，已售库存也要能对应到已支付订单。为了看清这些副作用，除了库存表，还要准备订单表和库存流水。每次扣减或释放都带上业务单号、动作类型和数量，后面发现账不平时才知道是哪一步多执行了一次。
### 两个请求一起到达
下面的脚本用两个线程同时提交订单。两个用户使用不同的 `requestId`，所以这不是重复点击场景，而是两个人在抢最后一件商品。接口地址和 Token 都是占位值，运行前需要替换为测试环境配置。
    
    import json
    import threading
    import urllib.error
    import urllib.request
    from concurrent.futures import ThreadPoolExecutor, as_completed
    
    
    API_URL = "https://order.example.test/api/orders"
    TOKEN = "<test-token>"
    SKU_ID = "SKU-CONCURRENT-01"
    barrier = threading.Barrier(2)
    
    
    def place_order(user_id, request_id):
        body = json.dumps(
            {
                "requestId": request_id,
                "userId": user_id,
                "skuId": SKU_ID,
                "quantity": 1,
            }
        ).encode("utf-8")
        request = urllib.request.Request(
            API_URL,
            data=body,
            method="POST",
            headers={
                "Authorization": f"Bearer {TOKEN}",
                "Content-Type": "application/json",
            },
        )
    
        barrier.wait(timeout=10)
        try:
            with urllib.request.urlopen(request, timeout=5) as response:
                return request_id, response.status, response.read().decode("utf-8")
        except urllib.error.HTTPError as error:
            return request_id, error.code, error.read().decode("utf-8")
        except urllib.error.URLError as error:
            return request_id, "NETWORK_ERROR", str(error.reason)
    
    
    cases = [
        ("U-1001", "REQ-STOCK-001"),
        ("U-1002", "REQ-STOCK-002"),
    ]
    
    with ThreadPoolExecutor(max_workers=2) as executor:
        futures = [executor.submit(place_order, *args) for args in cases]
        for future in as_completed(futures):
            print(future.result())
    
客户端同时发请求，不代表两个服务线程一定会在同一行代码相遇。为了稳定复现，可以在隔离测试环境给“读取库存之后、更新库存之前”加一个暂停点，等两个请求都读到库存为1后再一起放行。本地调试也可以用断点完成。这个开关不能进入生产配置，也不能让外部请求通过 Header 随意触发。反复跑脚本等它偶然撞上，既慢，也不方便做自动化回归。
放行后要立即查三类数据：
    
    SELECT sku_id, available_stock, frozen_stock, sold_stock
    FROM sku_stock
    WHERE sku_id = 'SKU-CONCURRENT-01';
    
    SELECT order_no, request_id, user_id, status
    FROM orders
    WHERE sku_id = 'SKU-CONCURRENT-01'
    ORDER BY created_at;
    
    SELECT biz_no, change_type, available_delta, frozen_delta
    FROM stock_flow
    WHERE sku_id = 'SKU-CONCURRENT-01'
    ORDER BY created_at;
    
库存只有1件时，两个请求最多一个下单成功。最终应有一张有效订单和一条冻结流水，另一个请求返回库存不足。只断言 `available_stock >= 0` 会漏掉一种很典型的超卖：两次请求都读到1，又都把库存写成0，库存数字看起来正常，成功订单却多了一张。
### 问题出在“先查再改”
容易出问题的代码通常分成两步：先查库存，在应用层判断够不够，再把计算结果写回数据库。下面是简化后的伪代码：
    
    stock = SELECT available_stock FROM sku_stock WHERE sku_id = ?
    
    if stock >= quantity:
        new_stock = stock - quantity
        UPDATE sku_stock SET available_stock = new_stock WHERE sku_id = ?
        INSERT INTO orders (...)
    
两个事务都读到 `stock=1`，算出的 `new_stock` 都是0。后一次更新覆盖前一次结果，数据库中看不到负库存，但两边都继续创建了订单。这就是为什么库存测试一定要把订单、库存和流水放在一起看。
一种更直接的处理方式，是把判断和扣减合并到同一条参数化 SQL。下面的冒号变量表示应用层绑定参数，不是直接粘贴到 MySQL 客户端执行的语法：
    
    UPDATE sku_stock
    SET available_stock = available_stock - :quantity,
        frozen_stock = frozen_stock + :quantity
    WHERE sku_id = :sku_id
      AND available_stock >= :quantity;
    
执行前先校验 `quantity` 是正整数，并符合单次购买上限；0、负数、小数和超大值都不能进入扣减 SQL。`sku_id` 还应命中唯一索引，避免同一 SKU 出现多行库存，也避免更新扫描并锁住无关记录。服务必须检查受影响行数：受影响1行才继续创建订单和库存流水，受影响0行就按库存不足处理。扣减、订单和流水若在同一个数据库中，应放进同一事务，后续插入失败时一起回滚，不能库存扣了，订单却没留下。
也可以先用 `SELECT ... FOR UPDATE` 锁住库存行，再查询和修改。MySQL 官方文档明确说明，普通 `SELECT` 后再更新相关数据不能提供足够保护，`FOR UPDATE` 会锁住读取到的记录直到事务提交或回滚。锁定读必须放在显式事务里，不能查完就因自动提交立即释放锁；事务中也不要夹杂慢接口和无关计算。不过单条条件更新少一次数据库交互，更适合这里简单的库存扣减。业务计算复杂到必须先读时，再考虑锁定读，并留意锁等待和死锁重试。
### 修好超卖，还没测完
并发扣减通过后，我会沿着同一张订单继续走几个状态。库存问题经常不在第一次扣减，而在超时、重试和释放。
#### 接口超时后，用同一个请求号重试
服务端可能已经冻结库存并创建订单，只是响应没有及时回到客户端。客户端用相同的 `requestId` 重试时，系统应返回第一次处理结果，不能再次扣库存。数据库最好按实际业务范围对幂等键建立唯一约束，例如“租户 + 请求号”；代码里的“先查是否处理过”仍然挡不住并发重复请求。
需要核对的结果很具体：同一个 `requestId` 只有一张订单、一条冻结流水，库存只减少一次；如果第一次仍在处理中，第二次请求应返回约定的处理中状态或等待同一结果，不能误报库存不足后又生成另一张订单。还要把相同请求号的 SKU 或数量改掉再提交，系统应明确返回幂等参数冲突，不能把旧订单当成这次新请求的结果。
#### 订单取消两次，只释放一次
订单取消、超时关单和消息重投都可能触发库存释放。连续调用两次取消接口，或者把同一条关单消息消费两次，最终只能有一次 `available +1、frozen -1`。库存流水可以用“业务单号 + 动作类型”做唯一约束，订单状态更新则使用类似 `WHERE status='PENDING_PAYMENT'` 的条件并检查受影响行数；只有成功抢到状态迁移的请求可以释放库存。订单状态和库存若在同一数据库，应在同一事务中完成；分属不同服务时，则要依赖可重试、可去重的释放指令和补偿状态，不能假设两个调用同时成功。
#### 支付和关单同时到达
把订单停在待支付状态，同时触发支付成功和超时关闭。两个处理都应以待支付为前置状态，只有一个能完成状态迁移。最终结果必须是业务允许的一种完整状态：要么支付成功、库存转为已售；要么关单成功、库存恢复可用，并按规则处理随后到达的支付。不能出现订单已支付但库存已释放，也不能冻结库存一直挂着。
#### 下单后半段失败
如果库存服务、订单服务和消息系统不在同一个本地事务里，还要主动让订单创建或消息发送失败。观察库存是否按设计回滚、补偿或等待重试，并确认补偿动作本身具备幂等性。这里只看接口返回500没有意义，真正要查的是库存有没有被永久冻结、订单是否处于可恢复状态、消息是否重复发送。补偿服务再失败一次也要测，确认任务会保留待处理状态并告警，而不是重试几次后悄悄丢掉。
### 热点 SKU 别只看有没有超卖
前面的两线程脚本适合复现竞态，不适合做性能结论。关闭测试暂停点后，再用压测工具逐步增加同一 SKU 的并发量，观察成功数、库存不足数、超时数和错误数是否能对上初始库存。请求结束后，还要确认没有可用库存凭空消失，也没有冻结库存长期找不到对应订单。
单条原子更新会让热点请求争用同一行。功能上不超卖，并不代表高峰期可用：同时记录接口 P95/P99、数据库行锁等待、死锁与重试次数、连接池占用，以及超时关单和库存补偿的积压量。若页面库存来自缓存，还要分别核对展示值和扣减结果；缓存短暂滞后可以按产品约定处理，数据库或库存服务的最终扣减结果仍应守住销售上限。
### 最后留下的回归场景

场景| 关键断言  
---|---  
库存1，并发下单2次| 仅1次成功，1张有效订单，1条冻结流水  
库存0下单| 返回库存不足，不创建订单和流水  
库存刚好等于购买量| 扣减成功，可用库存归零但不为负  
数量为0、负数、小数或超过限购| 参数校验失败，库存、订单和流水均不变化  
相同请求号并发提交| 复用同一处理结果，只扣减一次  
相同请求号修改 SKU 或数量| 返回幂等参数冲突，不复用旧结果或再次扣减  
响应超时后重试| 不重复下单，能查询到首次处理结果  
同一订单重复取消| 只释放一次，库存守恒  
支付与超时关单并发| 订单状态、库存状态和后续补偿一致  
订单创建或消息发送失败| 按设计回滚、重试或补偿，无永久冻结  
补偿任务再次失败| 保留待处理记录并触发告警，恢复后只补偿一次  
热点 SKU 逐级加压| 成功数不超过库存，超时和错误可解释，锁等待不超过约定阈值  
多 SKU 以不同顺序扣减| 能处理死锁或锁超时，不返回假成功  

并发测试不要只跑一次。测试环境可以循环执行多轮，每轮使用独立 SKU 或完整重置订单、库存和流水，并记录成功数、库存守恒结果、重复业务键和锁等待时间。多 SKU 下单还要交换商品顺序再跑一轮，确认服务按统一顺序加锁；MySQL 发生死锁时会回滚其中一个事务，业务需要使用同一幂等键有限次重试整个事务，不能把被回滚的请求返回成下单成功。共享数据没有清干净时，上一轮残留也很容易把下一轮结果搅乱。
### 总结
库存只剩1件时，两次下单都成功，库存表不一定会出现负数。普通查询后回写计算值，可能让两个事务都把1更新成0；如果只检查库存下限，这个问题很容易被放过去。
把并发稳定地卡在读取与更新之间，再同时核对订单、库存和流水，超卖证据会清楚很多。修复后继续覆盖同请求重试、重复取消、支付与关单竞争以及后半段失败，才能确认库存不仅扣得对，也能在异常链路里正确回来。
