# [测试技术] Token 刷新机制怎么测：过期、并发刷新和注销

> 原文: https://blog.csdn.net/weixin_42390585/article/details/163745159

> 原创内容，未获授权禁止转载、转发、抄袭。

很多登录问题不会出现在“输入账号密码”这一步，而是在用户连续使用一段时间后出现：Access Token 过期，页面开始不断重试；两个请求同时触发刷新，刚拿到的新 Token 又被旧响应覆盖；用户点击退出，原来的 Refresh Token 仍然可以换出新凭证。接口返回一次 200，无法说明这条会话链路是可靠的。
本文用一套明确的测试契约演示验证方法。示例系统使用短时 Access Token、Refresh Token 轮换和服务端撤销记录；客户端通过业务封装的 `/auth/refresh` 换取新凭证，退出时调用 `/auth/logout`。如果项目直接实现 OAuth 2.0 Token Endpoint，应按 RFC 6749 使用项目支持的认证方式和表单参数，不要照搬本文的 JSON 请求。接口、用户和 Token 均为虚构数据，重点放在测试人员如何观察 Token、会话和服务端状态的变化。
### 先确定被测规则
没有认证规则就直接设计用例，最后很容易把实现差异误判成缺陷。本文示例约定如下，真实项目应替换成自己的产品和安全策略：
  * Access Token 有效期较短，过期后 API 返回 `401` 和 `invalid_token`。
  * Refresh Token 可以换取新的 Access Token 和新的 Refresh Token，默认只能使用一次；如果项目配置了短暂幂等窗口，则只能在窗口内返回同一组结果。
  * 并发刷新时，服务端只接受一次旧 Refresh Token；再次使用同一 Token 按重放处理，并撤销同一 Token 家族的后续凭证。
  * 注销会清理当前应用 Session，撤销 Refresh Token；旧 Access Token 是否立即失效，按服务端采用的 JWT 黑名单、Introspection 或短有效期策略验证。
  * 刷新后，新的 Access Token 只能继承原有 Scope 和资源范围，不能通过刷新扩大权限。


测试报告至少记录下面几类证据：
  * API 返回的 HTTP 状态、OAuth 错误码和响应时间；
  * Access Token、Refresh Token 的安全摘要，不记录 Token 原文；
  * 用户 Session、Refresh Token 家族、撤销记录和审计事件；
  * 注销后再次访问 API、再次刷新以及其他设备会话的结果。


如果项目采用“不轮换 Refresh Token”，并发刷新和旧 Token 的预期会不同，不能直接套用本文结论。这个策略本身也要经过安全评审，并明确 Refresh Token 的过期、撤销和重放处理。
### 测试前先准备数据
我通常不会直接拿普通测试账号跑这类用例，因为登录状态、其他设备会话和历史 Refresh Token 会互相干扰。先准备一套隔离数据：

数据| 配置| 用途  
---|---|---  
用户 `qa-token-a`| 只有 `order.read`| 验证刷新后权限不扩大  
用户 `qa-token-b`| 具有 `order.read order.write`| 验证正常刷新和业务操作  
客户端 `order-web-a`| 被测客户端| 生成基线凭证  
客户端 `order-web-b`| 不同 `client_id`| 验证客户端绑定  
设备 A / 设备 B| 同一用户的两组 Session| 验证当前设备和全部设备注销  
测试活动| 支持设置 Access Token、Refresh Token 有效期| 快速构造过期状态  

测试环境最好提供一个只对测试租户开放的管理接口，用来撤销指定 Token、调整有效期、查询 Token 家族状态。没有管理接口时，可以在测试授权服务的存储层准备数据，但不要在业务 API 上增加“传入任意过期时间”的生产逻辑。
登录后把凭证只保存在本地临时文件，并记录摘要。下面的变量会在后续命令中复用；如果分开复制代码块，需要重新设置它们。所有命令只应指向测试环境：
    
    set -eu
    
    AUTH_URL='https://auth.example.test'
    API_URL='https://api.example.test'
    LOGIN_USER='qa-token-a'
    OUT_DIR="$(mktemp -d)"
    trap 'rm -rf "$OUT_DIR"' EXIT
    
    read -r -s -p '测试账号密码: ' LOGIN_PASSWORD
    printf '\n'
    export LOGIN_USER LOGIN_PASSWORD
    
    jq -n '{username: env.LOGIN_USER, password: env.LOGIN_PASSWORD}' |
    curl -sS "$AUTH_URL/test/login" \
      -H 'Content-Type: application/json' \
      --data-binary @- \
      -o "$OUT_DIR/login.json"
    
    unset LOGIN_PASSWORD
    
    ACCESS_TOKEN=$(jq -r '.access_token' "$OUT_DIR/login.json")
    REFRESH_TOKEN=$(jq -r '.refresh_token' "$OUT_DIR/login.json")
    token_digest() {
      printf %s "$1" | shasum -a 256 | cut -c1-12
    }
    
    jq '{token_type, expires_in, scope}' "$OUT_DIR/login.json"
    printf 'access_token=%s\nrefresh_token=%s\n' \
      "$(token_digest "$ACCESS_TOKEN")" "$(token_digest "$REFRESH_TOKEN")"
    
上面的登录接口只是测试环境示例，真实系统可以换成 OAuth 授权码流程。测试报告中保存 `sha256(token)` 的前 12 位、用户、客户端、生成时间和 Token 家族 ID，后续查日志时用这些字段关联，避免把完整凭证粘进缺陷单。代码块中的 `trap` 会在当前终端退出时删除临时文件，执行过程中不要把 `$OUT_DIR/login.json` 上传到日志平台。
### 先跑通一条正常刷新链路
登录成功后，测试账号拿到一组凭证。为便于阅读，下面只展示响应结构，不放真实 Token：
    
    HTTP/1.1 200 OK
    Content-Type: application/json
    
    {
      "access_token": "AT-01",
      "refresh_token": "RT-01",
      "token_type": "Bearer",
      "expires_in": 300,
      "scope": "order.read"
    }
    
先用 `AT-01` 访问订单接口，确认登录基线可用：
    
    GET /api/orders HTTP/1.1
    Host: api.example.test
    Authorization: Bearer AT-01
    
Access Token 过期后，接口应返回类似结果：
    
    HTTP/1.1 401 Unauthorized
    WWW-Authenticate: Bearer error="invalid_token", error_description="The access token expired"
    Content-Type: application/json
    
    {"code":"TOKEN_EXPIRED","message":"登录状态已过期"}
    
客户端拿 `RT-01` 请求刷新接口：
    
    POST /auth/refresh HTTP/1.1
    Host: auth.example.test
    Content-Type: application/json
    
    {"refresh_token":"RT-01"}
    
期望得到 `AT-02` 和 `RT-02`。此时先做三次检查：`AT-02` 可以访问原来的订单资源，返回 Scope 仍是 `order.read`，`RT-01` 再次刷新按项目契约失败，或在约定的幂等窗口内只返回同一组结果。只看新 Token 是否返回，无法证明轮换真的生效。
实际执行时，我会把这三次检查固定成一张结果表：

检查| 操作| 通过条件  
---|---|---  
新 Access Token| 用 `AT-02` 请求订单查询| HTTP 200，用户和租户未变化  
新 Refresh Token| 用 `RT-02` 再刷新一次| 成功得到下一代 Token  
旧 Refresh Token| 用 `RT-01` 再刷新一次| 按契约拒绝；若处于幂等窗口，只能返回同一组结果，不能生成第二套凭证  

如果测试只能看到 HTTP 响应，看不到 Token 家族状态，至少在授权服务日志中确认 `RT-01 -> RT-02` 的轮换关系和旧 Token 状态。否则“新 Token 返回成功”仍然可能只是服务端重复签发。
### 过期时间要测边界
#### Access Token 刚过期
测试数据不要只准备一个“已经过期”的 Token。至少准备三组状态：距离过期还有几秒、刚刚过期、过期较长时间。若 Access Token 是 JWT，可以结合 `exp` 和服务端时钟构造边界；若是不透明 Token，则应通过授权服务器或测试管理接口设置状态，不能自行解码或修改内容。请求分别在客户端显示的过期时间和服务端时间附近发出，观察客户端是否只对 `401 invalid_token` 触发一次刷新。
不要用 `sleep(300)` 等待真实过期。测试环境可以把 Access Token 有效期配置成 10 秒，或者调用测试管理接口把指定 Token 标记为 expired，然后立即执行：
    
    ACCESS_TOKEN='AT-EXPIRED'
    
    curl -sS -i "$API_URL/api/orders" \
      -H "Authorization: Bearer $ACCESS_TOKEN"
    
通过条件不是“页面跳到了登录页”，而是同时满足：资源接口返回 `401`；客户端只发起一次刷新；刷新成功后原请求最多重放一次；刷新失败时不再递归调用。可以在 Network 面板按 URL 过滤 `/auth/refresh`，再把请求时间线和服务端日志中的 Token 摘要放在同一条测试记录中。
需要特别检查时钟偏差。客户端根据 JWT 的 `exp` 提前刷新时，提前量过大可能造成无意义的刷新风暴；完全等到服务端返回 401，又可能让页面多一次失败请求。提前量应由项目约定，测试只验证约定值和边界，不自行规定“提前 30 秒一定正确”。
#### Refresh Token 过期
Refresh Token 过期时，刷新接口应终止刷新链路，返回 `401` 或项目约定的认证错误，客户端清理本地凭证并进入重新登录流程。测试需要确认：
  * 页面不会继续循环调用 `/auth/refresh`；
  * 原页面请求不会带着已经失效的 Token 无限重试；
  * 本地 Session、内存缓存和持久化存储中的旧凭证都被清理；
  * 用户看到的是重新登录或会话失效提示，而不是普通业务错误。


执行时不要复用上一条用例已经轮换过的 `RT-01`，那样无法区分“过期”和“已使用”。重新登录得到配套的 `AT-05` 和 `RT-05`，通过测试管理接口同时将 Access Token 和 Refresh Token 设置为过期，再让页面发起一次受保护请求：
    
    curl -sS -i "$AUTH_URL/auth/refresh" \
      -H 'Content-Type: application/json' \
      --data '{"refresh_token":"RT-05"}'
    
随后回到页面执行一次查询，确认客户端只尝试一次刷新，失败后不再拿旧 Access Token 重试。浏览器侧检查 `localStorage`、`sessionStorage`、Cookie 和内存状态；服务端侧检查没有创建新的 Token 家族，也没有写入新的登录 Session。
一个简单的失败重试断言如下：
    
    访问受保护接口 -> 401 invalid_token
            |
            v
    刷新接口 -> 401 invalid_grant
            |
            v
    清理凭证 -> 跳转登录页
    
如果刷新接口本身返回 500、超时或网络断开，不能直接按“Refresh Token 失效”处理。客户端可以按项目约定有限重试，但重试次数、退避时间和是否保留当前页面状态都要有明确边界。
### 轮换机制要验证旧 Token 的命运
单次刷新成功后，拿旧的 `RT-01` 再发一次请求：
    
    POST /auth/refresh HTTP/1.1
    Host: auth.example.test
    Content-Type: application/json
    
    {"refresh_token":"RT-01"}
    
在本文契约下，服务端应拒绝请求，并返回项目约定的重放错误，例如：
    
    {
      "error": "invalid_grant",
      "error_description": "refresh token reuse detected"
    }
    
随后检查 Token 家族状态。`RT-02` 是否也被撤销，取决于项目对重放的处置约定；本文假设检测到重放后撤销整个家族，要求重新登录。对真实客户端来说，网络重试和多请求并发也可能制造“看起来像重放”的请求，因此应优先用客户端刷新锁降低误报，再按服务端契约验证是否有短暂幂等窗口或家族撤销。测试报告不能只写“接口返回 400”，还要记录 `RT-02` 是否还能继续刷新，以及审计日志是否留下重放事件。
如果服务端采用不轮换模式，旧 Refresh Token 可能在有效期内重复使用，但必须验证它是否绑定客户端、用户、Scope 和资源，是否有明确撤销入口。两种模式的预期不能混写在同一条用例中。
### 并发刷新：先区分服务端和客户端问题
并发刷新经常被描述成“两个请求，一个成功，一个失败”，这句话不够完整。服务端需要保证旧 Refresh Token 的消费具有原子性；客户端还要保证多个业务请求共享同一个刷新结果，不因失败响应把刚保存的新凭证清掉。
#### 服务端并发消费
重新登录拿到一枚未使用的 `RT-03`，同时发出两个刷新请求：
    
    set -eu
    
    REFRESH_URL='https://auth.example.test/auth/refresh'
    BODY='{"refresh_token":"RT-03"}'
    OUT_DIR="$(mktemp -d)"
    trap 'rm -rf "$OUT_DIR"' EXIT
    
    for name in a b; do
      curl -sS "$REFRESH_URL" \
        -H 'Content-Type: application/json' \
        --data "$BODY" \
        -o "$OUT_DIR/response-$name.json" \
        -w "$name: %{http_code}\n" &
    done
    wait
    
    for file in "$OUT_DIR"/*.json; do
      jq '{error, access_token, refresh_token, scope}' "$file"
    done
    
在本文的轮换策略下，预期是一个请求成功，得到一组新凭证；另一个请求被识别为重复使用。两条请求的服务端日志应能关联到同一个 Refresh Token 摘要，数据库或缓存中不能出现两个都有效的后继 Token。若服务端对极短并发窗口提供幂等处理，也可以都返回同一组结果，但必须在测试契约中写明窗口和结果，不应与重放检测混用。
这个命令只能验证一次并发结果，不能证明高并发性能。还应增加不同到达顺序、网络延迟和多个用户同时刷新等场景，并检查失败请求是否错误地撤销了另一个用户或其他 Token 家族。
并发用例执行完后，按下面顺序查结果，避免只看终端里谁返回了 200：
  1. 记录两个响应中的 Access Token 和 Refresh Token 摘要，确认是否相同或属于同一代。
  2. 查询 Token 家族，确认最多只有一条后继凭证处于有效状态。
  3. 用成功响应中的新 Access Token 访问订单接口，确认用户、租户和 Scope 不变。
  4. 用失败响应中可能返回的 Token 再访问 API，确认不会得到另一套有效会话。
  5. 查看审计日志，确认重复使用事件只归属于当前用户和当前 Token 家族。


#### 客户端刷新锁
假设页面同时有 10 个 API 请求发现 `AT-01` 过期。如果每个请求都直接调用刷新接口，就会争抢同一枚 Refresh Token。客户端应把刷新过程放到共享 Promise、互斥锁或等价机制中：第一个请求负责刷新，其他请求等待结果，然后统一使用新 Access Token 重放原业务请求。
可以从浏览器 Network 面板检查以下事实：
  * 10 个业务请求只触发一次刷新请求；
  * 刷新成功后，等待中的业务请求都使用同一个新 Access Token；
  * 刷新失败后，所有等待请求结束，不再继续递归刷新；
  * 用户点击退出时，等待中的请求不能在退出完成后重新写入登录状态。


如果 Access Token 由前端保存，手工执行可以这样做：在浏览器 DevTools 的 Application 面板把 Access Token 替换为已过期值，打开 Network 保留日志，然后快速刷新一个同时发起多个接口请求的页面。导出 HAR 后统计 `/auth/refresh` 数量，再检查每个重放请求的 `Authorization` 是否使用同一枚新 Token。测试报告应附请求时间线，而不是只写“并发刷新正常”。
如果系统采用 BFF 或 HttpOnly Cookie，Application 面板无法读取或替换 Token。此时通过测试管理接口让服务端 Session 对应的 Access Token 过期，或在测试代理中注入一次 401，再重复相同操作；重点检查服务端刷新请求数量、Session 状态和后续业务请求，不要强行要求前端出现 `Authorization` 请求头。
如果要验证竞态，给刷新接口增加测试环境延迟：让第一个刷新请求停留 500 毫秒，期间点击退出或关闭页面。通过条件是刷新 Promise 最终被清理，响应回来后不会重新写入 Token，也不会把页面恢复成已登录状态。
如果产品允许服务端“短时间内同一 Refresh Token 返回同一刷新结果”，则并发请求可能都成功，但必须明确幂等窗口、响应中的 Refresh Token 是否相同，以及重放窗口结束后的行为。测试人员应按服务端契约判定，不能把某一种并发策略当成行业唯一答案。
### 权限不能在刷新时悄悄扩大
登录用户只有 `order.read` 权限时，用 Refresh Token 换出的新 Access Token 仍应只能访问订单查询接口。直接调用取消接口，预期是 `403` 和 `insufficient_scope` 或项目约定的等价错误，订单状态、库存和取消消息都不能变化。
刷新请求中如果允许传 `scope` 或 `resource` 参数，要分别测试扩大、缩小、删除和伪造其他资源的情况：
    
    POST /auth/refresh HTTP/1.1
    Content-Type: application/x-www-form-urlencoded
    
    grant_type=refresh_token&refresh_token=RT-03&scope=order.write&resource=admin-api
    
服务端应按授权服务器策略拒绝非法扩大，或返回不超过原授权范围的结果。不能因为刷新接口返回 200，就默认权限正确；需要解析返回 Scope，并用新 Token 调用资源 API 验证真实权限。
还要验证客户端绑定。把 A 客户端得到的 Refresh Token 送给 B 客户端，或者替换 `client_id`，服务端都不应发放新凭证。机密客户端的认证信息只能留在服务端，不能出现在浏览器脚本、URL 或普通日志中。
### 注销要拆成三件事
注销至少涉及本地 Session、Refresh Token 和 Access Token。很多实现只删除 Cookie，导致用户界面看起来退出了，旧 Token 仍可以继续访问接口。
我会按下面顺序执行，并分别记录结果：
  1. 登录同一账号，保存当前 Session、`AT-04` 和 `RT-04` 的安全摘要。
  2. 调用 `/auth/logout`，检查响应、Cookie 和服务端撤销记录。
  3. 用原 Session 访问页面，确认本地会话状态。
  4. 用 `RT-04` 调用刷新接口，确认不能再换取新凭证。
  5. 用 `AT-04` 调用资源接口，按项目策略确认立即失效或在短有效期内失效。
  6. 在另一台设备保留同一账号会话，确认“退出当前设备”和“退出全部设备”的影响范围不同。


注销接口示例：
    
    POST /auth/logout HTTP/1.1
    Host: auth.example.test
    Cookie: session=SESSION-04
    Content-Type: application/json
    
    {}
    
刷新 Token 被撤销后，服务端通常返回 `invalid_grant` 或等价错误。撤销接口即使返回 200，也不能只凭这个状态判断成功；RFC 7009 允许对无效 Token 返回成功，以避免暴露 Token 是否存在。还要再次使用原 Refresh Token 刷新，并检查撤销记录和审计事件。
Access Token 的处理取决于实现。服务端可以维护黑名单或主动查询状态，也可以让短生命周期 JWT 自然过期。测试报告应写清楚实际策略和时间窗口，例如“注销后 Refresh Token 立即不可刷新，Access Token 在剩余有效期内仍可读接口”，不要把所有系统都强行判定为立即 401。
如果注销依赖 Cookie Session，还要补一条跨站请求检查：从不同 Origin 发起注销请求，验证服务端是否按项目要求校验 CSRF Token、`Origin`/`Referer` 和 Cookie 的 `SameSite` 属性。没有 CSRF 防护时，第三方页面可能诱导用户被动退出；是否阻断请求要按项目安全策略记录，不要只看注销接口是否返回 200。
这条用例建议保留两份结果：一份是浏览器结果，一份是直接调用 API 的结果。浏览器退出成功只能说明当前页面清理了状态，不能证明服务端已经撤销凭证。直接调用 API 时，分别使用旧 Session、旧 Refresh Token 和旧 Access Token，并把响应时间记下来：
    
    curl -sS -i "$AUTH_URL/auth/refresh" \
      -H 'Content-Type: application/json' \
      --data '{"refresh_token":"RT-04"}'
    
    curl -sS -i "$API_URL/api/orders" \
      -H 'Authorization: Bearer AT-04'
    
如果产品提供“退出全部设备”，再用设备 B 的旧凭证重复这两次请求。若只提供“退出当前设备”，设备 B 仍能使用属于它的 Session，不能误报为注销失败。
最后检查凭证存储位置：前端持有 Refresh Token 时，确认它没有出现在 URL、HAR、错误日志、埋点和可被业务脚本随意读取的存储中；采用 Cookie 时，检查 `HttpOnly`、`Secure`、`SameSite` 和过期时间是否符合项目策略。BFF 场景则检查浏览器只保留 Session Cookie，Refresh Token 不下发到前端。
### 把结果整理成回归用例
下面这组用例覆盖认证生命周期的主要风险，接口名称和错误码需要替换成项目实际定义：

用例| 操作| 关键预期  
---|---|---  
Access Token 过期| 用过期 Token 访问 API| 返回 401，客户端只触发一次刷新  
Refresh Token 过期| 用过期 Refresh Token 刷新| 刷新失败，清理凭证并进入登录流程  
正常轮换| 用旧 Token 刷新一次| 得到新 Token，旧 Token 不能再次使用  
并发刷新| 两个请求同时消费同一旧 Token| 按项目策略保证原子性，不产生两套都有效的后继凭证  
客户端刷新协调| 多个 API 同时遇到 401| 刷新请求受控，业务请求等待同一结果  
刷新权限边界| 用低权限 Refresh Token 换取新 Token| Scope 和资源不扩大  
当前设备注销| 注销后重用 Session 和 Refresh Token| 本地会话结束，旧 Refresh Token 不能刷新  
退出全部设备| 其他设备继续使用旧凭证| 影响范围符合产品约定  
刷新接口超时| 服务端可能已处理但响应丢失| 不无限重试，最终状态符合约定  

用例执行时，优先检查三类副作用：是否生成了多套有效凭证，是否错误扩大了权限，是否在注销后重新建立了会话。返回码只是线索，Token 家族状态、审计记录和业务接口结果才是完整证据。
### 总结
Token 刷新测试要贯穿“过期、换新、并发、撤销”这条生命周期。Access Token 失效时，客户端要能有限刷新；Refresh Token 轮换时，服务端要能识别重复使用；多个请求同时触发刷新时，客户端要复用同一个结果；注销完成后，Session、Refresh Token 和 Access Token 的失效范围要符合明确策略。
把这些规则写进测试契约，再用一枚测试 Token 的状态变化串起接口、日志和业务结果，才能定位问题发生在服务端原子性、客户端并发协调，还是注销策略本身。
