# [测试技术] Apollo配置测试：灰度、断网与回滚

> 原文: https://blog.csdn.net/weixin_42390585/article/details/163459980

> 原创内容，未获授权禁止转载、转发、抄袭。

Apollo 页面显示发布成功，只能证明服务端生成了新的配置版本。客户端是否收到、应用是否接受、业务行为是否改变，仍是三件不同的事。只检查 Portal 状态，很容易漏掉实例配置不一致、非法值生效、灰度范围错误和回滚不彻底。
本文用 `order.timeout.seconds` 说明 Apollo 配置应该怎么测。测试重点不是页面操作，而是怎样建立证据链、制造故障并判断配置是否真正生效。
示例中，Apollo 服务端最新正式版为 2.5.2，Apollo Java Client 最新正式版为 2.5.0。文中的 Java 探针已在 Java 8 下编译通过；本文未运行完整 Apollo 集群，因此不虚构推送耗时和发布结果，时间阈值需要在实际测试环境中采集。
### 先区分四种“成功”
一次配置变更至少经过四层：

层级| 可观察证据| 不能替代的结论  
---|---|---  
Portal| 发布人、Release、Diff、发布时间| 客户端已经收到  
Apollo Client| 变化事件、本地缓存、实例使用的版本| 应用已经采用  
应用| 解析结果、有效值、资源重建结果| 业务行为已经改变  
业务| 超时、限流、路由等真实结果| 其他实例也已经一致  

例如，配置从 300 秒改成 60 秒后，客户端可能已经拿到字符串 `60`，但应用仍持有启动时绑定的 300；也可能某个实例收到 `abc` 后解析失败，却把旧值清空。测试必须同时记录原始值和业务有效值。
建议为每次发布保留以下信息：
  * `AppId、Environment、Cluster、Namespace`；
  * Release ID 或 ReleaseKey、发布类型、发布人和发布时间；
  * 实例 ID、IP、Label 和配置变化接收时间；
  * 配置旧值、新值、应用有效值和生效时间；
  * 业务请求的 `traceId`、命中实例和实际行为。


Release 信息可以从发布历史或 Webhook 获取，实例列表可辅助判断客户端使用的版本。但实例列表仍不能替代业务断言，因为它看不到应用是否正确解析并采用了配置。
### 给配置增加一个可测试的生效探针
业务配置不能只写成 `@Value` 后就不再观察。下面的类通过 Apollo `Config` 读取原始值，监听变化，并且只接受 30 至 1800 秒之间的整数。非法配置会被拒绝，业务继续使用最后一个合法值。
    
    package example;
    
    import com.ctrip.framework.apollo.Config;
    import com.ctrip.framework.apollo.ConfigService;
    import com.ctrip.framework.apollo.model.ConfigChange;
    import java.util.concurrent.atomic.AtomicInteger;
    import java.util.logging.Logger;
    
    public final class OrderTimeoutConfig {
      private static final Logger LOG = Logger.getLogger(OrderTimeoutConfig.class.getName());
      private static final String KEY = "order.timeout.seconds";
      private static final int DEFAULT_VALUE = 300;
      private static final int MIN_VALUE = 30;
      private static final int MAX_VALUE = 1800;
    
      private final Config config = ConfigService.getAppConfig();
      private final AtomicInteger effectiveValue = new AtomicInteger(DEFAULT_VALUE);
    
      public OrderTimeoutConfig() {
        String initial = rawValue();
        if (initial != null && parse(initial) == null) {
          LOG.warning("reject invalid config key=" + KEY);
        }
        config.addChangeListener(event -> {
          if (event.isChanged(KEY)) {
            ConfigChange change = event.getChange(KEY);
            if (parse(change.getNewValue()) == null) {
              LOG.warning("reject invalid config key=" + KEY);
            }
          }
        });
      }
    
      private Integer parse(String candidate) {
        try {
          int parsed = Integer.parseInt(candidate);
          if (parsed < MIN_VALUE || parsed > MAX_VALUE) {
            return null;
          }
          return parsed;
        } catch (NumberFormatException exception) {
          return null;
        }
      }
    
      public String rawValue() {
        return config.getProperty(KEY, null);
      }
    
      public int effectiveValue() {
        Integer parsed = parse(rawValue());
        if (parsed != null) {
          effectiveValue.set(parsed);
        }
        return effectiveValue.get();
      }
    }
    
测试环境可以提供一个受保护的内部探针，返回结构至少包含：
    
    {
      "instanceId": "order-a",
      "namespace": "application",
      "rawValue": "60",
      "effectiveValue": 60
    }
    
`rawValue` 表示 Apollo Client 当前内存中的原始配置，`effectiveValue` 表示业务真正使用的值。生产环境不能提供任意 Key 查询，也不能返回密码、Token 等敏感配置；探针需要鉴权，并限制允许查看的字段。
示例中的 `effectiveValue()` 会在每次业务读取时重新校验客户端内存值，避免初始化与配置发布并发时漏掉有效更新；变化监听器用于尽快发现并告警非法值。资源型配置不能只返回一个数值，还需要在监听器中完成资源切换并记录结果。
如果项目使用 `@ConfigurationProperties`，还要特别验证动态刷新。Apollo 官方文档明确说明，它需要配合 `EnvironmentChangeEvent` 或 `RefreshScope` 才能在配置变化时更新绑定对象。客户端内存已经变化，不代表 Bean 中的字段也会自动变化。对于连接池、线程池等资源型配置，还要断言旧资源是否平滑关闭、新资源是否创建成功。
### 正常发布要检查所有实例
准备两个相同版本的订单实例：

实例| Label| 初始值  
---|---|---  
`order-a`| `canary`| 300  
`order-b`| `stable`| 300  

把 `order.timeout.seconds` 从 300 发布为 60，批量查询两个实例的探针：
    
    for host in order-a.test order-b.test; do
      curl --fail --silent --show-error \
        -H "Authorization: Bearer ${PROBE_TOKEN}" \
        "https://${host}/internal/config-probe/order-timeout"
    done
    
探针必须直连具体实例，或在响应中返回可信的实例 ID。若仍通过普通负载均衡入口访问，多次请求可能重复落到同一台机器，不能据此证明所有实例已经生效。
完整断言应包括：
  * 发布历史中产生了新 Release，Diff 为 `300 -> 60`；
  * 两个实例最终都满足 `rawValue=60、effectiveValue=60`；
  * 配置变化日志包含实例、Namespace、Key 和接收时间，但不记录敏感值；
  * 使用该配置的订单超时逻辑确实按 60 秒执行；
  * 从 Portal 发布时间到各实例业务生效时间均未超过约定阈值；
  * 发布窗口结束后，不再存在长期使用 300 的实例。


Apollo Java Client 使用 HTTP Long Polling 感知配置变化；没有变化时，服务端挂起请求并在约 60 秒后返回 304。客户端还会默认每 5 分钟定时拉取，作为通知链路失效时的兜底。测试阈值应根据环境实测制定，不要机械断言“所有实例必须 1 秒生效”。
### 非法配置要验证“拒绝后仍可用”
Apollo 管理的是配置版本，不知道订单超时时间的业务范围。测试时分别发布：
    
    order.timeout.seconds=abc
    order.timeout.seconds=-1
    order.timeout.seconds=3600
    
基于前面的监听器，三次发布都应被应用拒绝。此时需要断言：
  * `rawValue` 已变为新值，证明客户端确实收到配置；
  * `effectiveValue` 保持上一个合法值 60；
  * 应用没有因为解析异常退出，订单请求仍可处理；
  * 产生包含 AppId、实例和 Key 的告警，但日志不打印敏感 Value；
  * Portal 发布记录仍然存在，不能把“应用拒绝”误判成“配置没有发布”。


还要测试删除 Key。删除事件的新值可能为空，应用应明确选择保留旧值、恢复默认值还是拒绝变更。这个策略必须写进需求，不能由 `getProperty()` 的默认值偶然决定。
非法值测试完成后，应重新发布一个合法值，避免后续断网测试把非法配置写进本地缓存，导致场景互相污染。
### 断开通知链路，验证最终追平
只阻断 `order-a` 到所有 Config Service 的网络，保持 `order-b` 正常，再把配置从 60 发布为 120。不要同时停止 Portal、Admin Service 和数据库，否则无法判断问题出在发布还是客户端拉取。
故障期间预期形成明确分层：

证据| `order-a`| `order-b`  
---|---|---  
Portal Release| 120| 120  
Client 原始值| 60| 120  
业务有效值| 60| 120  
订单行为| 仍按 60 秒| 按 120 秒  

恢复网络后，持续观察 `order-a`，断言它无需重启即可追平到 120，同时记录恢复耗时。若只破坏 Long Polling、仍保留普通配置拉取链路，则还应验证默认 5 分钟的定时拉取能否兜底；若所有 Config Service 通路都被阻断，定时拉取也无法获得新配置。
这里容易出现一个错误结论：断网实例仍能正常处理订单，并不代表容灾测试通过。它只能证明旧配置仍可用，还要检查恢复后是否追平，以及业务是否允许故障窗口内多个实例使用不同值。
客户端链路验证完成后，在多节点测试环境中再分别注入服务端组件故障：

故障| 重点断言  
---|---  
停止一台 Config Service| 客户端重连其他节点，发布和拉取仍可完成  
停止全部 Config Service| 客户端不能获取新配置，但已有内存值不应被清空  
停止全部 Admin Service| Portal 不能更新配置，运行中的客户端仍使用已有配置  
数据库不可用| Portal 不能更新；Config Service 开启缓存时验证已有配置读取不受影响  

这些场景应逐个执行，并在每次实验后恢复环境。否则多个故障叠加后，只能看到“配置不更新”，无法确定是哪一段链路失效。
### 本地缓存要区分老实例和新实例
Java Client 会把服务端配置写入本地文件，默认路径为：
    
    Mac/Linux: /opt/data/{appId}/config-cache
    Windows:   C:\opt\data\{appId}\config-cache
    
在 Config Service 不可用时，至少测试三种启动方式：
  1. 已运行过且缓存中保存合法值 120 的实例重启，应能从缓存恢复。
  2. 全新实例没有本地缓存，验证它是使用应用默认值、启动失败还是按约定阻止接流量。
  3. 缓存目录不可写、文件损坏或权限错误，验证告警、启动策略和业务值。


不要把其他机器的缓存文件随意复制到新实例。官方文档将其作为全量 Config Service 故障时扩容的容灾方式，但测试必须先核对文件名中的 `appId、cluster、namespace`，再用内容摘要和修改时间确认它对应预期配置，防止把其他环境或旧内容带入生产。
本地缓存保存的是 Apollo 原始配置，不是应用最后一个合法业务值。如果客户端曾缓存非法值，应用重启后仍可能再次拒绝该值并退回默认值。因此，非法配置拒绝策略还要覆盖重启场景，必要时单独持久化最后一个合法业务配置。
### 灰度发布要验证目标和非目标实例
将主版本保持为 60，为 `order-a` 设置 `-Dapollo.label=canary`，只对 Label 为 `canary` 的实例灰度发布 120：

实例| 期望原始值| 期望有效值  
---|---|---  
`order-a`| 120| 120  
`order-b`| 60| 60  

灰度测试不能只看目标实例变成 120，还要证明非目标实例仍为 60。建议覆盖：
  * IP 规则只命中指定 IP；
  * Label 规则只命中指定 Label；
  * Kubernetes Pod IP 变化后，Label 灰度仍能稳定命中；
  * 不存在的 IP 或 Label 不应误伤其他实例；
  * 公共 Namespace 灰度时，先限定目标 AppId；
  * 修改灰度规则后，目标范围能够实时变化；
  * 全量发布后所有实例使用主版本，灰度分支按选择保留或删除。


Apollo 2.0.0 起支持按 Label 灰度，适合 IP 不固定的 Kubernetes 场景。灰度规则修改本身会实时生效，不需要再次发布配置，因此规则变更也要纳入审计和回归，不能只关注“灰度发布”按钮。
### 回滚不等于把编辑区也恢复
准备两个已发布版本：
    
    R1: order.timeout.seconds=300
    R2: order.timeout.seconds=60
    
在 Portal 编辑区把值改成 90，但不要发布，然后对 R2 执行回滚。Apollo 的回滚会让客户端恢复到上一个已发布版本，因此应用应回到 300；编辑区中未发布的 90 不会被回滚。
测试应同时检查：
  * 发布历史新增回滚记录，操作人与目标版本正确；
  * 所有实例的 `rawValue` 和 `effectiveValue` 最终恢复为 300；
  * 订单业务行为也恢复为 300，而不是只检查监听日志；
  * Portal 编辑区仍保留 90，下一次发布前必须重新检查 Diff；
  * 连续回滚、灰度版本放弃和全量发布后的回滚符合预期。


如果只检查客户端变成 300，却忽略编辑区仍为 90，下一次发布很可能再次把问题配置带回来。
### 配置维度和权限也要测
很多“发布后不生效”并非通知失败，而是实例读取了错误维度。至少核对：
  * `app.id` 是否对应目标应用；
  * `env` 是否指向正确环境；
  * `apollo.cluster` 大小写和取值是否正确；
  * Namespace 是否被客户端加载；
  * 多个 Namespace 存在同名 Key 时，优先级是否符合设计；
  * 灰度 Label 是否随实例启动参数正确传入。


权限测试要区分编辑和发布。仅有编辑权限的用户不能让配置对客户端生效；生产环境应验证发布权限、审核流程、回滚权限和操作审计。敏感配置还应检查 Portal 查看权限、Webhook 内容、客户端缓存文件权限和日志脱敏，不能只保护数据库中的值。
### 一套最小回归集

场景| 故障或输入| 核心断言  
---|---|---  
正常发布| 300 改为 60| 所有实例原始值、有效值和业务行为一致  
非法类型| 发布 `abc`| 客户端收到，应用拒绝并保留合法值  
越界值| 发布 `-1`、`3600`| 不生效、有告警、服务不中断  
删除配置| 删除 Key| 按约定保留旧值、使用默认值或拒绝  
单实例断网| 阻断一个实例到 Config Service| 正常实例更新，故障实例保持旧值  
网络恢复| 恢复 Config Service 通路| 故障实例无需重启即可追平  
缓存启动| Config Service 不可用时重启| 有缓存实例按策略启动，版本可解释  
全新扩容| 无缓存且 Config Service 不可用| 不误用其他环境配置，接流策略明确  
Label 灰度| 仅命中 `canary`| 目标实例更新，非目标实例不变  
灰度转全量| 将灰度合并到主版本| 所有实例最终一致，分支状态正确  
配置回滚| R2 回滚到 R1| 客户端和业务回到 R1，编辑区不误判  
维度错误| 错 AppId、环境、Cluster、Namespace| 能定位读取来源，不把问题归因于推送  
动态绑定| `@ConfigurationProperties` 持有旧值| 刷新机制生效，Bean 与 Client 值一致  
权限越权| 编辑者尝试发布或回滚| 操作被拒绝并留下审计记录  

### 总结
Apollo 配置测试的重点不是“页面能否发布”，而是配置从 Release、客户端内存、应用有效值到业务行为的整条链路是否一致。测试时先建立原始值和有效值探针，再通过非法值、断网、缓存启动、灰度规则和回滚主动制造差异。
真正需要回答的是三个问题：哪些实例收到了哪个版本，应用最终采用了什么值，故障恢复后所有实例能否重新一致。把这三点测清楚，配置变更才具备可验证、可灰度和可回滚的基础。
