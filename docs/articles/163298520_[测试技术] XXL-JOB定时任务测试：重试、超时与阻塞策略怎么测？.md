# [测试技术] XXL-JOB定时任务测试：重试、超时与阻塞策略怎么测？

> 原文: https://blog.csdn.net/weixin_42390585/article/details/163298520

> 原创内容，未获授权禁止转载、转发、抄袭。

定时任务出现重复结算、重复发券时，很多人会先检查 Cron 是否配错。但在 XXL-JOB 中，失败重试、阻塞策略、超时中断和结果回调都可能让“一个计划周期”对应多次业务执行。
测试时不能只看调度中心的成功或失败，还要核对执行次数、业务数据和错误副作用。本文以“每日结算”任务为例，说明重复执行和漏执行应该怎样验证。
### 先分清四个阶段
一次任务不是只有“运行”一个动作，而是经过四个阶段：
    
    生成调度 -> 向执行器发送触发请求 -> 执行业务代码 -> 回调调度中心
    
现象| 能够证明什么| 不能证明什么  
---|---|---  
调度成功| 触发请求被执行器接收| 业务已经成功  
执行失败| 执行器回传失败结果| 业务数据一定没有写入  
日志长时间“运行中”| 调度中心尚未收到有效回调| 执行器仍在运行  
重试成功| 后续一次执行成功| 前一次没有产生副作用  

因此，测试证据至少要包含三部分：XXL-JOB 调度日志、执行器日志和最终业务数据。
### 给每次执行留下可追踪信息
调度日志 ID 只能标识某次触发，不能当作业务幂等键。失败重试会再次触发任务，产生新的执行记录；对“2026-07-29 的每日结算”来说，业务键应使用结算日期和账户 ID。
XXL-JOB 的任务参数通常是配置值，不会自动变成当次调度日期。自动调度应按业务日历解析待处理账期，人工补数时再显式传入目标日期；不要简单使用执行器的当前日期，否则延迟执行可能处理错账期。
在执行器日志中同时记录业务键和 `logId`：
    
    String requestedDate = XxlJobHelper.getJobParam();
    LocalDate settleDate = settlementDateResolver.resolve(requestedDate);
    long logId = XxlJobHelper.getLogId();
    
    XxlJobHelper.log(
        "dailySettlement start, settleDate={}, logId={}",
        settleDate,
        logId
    );
    
业务表使用唯一约束阻止同一账户、同一日期重复结算：
    
    CREATE TABLE settlement_result (
        id           BIGINT       NOT NULL AUTO_INCREMENT,
        account_id   BIGINT       NOT NULL,
        settle_date  DATE         NOT NULL,
        amount       DECIMAL(18,2) NOT NULL,
        created_at   DATETIME     NOT NULL,
        PRIMARY KEY (id),
        UNIQUE KEY uk_account_date (account_id, settle_date)
    );
    
唯一约束是最后一道防线，但它只能保护这张数据库表。如果任务还会发消息、发券或调用支付接口，下游也必须使用稳定的业务幂等键，或通过本地消息表等方式处理数据库与外部副作用的一致性。
### 失败重试：专门在业务提交后报错
最容易发现重复数据的场景，不是任务一开始就抛异常，而是业务数据已经提交，但执行器最终返回失败。
可以将失败重试次数设置为 `1`，然后在测试环境注入一次“提交后异常”：
    
    // 测试专用故障注入伪代码
    settlementService.commit(settleDate);
    
    if (failPoint.hitOnce("after-settlement-commit", settleDate)) {
        throw new IllegalStateException("injected failure after commit");
    }
    
`hitOnce` 必须在集群内全局只命中一次。可以用 Redis 或数据库原子记录故障状态，也可在该测试中使用固定路由，确保首次执行和重试落在同一执行器。如果故障点只保存在本地内存中，重试切换节点后可能再次命中，导致测试结果失真。
触发一次任务后，不要只断言“最后重试成功”，而要同时检查：
  * 首次执行在业务提交后失败，后续发生一次重试。
  * 同一业务键的执行器日志出现两次，`logId` 不同。
  * `settlement_result` 中每个账户仍只有一条结算结果。
  * 不会重复发送消息、发券或调用外部接口。


检查重复数据可以使用：
    
    SELECT account_id, settle_date, COUNT(*) AS row_count
    FROM settlement_result
    GROUP BY account_id, settle_date
    HAVING COUNT(*) > 1;
    
查询结果应为空。如果数据库唯一约束直接抛错，还要检查任务是否把“已处理”识别为幂等命中，而不是继续返回失败并消耗全部重试次数。
只查重复数据还不够。对批量结算任务，应在执行前保存本账期应处理的账户快照，然后在处理到第 N 个账户时终止执行器。恢复并重试后，用反连接查找漏处理账户：
    
    SELECT expected.account_id
    FROM settlement_test_snapshot AS expected
    LEFT JOIN settlement_result AS actual
        ON actual.account_id = expected.account_id
       AND actual.settle_date = expected.settle_date
    WHERE expected.test_run_id = 'CASE-001'
      AND actual.id IS NULL;
    
查询结果应为空，同时还要比对预期与实际的账户集合、记录总数、结算总金额和状态分布。这组断言才能证明任务不仅没有重复，也没有因中途失败而漏处理。
外部副作用也要有独立证据：使用 Outbox 时，按业务幂等键断言只有一条事件记录；调用券或支付接口时，使用 Mock Server 记录请求，核对同一业务键的请求次数、请求体和最终结果。
### 阻塞策略：测的不只是页面选项
将任务执行时间设为 20 秒，调度间隔设为 5 秒，可以稳定制造调度重叠。三种阻塞策略的断言不同：

阻塞策略| 应观察的行为| 容易忽略的风险  
---|---|---  
单机串行 `SERIAL_EXECUTION`| 同一执行器上不并发，后续请求进入 FIFO 队列| 任务会积压，且不限制不同执行器之间的并发  
丢弃后续调度 `DISCARD_LATER`| 运行中收到的新请求被拒绝并标记失败| 开启失败重试后，被丢弃的调度可能稍后又被重试  
覆盖之前调度 `COVER_EARLY`| 旧任务被中断、队列被清空，再执行新任务| 业务代码忽略中断时，新旧任务可能仍然并发产生副作用  

“单机串行”的作用域是单个执行器。执行器集群使用轮询或随机路由时，同一任务可能在不同机器上同时执行。因此，阻塞策略不能代替业务幂等。
### 超时中断：失败不等于已经停止
XXL-JOB 3.4.2 的任务超时依赖线程 `interrupt`。如果业务代码捕获 `InterruptedException` 后继续执行，或长时间做不响应中断的计算，调度日志虽然已经超时，业务线程却可能继续运行。
测试时可将超时时间设为 5 秒，任务内注入 15 秒阻塞，并分别验证：
  * 达到 5 秒超时阈值后，调度日志记录超时失败。
  * 业务代码能感知中断并尽快退出。
  * 超时之后不再写入数据库或调用外部服务。
  * 已经提交的副作用不会因线程中断自动回滚，后续重试仍然幂等。


下面这种处理会吞掉中断信号，应该被测试发现：
    
    try {
        Thread.sleep(15_000);
    } catch (InterruptedException ignored) {
        // 错误：忽略中断后继续写入业务数据
    }
    settlementService.commit(settleDate);
    
正确做法是尽快结束当前处理，必要时恢复中断标记并向上抛出异常。不过，这仍不能撤销中断前已经完成的外部操作。
### 补偿、故障转移和回调也要单独测
除了业务代码报错，调度中心和执行器故障也会改变执行次数。
**调度过期**
在 3.4.2 的调度实现中，错过触发时间超过 5 秒才进入过期策略。集群环境需要停止全部调度中心实例，跨过多个触发周期后再启动，分别验证：
  * `DO_NOTHING`：忽略过期调度，从当前时间计算下次触发。
  * `FIRE_ONCE_NOW`：立即补偿一次，而不是把停机期间每个错过的周期全部重放。


不能只检查任务后续恢复调度，还要按业务规则确认被忽略的周期是否需要另行补数。
**故障转移**
`FAILOVER` 发生在触发阶段：调度中心按顺序做心跳检测，将请求发给第一个存活的执行器。这不能解决“执行器已经接收请求，但响应在网络中丢失”的不确定性，此时调度中心和执行器对结果的认知可能不一致。
测试时应在触发请求到达后中断响应链路，再核对业务结果、调度日志和后续重试，而不是只停掉一台执行器验证路由切换。
**结果回调丢失**
执行器完成业务后通过回调通知调度中心。短暂回调失败会写入执行器本地失败回调文件，并在后续重试；持续失败则可能让日志长期停留在“运行中”。3.4.2 的调度中心会在记录超过 10 分钟且对应执行器已不在线时，将其标记为失败。
这里要分成两条用例：短暂中断回调后恢复网络，断言本地回调重试成功且调度日志最终更新；持续屏蔽回调并使执行器下线，断言业务已成功但调度日志最终失败。如果配置了失败重试，两种情况都要核对是否出现额外触发，并确认业务幂等。
### 一组可落地的回归场景

场景| 故障注入| 核心断言  
---|---|---  
正常调度| 无| 计划时间内触发一次，业务结果正确  
人工重复触发| 首次完成后再手动执行一次| 产生两次执行记录，业务副作用只生效一次  
提交后失败| 写库成功后抛异常| 发生重试，无重复数据和外部副作用  
批处理中断| 处理到第 N 个账户时终止执行器| 重试后预期账户集合无重复、无缺失  
任务重叠| 20 秒任务每 5 秒调度| 行为符合选定阻塞策略，无意外并发  
任务超时| 5 秒超时、15 秒阻塞| 中断后不再产生新的业务副作用  
调度中心重启| 停机跨过多个周期| 补偿次数符合 `DO_NOTHING` 或 `FIRE_ONCE_NOW`  
执行器下线| 停止首个执行器| `FAILOVER` 选择存活节点，业务结果正确  
触发响应丢失| 执行器接收后中断响应| 日志与业务结果分别可观测，重试不造成重复  
短暂回调中断| 屏蔽回调后恢复网络| 本地回调重试成功，日志最终更新  
持续回调丢失| 持续屏蔽回调并使执行器下线| 业务成功不会被日志状态掩盖，后续重试仍幂等  

测试结果不应只记录“调度成功率”。至少还要统计同一业务键的执行次数、重复副作用数、未完成业务数和最长恢复时间。
### 测试边界
  * 本文验证思路面向 XXL-JOB 3.4.2，其他版本需要重新核对调度、超时和回调实现。
  * 调度时间精度测试应使用时间区间而非某个精确毫秒，并保证调度中心、数据库和执行器时钟同步。
  * 故障注入只能在隔离的测试环境执行，测试任务不得发送真实短信、发券、扣款或操作生产数据。
  * 任务幂等需要在业务层落地，路由和阻塞策略只能降低重复概率，不能提供严格的“仅执行一次”保证。


### 总结
XXL-JOB 测试的核心不是确认 Cron 会触发，而是验证任务在重试、超时、重叠和网络故障下仍然不重复、不漏处理。只有把调度日志、执行日志和业务结果串起来，才能判断任务是否真正可靠。
