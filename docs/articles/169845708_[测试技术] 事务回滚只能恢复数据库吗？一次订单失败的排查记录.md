# [测试技术] 事务回滚只能恢复数据库吗？一次订单失败的排查记录

> 原文: https://blog.csdn.net/weixin_42390585/article/details/169845708

> 原创内容，未获授权禁止转载、转发、抄袭。

在一个可复现的测试场景中，订单已经写入数据库，服务却在事务提交前失败。接口返回了 500，订单表里最后没有这条记录，但库存少了一件；在另一条故障路径里，消息队列还出现了“订单已创建”的事件。这个结果看起来矛盾，实际上每个系统都按自己的规则完成了操作：数据库回滚了，Redis 没有回滚，消息也已经发出。
下面用一组可复现的订单场景记录排查过程。订单号、SKU 和日志都是脱敏的测试数据，重点是把一次失败拆成几个可验证的动作，看看事务到底保护了哪一段。
### 先画出这次下单经过了什么
示例流程如下：
    
    请求进入
      -> Redis 预扣库存
      -> 数据库写订单
      -> 发送订单创建消息
      -> 返回下单结果
    
数据库事务只能直接管理加入同一个事务上下文的数据库操作。Redis 预扣、消息发送和 HTTP 调用都在数据库事务之外，除非系统额外设计了跨资源事务或补偿机制，否则数据库回滚不会自动撤销它们。
测试数据先固定下来，方便失败后对账：

数据| 初始值  
---|---  
SKU| `SKU-TX-001`  
数据库可用库存| 10  
Redis 预扣库存| 10  
请求号| `REQ-TX-001`  
订单号| `ORD-TX-001`  
预期结果| 要么完整创建订单并扣库存，要么按约定恢复  

本例假设数据库库存是最终对账依据，Redis 只负责预扣，实际项目如果把 Redis 当作库存主数据源，断言需要按真实架构调整。除了订单表，还要准备数据库库存流水、Redis 预扣流水、Outbox 表、消息消费记录和 Redis Key 的查询方式，并把它们的事务归属写清楚。数据库库存流水如果和订单共用同一事务，应该随事务一起回滚；Redis 预扣流水属于独立资源，可能需要单独回补。只查订单表，很容易把“订单没有写进去”误判成“整个业务没有发生”。
这里的 Redis 预扣库存和数据库库存不是两份可以相加的销售库存。Redis 只是提前占住名额，数据库记录才是本例的最终账本；成功和失败路径都要验证两者如何同步，不能看到两个数字就把它们相加后判断库存是否正确。
### 先确认数据库事务真的生效
以常见的 Spring 服务为例，下面的代码看起来像是一个事务，但测试时不能只看注解：
    
    @Transactional
    public void createOrder(OrderCommand command) {
        orderRepository.insert(command.toOrder());
        inventoryRepository.freeze(command.skuId(), command.quantity());
    }
    
准备一个确定会失败的故障点：先让订单插入和数据库库存冻结都成功，再在事务提交前抛出异常。调用接口后检查两件事：订单插入和库存冻结是否都没有落库。也可以用重复订单号触发约束异常，但要确保异常发生前已经执行过一条成功的数据库写入，否则只能验证“写入失败”，不能验证“已写入数据被回滚”。日志中还要确认两个 Repository 使用的是同一个数据源和事务连接，不能一个操作走主库，另一个操作悄悄走了另一套连接。
如果项目使用 Spring，还要专门检查两个容易忽略的边界：
  * 默认情况下，未配置 `rollbackFor` 时，`RuntimeException` 和 `Error` 通常触发回滚，受检异常不一定触发回滚；
  * 同一个类里的自调用可能绕过事务代理，导致方法上的 `@Transactional` 没有真正生效。
  * 异常被方法内部捕获后如果没有继续抛出，事务拦截器可能认为方法正常结束；这种“失败被吞掉”的路径也要单独检查。
  * `REQUIRES_NEW` 之类的独立事务不会跟随外层事务回滚，审计、补偿或事件记录如果使用了独立事务，必须按各自的提交结果断言。


如果业务规定任何异常都要回滚，可以明确配置异常类型，并用测试验证，而不是只看代码上的注解：
    
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(OrderCommand command) throws Exception {
        orderRepository.insert(command.toOrder());
        inventoryRepository.freeze(command.skuId(), command.quantity());
    }
    
这里的示例只说明事务边界，不代表所有项目都应该把所有异常统一回滚。某些异常需要返回业务失败并保留处理记录，仍然要按实际契约设计。测试要关注“异常发生后哪些数据应该存在”，而不是看到 500 就默认所有东西都消失。
在注入异常前先跑一条正常链路，作为后面对照：订单创建成功，数据库可用库存从 10 变成 9，Redis 预扣库存也变成 9，数据库库存流水有一条 `freeze=1`，Outbox 有一条 `NEW` 事件。若正常链路的账本关系都没有确认，后面看到数据不一致时，很难判断是回滚问题还是初始数据就不完整。
### 第一次复现：数据库回滚了，Redis 库存没回来
为了复现问题，在测试环境的数据库写入成功之后、事务提交之前增加一个只对测试数据生效的故障点，让服务抛出异常。不要通过修改线上参数或让外部请求随意传入故障标记，测试开关应由内部配置控制，执行完成后关闭。
执行顺序如下：
  1. 查询 Redis 和数据库，确认可用库存均为 10。
  2. 提交 `REQ-TX-001`，让 Redis 预扣 1 件成功。
  3. 订单和数据库库存已经写入，但提交前故障点触发异常，数据库事务回滚。
  4. 接口返回失败后，查询订单、库存和库存流水。


一个典型结果是：
    
    接口：500 ORDER_CREATE_FAILED
    订单表：不存在 ORD-TX-001
    数据库库存：available=10
    Redis 库存：available=9
    数据库库存流水：不存在
    Redis 预扣流水：存在 freeze=1，但没有 release=1
    
数据库回滚是正确的，Redis 结果却留下了半笔业务。这里不能简单把 Redis 数值改回 10 作为修复，因为真实系统可能同时有其他请求扣减库存。正确做法通常是使用带业务号的预扣和幂等回补：失败后发送释放指令，释放动作按 `REQ-TX-001` 只执行一次，并检查 Redis 预扣流水是否完成。
回补测试至少包含三种结果：订单写入失败后立即回补、回补请求超时后重试、回补服务自身再次失败。最后一种不能直接丢弃，应该保留待处理记录并告警，否则库存会慢慢被吞掉。
补偿记录不能无条件和订单写入放在同一个失败事务里。如果订单事务回滚，事务内创建的“释放库存”记录也会一起消失；可以使用独立事务写入补偿任务、可靠事件，或通过库存预扣流水扫描出未关联订单的记录。具体方案不同，但必须保证回补凭证不依赖已经失败的那笔事务。
如果回补是异步完成的，接口可以返回失败或“处理中”，但不能返回订单创建成功。测试要把接口响应和补偿状态一起断言：库存尚未回补时，用户侧不能拿到一个已经可支付的订单号，后台也要能看到这笔待处理任务。
### 第二次复现：消息比数据库提交得更早
如果代码顺序是“写订单、发消息、最后提交数据库”，消息发送成功后进程可能在提交前退出：
    
    1. 订单 INSERT 执行成功，但事务尚未提交。
    2. 发送 OrderCreated 消息，消费者收到并开始处理。
    3. 当前服务在 COMMIT 前崩溃，数据库事务回滚。
    4. 消费者已经根据一条不存在的订单发出了通知或扣了积分。
    
这次要同时查看订单表、消息记录和消费者业务表。只要消费者产生了不可撤销的业务副作用，就说明出现了“幽灵消息”。测试时还要让消费者在订单提交前查询订单，确认它遇到不存在的订单时是重试、延迟处理还是进入异常队列，不能让一条空查结果被当成处理成功。
把消息发送挪到数据库提交之后，也只是换了一种风险：数据库提交成功后，进程在发送消息前退出，订单已经创建，消息却没有发出去。这个空档同样要测，不能把“提交后发送”当成完整解决方案。
### Outbox 解决什么，还会留下什么
常见做法是在同一个数据库事务里同时写订单和 Outbox 事件：
    
    BEGIN;
    
    INSERT INTO orders(order_no, user_id, status)
    VALUES ('ORD-TX-001', 'U-TEST-001', 'PENDING_PAYMENT');
    
    INSERT INTO outbox_event(event_id, event_type, aggregate_id, status)
    VALUES ('EVT-TX-001', 'OrderCreated', 'ORD-TX-001', 'NEW');
    
    COMMIT;
    
事务成功后，独立发布任务读取 `NEW` 事件发送到消息系统，再把事件标记为 `SENT`。这样订单和待发送事件可以一起回滚，发布任务失败时也有记录可重试。
Outbox 不是把消息变成绝对只发一次。发布任务可能已经发送成功，却在标记 `SENT` 前崩溃，恢复后会再次发送同一个 `event_id`。因此要继续验证消费者幂等：同一个事件重复到达时，只能产生一次积分、一次通知或一次库存变更。
消费者可以用 `event_id` 唯一记录、业务状态条件更新或幂等表来实现这个约束。测试时不要只看“重复消息被确认”，还要查询积分流水、通知记录和库存流水，确认确认消息没有掩盖重复副作用。
我会按下面的故障点跑一遍：

故障点| 应检查的结果  
---|---  
订单写入失败| 订单和 Outbox 都不存在，库存按约定回补  
Outbox 写入失败| 订单和 Outbox 一起回滚，不允许只留下订单  
发布前进程退出| Outbox 保持 `NEW`，恢复后可以继续发布  
消息发送成功后进程退出| 事件可能重复，但消费者业务副作用只能一次  
标记 `SENT` 失败| 事件可重试，重复发布有明确监控  
消费者处理失败| 消息重试或进入异常队列，不静默丢失  

如果消息必须与数据库事务严格绑定，也可以评估分布式事务方案，但测试范围、性能代价和故障恢复复杂度都会增加。多数订单场景更需要的是本地事务、Outbox、消费者幂等和可追踪补偿，而不是在代码里写一句“发送成功就算完成”。
### 外部接口成功后，数据库又回滚了
订单创建中还可能调用营销、支付或配送服务。外部接口一旦返回成功，数据库事务后面再回滚，远程系统不会跟着撤销。测试可以在“外部调用成功、数据库提交失败”这个顺序上制造异常，检查是否生成了撤销任务或补偿记录。
例如优惠服务已经冻结一张券，订单表因为唯一键冲突回滚，最终至少要满足一个约定：
  * 优惠服务提供幂等取消接口，系统创建取消任务并最终释放优惠券；
  * 或者独立的补偿记录标记为待处理，后续任务按请求号重试释放；
  * 如果业务允许冻结保留，则必须能在后台看到这条异常关联，不能让它永远悬着。


这里的释放任务也不能假设能和订单回滚一起保存。订单事务已经失败时，应由独立事务、外部服务的状态查询或可恢复的资源流水保留这条补偿线索。这个过程允许短暂的最终一致，但必须有状态、重试上限和告警，不能用“稍后会恢复”代替验证。
不能在当前事务里直接调用外部服务，然后把异常吞掉再返回成功。即使接口返回 200，也要核对订单、优惠券、库存、消息和补偿记录是否处于可解释状态。
### 接口超时后重试，回滚问题会再出现一次
还有一组经常被遗漏的场景：服务端事务已经提交，响应却因为网络超时没有到达客户端。客户端把相同请求重新发一次，如果没有幂等控制，第二次可能又冻结库存、又写订单。
测试时给每次请求带上固定的 `requestId`，先让服务端完成提交，再人为延迟响应。客户端超时重试后检查：
  * 同一个请求号只有一张订单；
  * 库存只冻结一次；
  * Outbox 事件按业务约定只产生一条，或重复发布但消费者只处理一次；
  * 第二次请求返回第一次的结果或明确的处理中状态。


如果第二次请求的 SKU、数量或收货人发生变化，应返回幂等参数冲突，不能把第一次订单直接当成新参数的处理结果。幂等记录本身也要和订单状态一起设计，不能只在 Redis 里临时放一个短 TTL Key，过期后又允许重复创建。
还要单独模拟“提交结果未知”：数据库可能已经提交，客户端却在收到确认前断开。此时不能因为客户端看到超时就认定事务回滚，应该用请求号查询最终订单状态，再决定返回原结果还是继续等待。若数据库因死锁回滚，重试也应从事务入口重新执行整笔业务，并继续使用同一个幂等键，不能只重试其中一条 SQL。
### 这几条证据要一起看
一次订单失败后，我会保留同一个 `traceId` 和 `requestId`，对照下面的数据：
    
    traceId=TRACE-TX-001 requestId=REQ-TX-001
    order=absent
    inventory_db=10 inventory_redis=9
    outbox=absent
    db_inventory_flow=absent redis_reservation=freeze:1
    consumer_effect=0
    compensation=WAITING
    
生产环境不建议记录完整 Token 或敏感订单信息，但应保留足够的关联字段。数据库事务 ID、库存流水号、Outbox 事件号、消息 ID 和补偿任务号如果互相对不上，排查时就只能依赖时间猜测。
测试报告也不要只写“事务已回滚”。更准确的结论应该是：数据库订单与 Outbox 是否回滚，Redis 是否回补，消息是否已发送，消费者是否产生副作用，外部资源是否创建补偿任务。每一项都有明确结果，才知道还剩哪一块没有处理。若补偿仍处于 `WAITING`，报告中要写清观察截止时间和后续处理状态，不能在补偿尚未完成时直接判定全链路通过。
### 最后收进回归的场景

场景| 关键断言  
---|---  
事务提交前失败| 数据库订单和 Outbox 按事务一起回滚，Redis 预扣按约定回补  
数据库事务正常提交| 订单、数据库库存流水和待发送事件一致  
Outbox 发布前进程退出| 事件保持可重试状态，不丢失  
消息发送成功后标记失败| 允许重复发布，但消费者副作用只有一次  
外部优惠冻结成功、订单回滚| 有可追踪、可重试的释放或补偿  
消费者处理失败| 进入重试或异常队列，不静默确认  
响应超时后相同请求重试| 订单、库存和事件不重复产生  
相同请求号修改业务参数| 返回幂等参数冲突，不复用错误结果  
事务抛 RuntimeException| 按契约回滚  
受检异常| 按项目配置验证是否回滚，不能凭经验判断  
内部捕获异常后返回失败| 确认事务是否按预期提交或回滚，不能只看接口状态码  
事务方法自调用| 用数据库结果确认事务代理是否真正生效  
外层回滚、内层独立事务提交| 独立事务留下的审计或补偿记录符合设计  
提交结果未知| 用请求号核对最终状态，重试不产生重复业务  
数据库死锁| 整笔事务回滚并有限重试，订单和库存不产生半成品  
补偿任务重复执行| 释放、撤销和状态修复只生效一次  

这组用例最好每次使用独立订单号、请求号和 SKU，先完成断言，再清理 Redis、数据库、消息和补偿记录。共享测试数据没有清理干净时，下一轮很容易把上一次遗留的库存冻结误认为本轮事务没有回滚；如果要验证待处理补偿，也应在记录状态和告警已经采集后再清理。
### 总结
数据库事务回滚只能撤销它管理范围内的数据库变化。订单流程里，Redis 预扣、消息发送、外部接口和异步任务都可能已经产生结果，它们需要通过幂等、Outbox、补偿或明确的状态机继续处理。
排查订单失败时，先用故障点把流程停在不同位置，再同时核对订单、库存流水、Outbox、消息消费、外部资源和补偿记录。接口返回失败、订单表为空，只能说明其中一段回滚了，不能直接代表整个业务已经恢复。
