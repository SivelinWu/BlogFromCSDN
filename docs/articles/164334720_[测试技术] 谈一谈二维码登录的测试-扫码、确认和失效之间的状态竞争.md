# [测试技术] 谈一谈二维码登录的测试-扫码、确认和失效之间的状态竞争

> 原文: https://blog.csdn.net/weixin_42390585/article/details/164334720

> 原创内容，未获授权禁止转载、转发、抄袭。

测试二维码登录时，可以先把测试环境的有效期临时调成30秒，然后专门卡在第29秒扫码、第30秒确认。手机端在提交确认，电脑端仍在轮询，服务端也正好进行过期判定。如果几条链路各自改状态，同一张码可能一会儿显示“已过期”，一会儿又登录成功。
二维码登录看起来只有“展示、扫码、确认”三个动作，实际上是电脑端、手机端和认证服务共同推进一个短命会话。当几个动作同时到达，测试要确认哪一个动作可以改变状态，以及失败的请求是否留下了登录会话。
### 先把一次登录拆开
各家系统的接口名称不同，但常见链路大致如下。这里的名称和报文均是简化示例：
  1. 电脑端创建二维码会话，获得放入二维码的 `qrToken`、过期时间和独立的查询凭据。
  2. 手机端扫描二维码，认证服务记录扫码账号，等待用户确认或取消。
  3. 手机端确认后，服务端将这次授权标记为成功。
  4. 电脑端通过轮询或WebSocket收到结果，使用一次性凭据换取登录会话。


二维码里不应直接放可长期使用的登录Token。`qrToken` 应是高随机、短时有效的不透明值，服务端将它与浏览器的预登录会话关联；查询凭据只交给创建该二维码的浏览器，不放进二维码。数据库和日志中也不宜保留完整凭据，可以像密码重置Token一样只存摘要。
查询接口同样需要校验查询凭据和预登录会话的绑定关系，不能拿到一个会话ID就能查询。待扫码阶段只需返回最小状态，不要把扫码账号、手机号或可换取会话的凭据一起交给前端。
### 测试用例从状态机开始
如果需求只写了“扫码后待确认，超时后失效”，还不足以直接写并发用例。我会先和开发对齐一张状态表：

当前状态| 事件| 允许转入| 需要校验的条件  
---|---|---|---  
`WAIT_SCAN`| 手机扫码| `WAIT_CONFIRM`| 二维码未过期，扫码账号有效  
`WAIT_CONFIRM`| 原账号重复扫码| `WAIT_CONFIRM`| 幂等返回，不改变 `scannerUserId` 和截止时间  
`WAIT_CONFIRM`| 其他账号扫码| 保持不变| 拒绝覆盖已绑定账号  
`WAIT_CONFIRM`| 原扫码账号确认| `CONFIRMED`| 账号与扫码记录一致，且当前时间未到截止点  
`WAIT_CONFIRM`| 手机取消| `CANCELED`| 操作人与扫码账号一致  
`WAIT_SCAN` / `WAIT_CONFIRM`| 超时| `EXPIRED`| 以服务端时间和 `qrExpiresAt` 判定  
`WAIT_SCAN` / `WAIT_CONFIRM`| 电脑端刷新二维码| `SUPERSEDED`| 旧会话不再接受扫码或确认  
`CONFIRMED`| 电脑端换取会话（下文简称“取票”）| `CONSUMED`| 与原浏览器匹配，且未超过 `consumeExpiresAt`  
`CONFIRMED`| 取票超时| `CONSUME_EXPIRED`| 以服务端时间和 `consumeExpiresAt` 判定  

`CANCELED`、`EXPIRED`、`SUPERSEDED`、`CONSUMED` 和 `CONSUME_EXPIRED` 都应视为终态。一张码已经过期，即使延迟的确认请求后来到达，也不能再回到 `CONFIRMED`。前端显示的“已过期”不是权威结果，服务端的状态和时间判定才是。
这里还有两个不能混用的时间：`qrExpiresAt` 限制用户何时之前可以扫码和确认，`consumeExpiresAt` 限制确认成功后的一次性凭据何时之前可被电脑端消费。例如手机在第29.9秒确认成功，电脑在第30.2秒收到结果，只要还在取票期内，就不应因原二维码到期而随机失败。
### 把请求卡在这五个位置
#### 1\. 扫码、确认和过期撞在一起
先记录服务端返回的 `qrExpiresAt`。手工黑盒测试可以选取截止点前1秒和后1秒，分别提交扫码与确认请求；要验证精确边界，则需要可控时钟或服务端测试钩子，不能根据手机的发送时间猜测。按本文契约，服务端处理时间等于截止点时就应拒绝请求。
按上面的状态契约，在截止点到达时，未扫码的会话不再接受扫码，已扫码但未确认的会话也不再接受确认。也就是说，第29.9秒扫码、第30.1秒确认应该失败；手机上即使还停留在确认页，也不能绕过服务端的过期判断。
这组用例如果只靠 `sleep(30)`，调度和网络误差会让问题很难复现。可以让“手机确认”和“过期处理”在同一个并发屏障后释放，再连续执行多次。无论请求到达顺序如何，最终只能是“确认成功”或“二维码过期”之一；数据库与登录会话必须立即一致，缓存和页面则应在约定的同步时间内收敛。
#### 2\. 确认和取消同时提交
同一账号对同一张码并发发送“确认”和“取消”，两个接口不能同时返回业务成功。如果取消先完成，电脑端后续不应获得会话；如果确认先完成，取消请求应返回已确认或冲突，而不是把状态又改回去。
除了接口响应，还要查最终状态、登录会话数量和审计记录。如果“确认成功”和“取消成功”各记了一条日志，即使页面最后只显示一个结果，服务端也已经出现分叉。
#### 3\. 旧码确认遇上电脑端刷新
电脑端刷新二维码后，旧码要立即进入 `SUPERSEDED`。测试时先用手机扫描旧码，停在确认页；电脑端刷新出新码后，再在手机上确认旧码。预期是旧码确认失败，旧码既不能登录原页面，也不能把授权“串”到新码上。
还要用两个独立的浏览器会话重复这组操作，例如普通窗口与无痕窗口。授权结果只能被创建该二维码的预登录会话消费，另一个会话即使拿到查询地址，也不能领取登录结果。
同一浏览器打开两个登录标签页也要测。两个页面共享Cookie，却各自创建了二维码；再让账号A和账号B分别确认。对于依赖Cookie的单账号会话，项目应约定首个成功登录是否作废另一张码，至少不能让后到的确认静默覆盖已登录账号，也不能出现页面显示A、接口却携带B会话的情况。
#### 4\. 重复确认和重复取票
手机在弱网下连续点击确认，或客户端因超时自动重试，都会产生重复请求。确认接口可以返回相同结果，也可以告知已处理，但不能生成多份可消费凭据。电脑端并发取票时，也只能建立一份登录关系。
还要故意丢掉首次取票的响应，然后让电脑端重试。如果服务端已建立登录会话，重试应恢复原结果或识别到当前浏览器已登录，不能既拒绝重试，又让浏览器永远拿不到会话。这里的幂等结果必须绑定原预登录会话，不能对拿到同一查询地址的其他浏览器开放。
登录成功后还要更换预登录阶段的会话ID。OWASP的会话管理建议要求在权限级别发生变化时更新会话ID，否则即使二维码凭据只用了一次，仍可能留下会话固定风险。
#### 5\. 两个账号扫同一张码
首次扫码后，二维码会话应绑定该账号。同一账号因弱网重复扫码可以按幂等请求处理，不同账号再扫时则不能覆盖 `scannerUserId`。还可以在扫码后退出手机账号A，登录账号B再提交原确认页，服务端也应因操作人变化而拒绝。用户需要更换账号时，电脑端应刷新二维码、重开一次会话。
### 服务端要用原子迁移给出唯一结果
状态竞争的典型问题是：两个请求先读到同一个旧状态，再各自写入新状态。MITRE将这类共享资源缺少正确同步的问题归入CWE-362；若校验状态与实际使用之间留有窗口，也符合CWE-367描述的TOCTOU竞态特征。
确认动作可以用条件更新保证只有一个请求改变状态。下面是简化SQL：
    
    UPDATE qr_login_session
    SET state = 'CONFIRMED',
        confirmed_at = :server_now,
        consume_expires_at = :consume_expires_at,
        version = version + 1
    WHERE qr_token_hash = :qr_token_hash
      AND state = 'WAIT_CONFIRM'
      AND scanner_user_id = :current_user_id
      AND qr_expires_at > :server_now;
    
影响行数为1才表示确认成功，这次成功更新就是唯一生效点。影响行数为0时，需要重新读取当前状态，区分已取消、已过期、已替换和已确认。取票也要使用同样的条件更新：
    
    UPDATE qr_login_session
    SET state = 'CONSUMED',
        consumed_at = :server_now,
        version = version + 1
    WHERE query_token_hash = :query_token_hash
      AND browser_session_hash = :browser_session_hash
      AND state = 'CONFIRMED'
      AND consume_expires_at > :server_now;
    
取票状态更新与登录会话创建需要处于同一个事务或可恢复的幂等过程中，否则会出现“已消费但没有会话”或“创建了两个会话”。如果状态放在Redis中，可以使用Lua脚本或等价的原子操作完成“检查 + 更新”。只依赖TTL删Key不够，因为过期清理可能延迟，业务接口仍要比较对应的截止时间和服务端时间。
集群部署时还要考虑节点时钟偏差。同一张码的扫码和确认请求可以分别打到不同节点，SQL中的 `server_now` 应来自统一时钟，或直接使用数据库时间做比较。回归时可以在网关后端替换节点重复截止点用例，看结果是否会随节点变化。
WebSocket推送和轮询只负责传递状态，不能各自计算结果。消息延迟或乱序时，前端可以根据单调递增的 `version` 忽略旧消息，避免页面从“已确认”又退回“待确认”。
### 别只看页面提示
每组并发用例至少要对齐下面几类证据：
  * 手机端和电脑端的接口响应，包括业务错误码；
  * 二维码会话的最终 `state`、`version`、`scannerUserId` 和消费时间；
  * 新建登录会话的数量、归属账号和浏览器绑定关系；
  * 审计日志中的扫码、确认、取消、过期和消费顺序，以及服务端处理时间和Trace ID。


日志应记录脱敏后的会话标识和状态版本，不要打印完整 `qrToken`、登录Token或二维码内容。需要多次重复竞态用例时，可以统计每种最终状态的次数，但不能把“100次都没复现”当成没有并发问题的证明。更可靠的依据是原子状态转移，以及能稳定打开竞争窗口的自动化用例。
### 二维码还可能被转发
二维码是跨设备授权的载体，截图发给别人后，对方也可能完成扫码。手机端不宜“扫到即登录”，确认页应显示正在授权的客户端、大致位置或两端一致的短校验码，并要求用户主动确认。测试时要核对这些信息确实属于当前预登录会话，而不是一段固定文案。RFC 8628在跨设备授权场景中也特别提到远程钓鱼和窃看会话风险，建议让用户知道自己在授权哪台设备。
需要说明的是，RFC 8628定义的是OAuth 2.0设备授权流，不等同于所有网站的二维码登录实现。它对 `authorization_pending`、`slow_down`、`access_denied` 和 `expired_token` 等轮询结果的定义，以及过期后停止轮询的要求，可以用来审视自己项目的状态契约。如果服务端返回降低轮询频率的指令，客户端也要实际遵守，不能在待扫码页面上持续打满接口。
还可以用随机无效 `qrToken` 验证限频和错误响应。接口不应因为Token“不存在、已过期、已扫码”而返回可被批量利用的详细账号信息，扫码和查询接口也都要有合理的频率限制。
### 这些组合值得留进回归

场景| 主要断言  
---|---  
未扫码、已扫码、已确认| 电脑端展示与服务端状态一致  
扫码或确认与过期并发| 只有一个结果能生效，终态不回退  
到期前确认，到期后电脑端取票| 在 `consumeExpiresAt` 之前可正常消费，超时后拒绝  
确认与取消并发| 只有一个请求改变状态  
刷新后确认旧码| 旧码失败，不影响新码，不串浏览器会话  
同一浏览器两个标签页分别登录A和B| 结果符合单账号会话契约，不静默覆盖、不出现页面与会话串号  
重复扫码、重复确认、重复换取| 不产生额外凭据或登录会话  
同一账号重复扫码| 幂等返回，不重置过期时间，不重复记录副作用  
两个账号扫同一张码| 首个账号绑定保持不变，另一账号无法确认  
扫码后手机切换账号再确认| 因操作人与 `scannerUserId` 不一致而拒绝  
码已过期但清理任务延迟| 业务仍按 `qrExpiresAt` 拒绝扫码和确认  
WebSocket断开、消息乱序或轮询超时| 重连后恢复权威状态，不倒退、不重复登录  
二维码截图在另一设备扫描| 必须显式确认，展示可识别的授权对象信息  
登录成功后重放二维码凭据| 凭据已消费，无法创建第二个会话  

这张表只是通用基线。项目如果还有账号风控、企业租户、多端互斥或二次验证，需要把它们继续加到状态机中，不要在页面上临时补几个分支了事。
### 总结
测试二维码登录时，我更关心它作为一次跨设备、短时效、单次消费的授权过程是否可控。正常扫码只能证明主流程可用；扫码和确认与过期、取消、刷新和重试相遇时，更容易暴露状态分叉。
执行这类用例时，页面提示、接口响应、最终状态和会话副作用要一起检查。服务端用原子更新决定唯一结果，前后端都以该结果为准，即使请求换了到达顺序，登录结果也不会跟着变。
