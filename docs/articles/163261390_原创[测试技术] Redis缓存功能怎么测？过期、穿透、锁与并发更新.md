# 原创[测试技术] Redis缓存功能怎么测？过期、穿透、锁与并发更新

> 原文: https://blog.csdn.net/weixin_42390585/article/details/163261390

> 原创内容，未获授权禁止转载、转发、抄袭。

Redis 接口返回成功，不代表缓存逻辑可靠。线上常见问题往往出现在 `set/get` 之外：缓存没有按预期失效、同一无效参数反复访问数据库、锁没有过期时间，以及并发更新覆盖。
本文用商品缓存作为例子，不罗列 Redis 命令，重点说明这些风险应该如何验证。
### 先把风险转换成可观察结果

风险| 只检查返回值会漏掉什么| 应验证的结果  
---|---|---  
缓存未过期| 每次请求都回源| 连续读取只调用一次数据源  
缓存过期| 旧值一直存在，或过期后没有重建| Key 消失后再次回源  
缓存穿透| 不存在的数据反复查询数据库| 空值被短暂缓存，第二次不回源  
锁使用错误| 加锁成功，但进程异常后锁不释放| `NX` 互斥成立，且 TTL 存在  
并发更新| 多个请求读到旧值并相互覆盖| 并发完成后的最终值正确  

这类测试应连接独立的真实 Redis。Mock 适合验证业务分支，却无法证明 TTL、事务冲突和服务端命令语义。

自动化测试不要连接开发或生产 Redis。下面只展示 fixture 的关键结构：测试启动临时实例，关闭 RDB 和 AOF，并在每条用例前后执行 `FLUSHDB`。
    
    @pytest.fixture(scope="session")

            REDIS_SERVER,

            host="127.0.0.1",

        )
        wait_until_ping_succeeds(client)

        try:
            client.shutdown(nosave=True)

其中 `find_free_port()` 负责获取空闲端口，`wait_until_ping_succeeds()` 应使用带截止时间的轮询，不能用固定休眠猜测 Redis 是否已启动。正文只保留与测试方法有关的片段，不作为可直接复制的完整工程；CI 中也可以使用容器启动 Redis，但仍要做到实例独立、端口隔离和测试后清理。
### 过期测试不要卡死在某个毫秒
商品缓存读取逻辑如下。正常数据缓存 60 秒，不存在的数据只缓存 5 秒：
    
    import json
    
    
    MISSING_VALUE = "__MISSING__"
    
    
    class ProductCache:
        def __init__(self, redis_client, loader, data_ttl=60, missing_ttl=5):
            self.redis = redis_client
            self.loader = loader
            self.data_ttl = data_ttl
            self.missing_ttl = missing_ttl
    
        def get_product(self, product_id):
            key = f"product:{product_id}"
            cached = self.redis.get(key)
            if cached is not None:
                return None if cached == MISSING_VALUE else json.loads(cached)
    
            product = self.loader(product_id)
            if product is None:
                self.redis.set(key, MISSING_VALUE, ex=self.missing_ttl)
            else:
                self.redis.set(key, json.dumps(product), ex=self.data_ttl)
            return product
    
TTL 测试不应断言“必须等于 60”。命令执行和断言之间存在耗时，在秒级 TTL 下应验证合理区间：
    
    def test_product_cache_has_ttl(redis_client):
        cache = ProductCache(
            redis_client,
            lambda product_id: {"id": product_id},
            data_ttl=60,
        )
    
        cache.get_product("1001")
    
        assert 1 <= redis_client.ttl("product:1001") <= 60
    
验证过期后的行为时，也不要简单 `sleep(1)` 后立即断言。使用截止时间轮询 Key 是否消失，再检查数据源被重新调用：
    
    deadline = time.monotonic() + 2.5
    while redis_client.exists("product:1001") and time.monotonic() < deadline:
        time.sleep(0.02)
    
    assert redis_client.exists("product:1001") == 0
    cache.get_product("1001")
    assert calls == ["1001", "1001"]
    
这里验证的不是 Redis 能否过期，而是业务在缓存失效后能否重新加载。真实项目还应根据容量和流量检查 TTL 是否加入随机抖动，避免大量热点 Key 在同一时刻失效。
### 防穿透要检查“没有再次回源”
只断言接口第二次仍返回 `None`，无法证明空值缓存生效。测试还要观察数据源调用次数和空值 TTL：
    
    def test_missing_product_is_cached_with_shorter_ttl(redis_client):
        calls = []
    
        def load_missing_product(product_id):
            calls.append(product_id)
            return None
    
        cache = ProductCache(
            redis_client,
            load_missing_product,
            data_ttl=60,
            missing_ttl=5,
        )
    
        assert cache.get_product("404") is None
        assert cache.get_product("404") is None
        assert calls == ["404"]
        assert redis_client.get("product:404") == MISSING_VALUE
        assert 1 <= redis_client.ttl("product:404") <= 5
    
空值 TTL 通常应短于正常数据，否则新创建的商品可能在较长时间内仍被判定为不存在。`MISSING_VALUE` 也不能与合法业务值冲突，生产代码可采用带类型字段的序列化结构。
空值缓存只能拦截对同一无效 Key 的重复访问。如果请求不断使用不同的随机 ID，仍会持续回源，还需要结合参数校验、限流或布隆过滤器处理。
### `SET NX EX` 要作为一个整体验证
先 `SETNX`、再单独 `EXPIRE` 存在中间失败窗口，可能留下永久锁。Redis 的 `SET` 支持同时传入 `NX` 和 `EX`，测试应确认互斥与过期时间同时成立：
    
    def claim_refresh_lock(redis_client, product_id, ttl=5):
        return bool(
            redis_client.set(
                f"lock:product:{product_id}",
                "1",
                nx=True,
                ex=ttl,
            )
        )
    
    
    def test_refresh_lock_is_exclusive_and_has_ttl(redis_client):
        assert claim_refresh_lock(redis_client, "1001", ttl=5) is True
        assert claim_refresh_lock(redis_client, "1001", ttl=5) is False
        assert 1 <= redis_client.ttl("lock:product:1001") <= 5
    
这个顺序用例只验证同一个 Key 第一次获取成功、再次获取失败，并确认锁带有 TTL，不代表已经覆盖并发竞争，也不是完整的分布式锁测试。正式锁还要使用唯一持有者标识，并通过 Lua 脚本或等价原子操作校验持有者后删除，避免误删其他请求后来取得的锁。
### 并发更新看最终状态，不只看单次成功
下面是典型的读改写操作。没有并发控制时，多个线程可能读到同一个旧值，最终计数小于实际更新次数。Redis 事务可以用 `WATCH` 做乐观并发控制：Key 被其他客户端修改时，`EXEC` 失败，客户端重新读取并重试。
    
    from redis.exceptions import WatchError
    
    
    def increment_with_watch(redis_client, key, max_retries=1000):
        for _ in range(max_retries):
            with redis_client.pipeline() as pipe:
                try:
                    pipe.watch(key)
                    current = int(pipe.get(key) or 0)
                    pipe.multi()
                    pipe.set(key, current + 1)
                    pipe.execute()
                    return
                except WatchError:
                    continue
        raise RuntimeError(f"failed to update {key} after {max_retries} retries")
    
测试同时启动 8 个线程，每个线程更新 30 次。必须调用每个 `Future.result()`，否则工作线程中的异常可能不会让用例失败：
    
    from concurrent.futures import ThreadPoolExecutor
    
    
    def test_watch_prevents_lost_updates(redis_client):
        workers = 8
        updates_per_worker = 30
    
        def update_many_times():
            for _ in range(updates_per_worker):
                increment_with_watch(redis_client, "inventory:1001")
    
        with ThreadPoolExecutor(max_workers=workers) as executor:
            futures = [executor.submit(update_many_times) for _ in range(workers)]
            for future in futures:
                future.result()
    
        assert redis_client.get("inventory:1001") == str(
            workers * updates_per_worker
        )
    
固定重试上限可以避免高竞争时无限循环。这条测试证明的是当前并发规模下没有丢失更新，不代表已经完成性能测试；吞吐量、冲突率和延迟应在独立的压测环境中测量。对于单纯计数，生产代码应优先使用原子的 `INCR`；复杂更新在高竞争下还要评估 `WATCH` 重试成本，并与 Lua 脚本等服务端原子方案比较。

### 测试边界
  * 单元测试可以 Mock 数据源，快速验证命中、未命中和异常分支。
  * 集成测试应连接独立 Redis，验证命令语义、TTL、事务、序列化和连接配置。
  * 故障与性能测试应使用独立环境，注入网络延迟、进程重启和节点切换，并观察业务降级与恢复结果。
  * 测试清理只能作用于专用实例或专用数据库，禁止对共享环境直接执行 `FLUSHDB`。


### 总结
Redis 测试的重点不是证明命令能执行，而是验证缓存失效后系统是否仍然正确。测试时应连接独立的真实 Redis，并把回源次数、TTL、锁状态和并发最终值变成断言，才能覆盖真正影响线上稳定性的风险。
