# [测试技术] 优惠券只剩1张，两个账号却都领到了

> 原文: https://blog.csdn.net/weixin_42390585/article/details/164807300

> 原创内容，未获授权禁止转载、转发、抄袭。

测试优惠券时，可以先把库存调成最小值。下面是一组测试环境可复现的场景：准备一张限量券，用账号A和账号B同时发起领取。如果两个请求都返回领取成功，后台又出现两条有效领取记录，问题就落在并发与数据一致性上，需要继续排查。
只看库存数字，很容易误以为没有超卖。优惠券是否真正超卖，要把库存、领取记录、使用记录和订单优惠金额放在一起对。这篇记录用脱敏后的测试数据说明如何复现、定位和回归这类问题。
### 先把领取规则写清楚
我们先按一次性领取来设计这组测试数据：

数据项| 值  
---|---  
优惠券| `COUPON-TEST-01`  
总库存| 1  
每人限领| 1  
每订单限用| 1  
适用商品| 测试商品A  
有效期| 测试环境内可控  

这几个限制要分开验证。“每人限1张”是账号维度规则，“总库存1张”是活动维度规则，“每单限1张”则是订单维度规则。把它们都写成“判断失败”，后面很难判断到底是哪一层漏了。
### 库存为1时怎么复现
单请求先跑通，确认正常用户可以领到一张，库存减为0，重复领取会返回库存不足。然后使用两个不同账号，只并发执行领取接口：
    
    POST /api/coupons/COUPON-TEST-01/claim HTTP/1.1
    Authorization: Bearer &lt;token-a&gt;
    Content-Type: application/json
    
    {"orderId":"ORDER-A-1001"}
    
    
    POST /api/coupons/COUPON-TEST-01/claim HTTP/1.1
    Authorization: Bearer &lt;token-b&gt;
    Content-Type: application/json
    
    {"orderId":"ORDER-B-1002"}
    
我不会用手动同时点两下来判断并发，这个时间差不可控。更可复的方式是让两个请求先到达并发屏障，再同时释放，并重复执行。如果没有并发测试工具，也可以在测试代码里用倒数门闭塞两个请求。
#### 先看返回，再看数据
测完后同时保留两个请求的Trace ID，对照下面几项：
  * 成功返回的请求数和失败返回的请求数；
  * 优惠券库存的剩余值；
  * 领取记录是否一人一条；
  * 订单实际优惠金额和优惠券使用状态；
  * 库存流水、领取记录和订单优惠是否能用Trace ID对上。


如果两个请求都返回成功，还要区分两种情况：一是真的创建了两条有效领取记录；二是接口重试返回了同一条幂等记录。不要只根据返回码判断超卖。
### 问题通常出在哪一步
一种常见的错误实现是先查库存，再扣减，两步之间没有原子性：
    
    SELECT stock
    FROM coupon_stock
    WHERE coupon_id = :coupon_id;
    
    UPDATE coupon_stock
    SET stock = stock - 1
    WHERE coupon_id = :coupon_id;
    
库存只剩1张时，两个请求都可能先查到 `stock = 1`，然后分别扣减并创建领取记录。如果更新语句还没有 `stock > 0` 条件，还可能出现库存变成负数。库存不变成负数，也不代表没有超卖；领取记录和订单优惠才是最终证据。
### 先扣库存，再写领取记录也不一定够
把库存扣减改成条件更新，是一个常见修复方向：
    
    UPDATE coupon_stock
    SET stock = stock - 1,
        version = version + 1
    WHERE coupon_id = :coupon_id
      AND stock > 0;
    
只有影响行数为1时才能继续创建领取记录。这个方案能防住库存减成负数，但后面仍有两个问题要测：领取记录写失败时库存是否补回，以及同一账号重试时是返回原记录还是又扣一次。
幂等要另有一个识别请求的键。当前规则是“每人限1张”，所以服务端应以“账号 + 优惠券”建立唯一约束：
    
    CREATE UNIQUE INDEX uk_coupon_claim
    ON coupon_claim(coupon_id, user_id);
    
重复请求命中唯一键时，接口应返回原领取记录或可识别的“已领取”结果，不应又扣库存。唯一索引是最后一道约束，不代替库存扣减和补偿事务。  
如果业务改为“每人可领多张，但每单限1张”，则应另按 `coupon_id + order_id` 建立约束，两种规则不能用同一个索引代替。
如果领取记录和库存在同一个数据库中，可以放在同一个事务里。如果库存在Redis、领取记录在数据库，就不能用“先扣Redis，写库失败就不管了”来结束。这里要测消息补偿、重试和库存回补，否则库存会慢慢被吃掉。
### 库存通过了，优惠金额还要继续查
优惠券领取成功不等于订单一定只使用了一次优惠。我会用同一个账号重复提交、用两个账号同时下单，再检查：
  * 是否只创建一条有效的领取记录；
  * 是否只有一张订单计入优惠金额；
  * 取消订单、支付失败、退款后，优惠券是否按规则释放；
  * 同一订单重试优惠计算时，优惠金额是否被重复计入。


如果领取接口里带了 `orderId`，要验证订单属于当前账号，并且商品、金额和优惠券规则都匹配。不能因为库存扣减是正确的，就放过了修改他人订单或套用不适用优惠券的入参。
### 我留下的回归组合

场景| 主要断言  
---|---  
单账号首次领取| 只成功一次，库存和领取记录一致  
两个账号并发领取，库存为1| 只有一个成功，不出现两条有效领取记录  
同账号并发重试| 幂等返回，不重复扣库存  
领取记录写失败| 库存按约定回补，不留孤立成功状态  
订单取消、支付失败| 按业务规则释放或保留，不重复增加库存  
退款后重新使用| 按业务规则判断是否释放，释放次数、订单状态和领取记录对齐  
两个账号同时创建订单| 只有一单使用优惠，金额不被重复减免  
修改他人 `orderId`| 订单归属校验失败，不消耗优惠券  
缓存、数据库、消息延迟| 最终数据可对账，补偿任务可重试且幂等  

这组回归不是只看“只有一个请求返回200”。领取、使用、释放、回补和订单优惠要能对上，一条记录不一致就足以继续往下排。
### 总结
优惠券并发测试要把库存、领取记录、订单优惠和释放回补放在同一条数据链路上。库存为1时，两个账号中最多只能有一个有效领取，且重试不能重复扣减。
测试时先用可控的库存和账号构造竞争窗口，再用Trace ID对照请求、库存、领取、订单和补偿数据。修复后要重跑写失败、超时重试、取消和退款，否则很可能只修好了“同时领取”这一个断面。
